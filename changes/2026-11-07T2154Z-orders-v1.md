## What and why

A signed API-key request can now name its own receive window, so a client
decides how late a request may still be processed (the `recvWindow` of other
venues). Until now every signed request was accepted for a fixed 10 seconds
either side of the server clock.

- New optional request header `X-API-RECV-WINDOW`: a whole number of
  milliseconds from 1 to 60000. Without it the window is 10000, today's
  behavior. A request is processed only while the server clock is at most
  its `X-API-TIMESTAMP` plus the window; a timestamp more than 10 seconds
  ahead of the server clock is refused whatever the window.
- When the header is sent it is signed: the canonical string gains a line
  with the header value, exactly as sent, right after the timestamp line:

  ```text
  <timestamp>\n<recvWindow>\n<METHOD>\n<path>\n<canonical query>\n<sha256 hex of body>
  ```

  Without the header the canonical string is unchanged.
- A request that arrives after its window is refused as before with
  `TIMESTAMP_SKEW` (`AUTH_TIMESTAMP_SKEW`).
- New refusal `RECV_WINDOW_INVALID` (REST problem code, HTTP 401) and
  `AuthErrorCode.AUTH_RECV_WINDOW_INVALID = 56` (ConnectRPC
  `unauthenticated` with `AuthErrorDetail`) for a header that is not one
  whole number from 1 to 60000, empty, or repeated. A session-token (JWT)
  request that sends the header is refused `UNAUTHENTICATED`.
- New `ErrorCode.ERROR_CODE_REQUEST_DEADLINE_EXCEEDED = 308` on orders and
  triggers writes: the request passed authentication but its window ended
  before it was sent on for admission. Nothing changed. REST answers HTTP 400
  with code `REQUEST_DEADLINE_EXCEEDED`; ConnectRPC answers
  `failed_precondition` with an `ErrorDetail`. It is never an unknown outcome:
  a request that may have been admitted still answers the `*_OUTCOME_UNKNOWN`
  codes.
- Trading WebSocket, protobuf encoding: `tradews.v1.ClientFrame` gains
  `timestamp_ms` (field 3) and `recv_window_ms` (field 4). With
  `timestamp_ms` set, a command arriving after `timestamp_ms` plus
  `recv_window_ms` (10000 when zero), or waiting past it before being sent
  on, is rejected with `CommandReject.code` `REQUEST_DEADLINE_EXCEEDED`.
  Either way the command has taken its `seq` (the next command uses the next
  one), nothing changed, and the session continues. A timestamp more than
  10 seconds ahead, a window above 60000, or a window without a timestamp is
  rejected `BAD_REQUEST` without taking the `seq`. Ping ignores both. The SBE
  encoding does not carry a receive window yet.

## How clients use it

Sign with a 5-second window:

```http
POST https://<api-host>/v1/orders
X-API-KEY-ID: ak_...
X-API-TIMESTAMP: 1762553700123
X-API-RECV-WINDOW: 5000
X-API-NONCE: 4f1c...
X-API-SIGNATURE: <ed25519 over "1762553700123\n5000\nPOST\n/v1/orders\n\n<sha256 hex of body>">
Content-Type: application/json

{"order": {...}}
```

The same headers apply to ConnectRPC calls such as
`POST /orders.v1.OrdersService/CreateOrder` and to every other signed API.

Trading WebSocket (protobuf):

```json
{"seq": 7, "correlationId": "c-7", "timestampMs": "1762553700123", "recvWindowMs": 2000,
 "createOrder": {"order": {...}}}
```

## Migration

No code change is required: the header and the WebSocket fields are
optional, and without them a request is signed and accepted on arrival as
before (a timestamp within 10 seconds either side of the server clock).

One behavior changes for every signed request, with or without the header:
its window (10 seconds without the header) now also applies until the
request is sent on for admission. A request accepted on arrival that then
waits past its timestamp plus its window, which before was processed late,
is now answered `REQUEST_DEADLINE_EXCEEDED` (308) and changes nothing.
Handle it like `TIMESTAMP_SKEW`: sign the request again with a fresh
timestamp and send it again.
