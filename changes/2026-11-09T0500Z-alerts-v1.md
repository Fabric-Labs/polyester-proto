## What and why

**Availability:** devnet only. Not available on testnet yet; the service isn't deployed or routed there.

`UpdateAlertRequest` gains an optional `idempotency_key`, with the contract
`CreateAlertRequest` already has. A client that retries an update after a lost
answer, or replays it after a restart, sends the same key, and the update
applies at most once.

The same key and request (the alert, the fields it sets and their values;
`expected_revision` aside) return the alert in its current state and apply
nothing again. That holds even when the alert fired or changed since: a
replayed update never sets a fired alert again, and never overwrites a later
change. Another request under the same key is `ALREADY_EXISTS` with
`IDEMPOTENCY_CONFLICT`. Keys are per caller and kept as long as their alert,
like create keys, so a repeat is recognized however late it comes.

`UpdateAlertResponse` also gains `outcome` (`UpdateOutcome`), what the call
did as decided where it was applied: `APPLIED` (it changed the alert),
`UNCHANGED` (the alert already held the requested values) or `REPLAYED` (the
key was already used for this request; nothing was applied now, and the alert
is returned as it is now). A client tells a retry or replay from a fresh change
by this field, never by comparing revisions.

`update_mask` may now be empty: an update that names no field changes no
field. It sets a fired (`TRIGGERED`) alert again, and changes nothing on an
`ACTIVE` one (`UNCHANGED`). This is the way to set a fired alert again as it
is: the request carries nothing read from the alert, so a retry or replay under
the same key is the same request even after the alert changed in between. The
mask itself stays required; a request without one is `INVALID_ARGUMENT`.

An alert keeps at most 1,000 update keys. An update with a new key beyond that
is `FAILED_PRECONDITION` with the new error code `ALERT_UPDATE_LIMIT_REACHED`;
repeats of stored keys and updates without a key still work.

## How clients use it

```http
POST /alerts.v1.PriceAlertService/UpdateAlert
Content-Type: application/json

{"alertId": "1234", "update": {"priceTicks": "85000000000000"},
 "updateMask": "priceTicks", "expectedRevision": "1",
 "idempotencyKey": "run-7:tool-3"}
```

To set a fired alert again without changing it, send an empty mask and no
values:

```http
POST /alerts.v1.PriceAlertService/UpdateAlert
Content-Type: application/json

{"alertId": "1234", "update": {}, "updateMask": "",
 "expectedRevision": "3", "idempotencyKey": "run-7:tool-4"}
```

Use one key per intended change, and the same key for every retry of that
change. A retry may read the alert again and send its current revision as
`expected_revision`; the key still matches.

## Migration

None: the field is optional, and an update without it behaves as before. An
empty `update_mask`, refused before, is now accepted and changes no field.
