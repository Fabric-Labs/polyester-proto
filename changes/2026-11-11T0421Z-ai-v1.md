## What and why

A run in an existing conversation now also reports the memories the user saved
or changed in their other conversations since the assistant's previous answer in
this one, whatever the new message is about. Before, the assistant only saw
memories relevant to the message, so a fact the user had just saved elsewhere
could be missed when the next message was worded differently.

**Availability:** devnet only.

No message, field or enum changes. The `MemoriesRecalled` documentation now
covers a second kind of call: when there are such memories, the run reports a
`memory_updates` tool call (`ToolStarted`, then `ToolFinished` with `ok` true)
followed by a `MemoriesRecalled` event with that call's `tool_call_id`, before
the answer. Its `memories` are newest first, at most 20, never empty and never a
profile memory. A run with no such memories has no `memory_updates` call.

## How clients use it

Watch a run as before (`/ai.v1.AssistantService/WatchRun`). To show that memory
was updated from another conversation, look for a `ToolStarted` event named
`memory_updates`:

```json
{"seq": "4", "toolStarted": {"toolCallId": "memory-updates", "name": "memory_updates", "input": {"limit": 20}}}
{"seq": "5", "toolFinished": {"toolCallId": "memory-updates", "name": "memory_updates", "ok": true}}
{"seq": "6", "memoriesRecalled": {"toolCallId": "memory-updates", "memories": [{"memoryId": "1234567890123456789", "text": "Is saving up for a sailboat.", "kind": "FACT"}]}}
```

The `memory_id` values are the ones `DeleteMemory` takes.

## Migration

None: no wire change. A client that counts every `MemoriesRecalled` event as
memories relevant to the message should count only those of `recall_memories`
calls, and show `memory_updates` ones apart.
