## What and why

API keys can now read account and security data that previously required an interactive session, each read gated by its own permission on the key's API-key policy. `PolicyAction` gains six account permissions, valid on API-key policies only:

| Permission | Calls it opens to an API key | Scope |
| --- | --- | --- |
| `READ_API_KEYS` | `ListApiKeys`, `GetApiKey` | A key scoped to the main account reads the main account's keys and those of its sub-accounts; a key scoped to a sub-account reads only that sub-account's keys. |
| `READ_API_POLICIES` | `ListApiPolicies`, `GetApiPolicy` | Main-account key: every API-key policy of the main account. Sub-account key: only the policies attached to that sub-account's keys. |
| `READ_SUBACCOUNT_POLICIES` | `ListSubaccountPolicies`, `GetSubaccountPolicy` | Main-account key: every sub-account policy. Sub-account key: only its sub-account's attached policy. |
| `READ_SUBACCOUNT_PERMISSIONS` | `GetEffectiveSubaccountPermissions` | What the key itself may do on a sub-account within its scope. |
| `READ_VIP_STATUS` | `GetVIPStatus` | Main-account keys only. |
| `READ_SOCIAL_VERIFICATION` | `GetSocialVerification` | Main-account keys only; the response carries the link status only. |

Each permission grants exactly its reads and implies no other permission or any write. Account and policy writes stay session-only. Interactive sessions behave as before.

## How clients use it

Grant the permissions on the key's API-key policy with an interactive session, for example over ConnectRPC `/auth.v1.PolicyService/UpdateApiPolicy`:

```json
{
  "policyId": "<decimal-fixed64-policy-id>",
  "policy": {"actions": ["READ_SPOT", "READ_API_KEYS", "READ_VIP_STATUS"]},
  "updateMask": "actions",
  "expectedRevision": "3"
}
```

The key then signs the reads as any API-key request, for example `GET /v1/vip/status` or ConnectRPC `/vip.v1.VIPService/GetVIPStatus` with `{}`. `GET /v1/auth/social/verification?provider=TWITTER` returns `provider`, `method`, `handle`, `status`, and `verifiedAt` to an API key, and leaves every other field empty.

A key without the permission is refused with `PERMISSION_DENIED` and `AUTH_API_KEY_ACCESS_DENIED`, and the message names the missing permission. A key scoped to a sub-account calling a main-account read is refused the same way. A target outside the key's scope answers `NOT_FOUND`. A sub-account policy that names an account permission is refused with `INVALID_ARGUMENT`.

`GetEffectiveSubaccountPermissions` answers an API key with `role` `OWNER`, because keys belong to the main account, and only the permissions its API-key policy also grants and that API keys can use.

## Migration

None: the permissions are new, and existing policies and sessions keep their behavior.
