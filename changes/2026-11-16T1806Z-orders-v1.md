## What and why

A modify, or a batch replace item, whose new price is off the pair's tick or
whose new quantity is off the pair's step now names the refused field, as a
create or a batch create item does for the same mistake.

- **Before:** `ModifyOrder` and `BatchReplaceOrders` refused such a value
  `PRICE_TICK_SIZE` or `QTY_STEP_SIZE` with an empty `violations` list,
  unless the decimal was finer than its scale.
- **Now:** the refusal carries one field violation, rule `tick_size` or
  `step_size`, with the message create answers. A batch replace item is
  still refused alone, at its `itemIndex`; the other items proceed.

No message, field, enum value, code or status is added or changed.

## How clients use it

Read the violation of a refused item or modify:

```text
POST /v1/orders/replace-batch
{"requestId":"r-1","symbol":"XRP-USDT","items":[
  {"orderId":"<A>","newPrice":"0.5002"},
  {"orderId":"<B>","newPrice":"0.47231"}]}

results[1] = {"itemIndex":1,"status":"REJECTED","code":"PRICE_TICK_SIZE",
  "error":{"code":"PRICE_TICK_SIZE","violations":[
    {"fieldPath":"items[1].newPrice","ruleId":"tick_size",
     "message":"price does not align with the pair tick size"}]}}
```

ConnectRPC (`/orders.v1.OrdersService/BatchReplaceOrders`,
`/orders.v1.OrdersService/ModifyOrder`) names the proto fields:
`items[1].new_price_ticks`, `items[1].new_qty_scaled`, `new_price_ticks` and
`new_qty_scaled`. REST `POST /v1/orders/modify` names `newPrice` and
`newQtyScaled`.

## Migration

None: the codes and statuses are unchanged, and a violation is added where
the list was empty.
