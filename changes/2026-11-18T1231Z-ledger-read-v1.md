## What and why

While balance history is being rebuilt, for example for some minutes after a
network reset, the ledger read API now serves every read that does not need
history. `GetBalances`, `GetPortfolioEquitySnapshot` and `ListTransfers`
answer as usual. They used to answer 503 / Unavailable with the generic
problem code `UNAVAILABLE` ("The service is starting or temporarily
unavailable") until the history was ready.

Only the history reads wait: `GetBalanceHistory`, `GetEquityHistorySeries` and
`GetPortfolioEquityHistorySeries`. Until the history is ready they answer
503 / Unavailable with problem code `UPSTREAM_ERROR`, a detail starting with
`balance_history_uncertified:` and `Retry-After: 5`. They serve again as soon
as it is ready.

## How clients use it

Calls are unchanged. A history read during a rebuild answers:

```bash
curl -sS -i 'https://<api-host>/v1/balances/history?range=1d' \
  -H 'Authorization: Bearer <session token>'
# ConnectRPC: POST https://<api-host>/ledger.read.v1.LedgerReadService/GetBalanceHistory {"range": "DAY_1"}
```

```text
HTTP/1.1 503 Service Unavailable
Retry-After: 5
Content-Type: application/problem+json

{"status": 503, "code": "UPSTREAM_ERROR",
 "detail": "balance_history_uncertified: Balance history is not available yet. Retry later."}
```

Over ConnectRPC the error is `unavailable` with the same message, a
`Retry-After` response header and the error detail
`ledger.read.v1.ErrorDetail` with `ERROR_CODE_UPSTREAM_ERROR`.

## Migration

None: the status stays 503 / Unavailable and is safe to retry. Balance, snapshot
and transfer reads that used to fail during a rebuild now succeed. A client that
waited for the whole API to recover before showing balances can show them at
once and retry only the history charts, after `Retry-After` seconds.
