## What and why

`TriggersService.ListTriggerEvents` now answers `NOT_FOUND` for a trigger the
caller cannot read: no trigger has the ID, it belongs to another account, or
it is outside the selected `subaccount_id`. This is the same answer
`GetTrigger` gives for that ID. Before, it answered an empty list, so a
mistyped or foreign trigger ID looked the same as a trigger with no history
yet. A trigger the caller can read that has no event yet still answers an
empty list. The comment on `ListTriggerEvents` says so. No field, enum value
or method changed.

## How clients use it

The request is unchanged. Handle `NOT_FOUND` as for `GetTrigger`:

```bash
# Authenticate as for any private read (omitted here).
curl -sS https://<api-host>/triggers.v1.TriggersService/ListTriggerEvents \
  -H 'Content-Type: application/json' -d '{"triggerId": "<trigger-id>"}'
# A trigger the caller cannot read:
#   {"code": "not_found", "message": "NOT_FOUND"}
curl -sS 'https://<api-host>/v1/triggers/<base58-trigger-id>/events'
# A trigger the caller cannot read: HTTP 404 with the problem
# GET /v1/triggers/<base58-trigger-id> answers,
#   {"type": "https://polyester.dev/problems/not-found", "title": "Not Found",
#    "status": 404, "detail": "Not found.", "code": "NOT_FOUND"}
```

ConnectRPC JSON carries the trigger ID as the decimal string of its
`fixed64`; REST paths take the base58 public ID instead. Paging, filters and
ordering are unchanged.

## Migration

A client that listed the events of a trigger ID it cannot read and treated the
empty list as "no history" now gets `NOT_FOUND` (HTTP 404 on REST). Treat it
as `GetTrigger`'s not-found: the ID is wrong, or the trigger belongs to another
account or subaccount. Check the ID and the `subaccount_id` selector. Reading
the events of a trigger the caller can read is unchanged.
