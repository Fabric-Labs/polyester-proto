## What and why

**Availability:** `ai.v1.AssistantService` and the assistant-key methods of
`auth.v1.ApiKeyService` (`SetAssistantKeys`, `ListAssistantKeys` and `DeleteAssistantKeys`, with
their REST paths under `/v1/auth/assistant-keys`) are devnet only. Not available on testnet yet;
they aren't deployed or routed there. Elsewhere the assistant-key methods answer `Unimplemented`
over ConnectRPC and 404 over REST. The rest of `auth.v1.ApiKeyService` is unchanged and available
everywhere.

The assistant acts on a user's accounts only through assistant keys: one API key per account the
user enables, bounded by that account's API policy, which never allows moving funds out. The
assistant generates each key pair and keeps the private key; the user registers the public keys
with `auth.v1.ApiKeyService/SetAssistantKeys` and one fresh step-up proof. The step-up proof goes
to `SetAssistantKeys` only, never to the assistant.

Each key the assistant generates comes with a registration proof and deadline, and
`SetAssistantKeys` registers a new assistant key only with them, before the deadline. So a key the
assistant no longer holds can never be registered later, not even by replaying an old request.

`ai.v1.AssistantService` gains three methods for that setup:

- `PrepareAssistantKeys`: the assistant generates one key pair per account and returns the public
  keys, each with its `registration_proof` and `registration_deadline`, a `setup_id` and
  `expires_at` (the deadline).
- `CompleteAssistantKeys`: once `SetAssistantKeys` registered them, the assistant starts using the
  keys and drops the ones the new set replaced or left out.
- `ListAssistantKeys`: the keys the assistant holds and uses, at most one per account.

New messages: `AssistantKey`, `AssistantKeyAccount`, `PreparedAssistantKey` and the requests and
responses. New enum `AssistantKeyState` (`ACTIVE`, `DISABLED`). New `ErrorCode` values
`KEY_SETUP_NOT_FOUND` and `KEY_SETUP_NOT_REGISTERED`.

`auth.v1.AssistantKeySpec` gains `registration_deadline` (Timestamp) and `registration_proof`
(bytes, 64). New `AuthErrorCode` values: `AUTH_ASSISTANT_KEY_PROOF_INVALID` (400 / INVALID_ARGUMENT:
the proof is missing or does not verify), `AUTH_ASSISTANT_KEY_REGISTRATION_EXPIRED` (412 /
FAILED_PRECONDITION: the deadline has passed) and `AUTH_ASSISTANT_KEY_DEADLINE_TOO_FAR` (400 /
INVALID_ARGUMENT: more than 15 minutes ahead).

## How clients use it

ConnectRPC, JSON over POST, session token only. `fixed64` IDs are decimal strings in JSON and
`bytes` are base64.

```bash
# 1. Run the step-up first, then prepare keys for the main account and one subaccount.
curl -sS https://<api-host>/ai.v1.AssistantService/PrepareAssistantKeys \
  -H 'Authorization: Bearer <session-token>' -H 'Content-Type: application/json' \
  -d '{"accounts": [{}, {"subaccountId": "9000000001"}]}'
# {"setupId": "5129847726104538861",
#  "keys": [{"publicKeyEd25519": "q8Ff...=", "registrationProof": "3kq...==",
#            "registrationDeadline": "2026-11-09T10:05:00.123Z"},
#           {"subaccountId": "9000000001", "publicKeyEd25519": "Zr1c...=", "registrationProof": "Ylb...==",
#            "registrationDeadline": "2026-11-09T10:05:00.123Z"}],
#  "expiresAt": "2026-11-09T10:05:00.123Z"}

# 2. Register them, each with its proof and deadline unchanged, a policy per account and the
#    step-up proof, before the deadline.
curl -sS -X PUT https://<api-host>/v1/auth/assistant-keys \
  -H 'Authorization: Bearer <session-token>' -H 'X-Auth-Step-Up: <step-up-token>' \
  -H 'Content-Type: application/json' \
  -d '{"keys": [{"publicKeyEd25519": "q8Ff...=", "policyId": "7001",
                 "registrationProof": "3kq...==", "registrationDeadline": "2026-11-09T10:05:00.123Z"},
                {"subaccountId": "9000000001", "publicKeyEd25519": "Zr1c...=", "policyId": "7001",
                 "registrationProof": "Ylb...==", "registrationDeadline": "2026-11-09T10:05:00.123Z"}]}'

# 3. Complete the setup.
curl -sS https://<api-host>/ai.v1.AssistantService/CompleteAssistantKeys \
  -H 'Authorization: Bearer <session-token>' -H 'Content-Type: application/json' \
  -d '{"setupId": "5129847726104538861"}'
# {"keys": [{"keyId": "ak_...", "publicKeyEd25519": "q8Ff...=", "state": "ACTIVE"},
#           {"subaccountId": "9000000001", "keyId": "ak_...", "publicKeyEd25519": "Zr1c...=", "state": "ACTIVE"}]}
```

- `PrepareAssistantKeys` takes 1 to 64 accounts, each at most once; an omitted `subaccount_id`
  is the main account. Keys come back in request order.
- Register each setup before `expires_at` (a few minutes): `SetAssistantKeys` refuses a new key
  past its deadline with `AUTH_ASSISTANT_KEY_REGISTRATION_EXPIRED`; prepare again. Run the step-up
  first, then prepare, so the deadline is not spent on the step-up.
- In `SetAssistantKeys`, an entry whose account already holds that public key needs no proof:
  changing only the policies keeps working without preparing again.
- `CompleteAssistantKeys` before the registration succeeded is `FAILED_PRECONDITION` with
  `KEY_SETUP_NOT_REGISTERED`, and changes nothing; repeat it after the registration. An unknown,
  expired or replaced setup is `NOT_FOUND` with `KEY_SETUP_NOT_FOUND`. Completing a completed setup
  returns the keys again.
- Too many setups pending is `RESOURCE_EXHAUSTED` with `USAGE_LIMIT_REACHED`.
- To turn the assistant's access off, call `auth.v1.ApiKeyService/DeleteAssistantKeys`. There is
  no assistant method for it; the assistant stops using revoked keys.
- `ListAssistantKeys` lists keys oldest first.

## Migration

`SetAssistantKeys` callers must send each new key's `registration_proof` and
`registration_deadline`, as `PrepareAssistantKeys` returns them; without them a new key is refused
with `AUTH_ASSISTANT_KEY_PROOF_INVALID`. Only keys the assistant generated carry them, so assistant
keys are set up through `PrepareAssistantKeys`. Entries that keep an account's current public key
need nothing new. The assistant methods are new.
