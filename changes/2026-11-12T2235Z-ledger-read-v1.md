## What and why

Account statements can now be downloaded over REST: `GET /v1/statements`
returns the same statement page as the ConnectRPC
`ledger.read.v1.LedgerReadService/ExportStatement`, as a `text/csv` body that
can be saved directly as a file. The rows, columns, paging and permissions are
the same on both transports.

## How clients use it

```http
GET /v1/statements?startTime=2026-10-01T00:00:00Z&endTime=2026-11-01T00:00:00Z
```

```http
HTTP/1.1 200 OK
Content-Type: text/csv; charset=utf-8
Content-Disposition: attachment; filename="statement.csv"
Next-Page-Token: <opaque token>

time,entry_id,type,account,asset,amount,fee,balance,link_id
2026-10-03T08:12:45.123456Z,27419385013475392811,trade,trading,BTC,0.1,0,1.1,77
2026-10-03T08:12:45.123456Z,27419385013475392811,trade,trading,USDT,-5000,2.5,4997.5,77
```

- `startTime` (inclusive) and `endTime` (exclusive) are required RFC 3339
  times, at most 366 days apart. `subaccountId` (base58) and `assetId` are
  optional, as on `/v1/transfers`.
- Each response is one page: at most 2000 ledger movements, entries never
  split, and the header row only on the first page. When more rows follow,
  the `Next-Page-Token` response header carries the cursor: repeat the
  request with the same parameters and `pageToken` set to it, and append the
  body, until the header is absent.
- A page token works on both transports for the same request.
- Session tokens and signed API keys are accepted; API keys need the
  `READ_STATEMENTS` policy action. Errors are `application/problem+json` with
  the same codes as the other ledger REST routes.

## Migration

None: the REST route is new.
