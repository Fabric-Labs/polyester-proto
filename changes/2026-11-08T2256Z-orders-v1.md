## What and why

On the private WebSocket's orders channel, the first revision of an order
that a trigger placed now carries the order's `origin`. That covers a fired
stop-loss, take-profit or trailing stop, an attached leg's exit, a TWAP
slice and a ladder level. Before, that first revision (status `PENDING`,
`version` 0) showed `origin.scope` `DIRECT`, and only later revisions named
the trigger. Every revision of the order now carries the same `origin` as
`GetOrder` and the order history: `STANDALONE_TRIGGER` or `ATTACHED_RISK`,
`triggerId`, `triggerType`, `childSeq` and, for an attached leg's exit,
`parentOrderId`. A client can classify an order the first time it sees it.

Orders a client placed directly still show `DIRECT` on every revision. No
message, field or enum changes, and the open-orders read of a `PENDING`
order shows the same origin.

## How clients use it

Read `origin` from any revision of the orders channel, the first included.
For example, a fired stop-loss's child in its first unit on the
`polyester.v1.json` subprotocol, which sends canonical protobuf JSON: enum
values by name, 64-bit IDs as decimal strings, and zero values such as
`version` 0 omitted (other `Order` fields are left out here):

```json
{
  "sub": "s1",
  "seq": "7",
  "unit": {
    "prevCursor": "<cursor>",
    "nextCursor": "<cursor>",
    "orders": [
      {
        "orderId": "357381960957428068",
        "status": "PENDING",
        "origin": {
          "scope": "STANDALONE_TRIGGER",
          "triggerType": "STOP_LOSS",
          "triggerId": "357381960957428067",
          "childSeq": 1
        }
      }
    ]
  }
}
```

`POST https://<api-host>/orders.v1.OrdersReadService/GetOrder` returns the
same `origin` for the order at every version.

## Migration

None: the fields and their meaning are unchanged. A client that waited for
a later revision before classifying an order, or that re-labelled an order
when its origin changed, can classify it on its first revision.
