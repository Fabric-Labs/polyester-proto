## What and why

An order or trigger refused because the account does not have enough
available balance now answers the ConnectRPC code `failed_precondition`
instead of `invalid_argument`. The request itself is valid; the account's
balance refuses it. Withdrawals and internal transfers already answer
`failed_precondition` for the same refusal, so one refusal now has one code
across the API.

The error code stays `ERROR_CODE_INSUFFICIENT_FUNDS` (REST problem `code`
`INSUFFICIENT_FUNDS`), and the HTTP status stays 400 over both REST and
ConnectRPC. No message, field or enum value changed.

## How clients use it

Every write refused for funds answers the same way: create, modify, batch
create, batch replace, and trigger creates.

```http
POST /orders.v1.OrdersService/CreateOrder
HTTP/1.1 400 Bad Request

{"code":"failed_precondition","message":"...","details":[{"type":"orders.v1.ErrorDetail","value":"..."}]}
```

```http
POST /v1/orders
HTTP/1.1 400 Bad Request

{"code":"INSUFFICIENT_FUNDS", ...}
```

## Migration

1. Where a ConnectRPC client detects insufficient funds by matching
   `invalid_argument`, match `failed_precondition` instead, or, better, read
   `ERROR_CODE_INSUFFICIENT_FUNDS` from the `orders.v1.ErrorDetail`.
2. Treat `failed_precondition` as "do not retry unchanged": add funds or
   reduce the order first.

REST clients that branch on the HTTP status or the problem `code` need no
change.
