## What and why

`system.v1.SystemService.GetTime` (REST `GET /v1/time`) returns the server
time in milliseconds since the Unix epoch, `server_time_ms` (`serverTimeMs`
in JSON). It is public, needs no authentication, and is never cached. It is
the clock that checks the `X-API-TIMESTAMP` of requests signed with an API
key, so clients can measure their clock's offset before they sign.

A request signed with an API key is accepted only while its timestamp is at
most 1000 ms ahead of the server time and at most its receive window behind
it: the `X-API-RECV-WINDOW` header, from 1 to 60000 ms, or 5000 ms when the
header is omitted. Otherwise it is refused unprocessed with
`AUTH_TIMESTAMP_SKEW` (REST problem code `TIMESTAMP_SKEW`, HTTP 401). That
refusal now carries the server time and the window too, so a client can
resync from the refusal alone:

- ConnectRPC: the new `auth.v1.AuthErrorDetail.timestamp_window`, a new
  `auth.v1.TimestampWindow` message with `server_time_ms`, `recv_window_ms`
  and `max_future_ms`. It is set for `AUTH_TIMESTAMP_SKEW` only.
- REST: the problem's new `timestampWindow` member with `serverTimeMs` (a
  decimal string), `recvWindowMs` and `maxFutureMs`. Present for
  `TIMESTAMP_SKEW` only.

Both apply to signed REST and ConnectRPC requests. A signed WebSocket login
refused for its timestamp gets the REST problem, with `timestampWindow`.

The receive window is now checked before the timestamp: a request with both
an invalid `X-API-RECV-WINDOW` and a malformed timestamp is refused
`AUTH_RECV_WINDOW_INVALID` (`RECV_WINDOW_INVALID`) rather than
`AUTH_TIMESTAMP_SKEW`.

## How clients use it

```bash
curl https://<api-host>/v1/time
# {"serverTimeMs":"1763337600000"}

curl -X POST https://<api-host>/system.v1.SystemService/GetTime \
  -H 'Content-Type: application/json' -d '{}'
# {"serverTimeMs":"1763337600000"}
```

Estimate the offset as `serverTimeMs - (sent + received) / 2`, with `sent`
and `received` the local times around the call, and sign with the local time
plus that offset. A refused signed request reads the same from its error:

```json
{
  "type": "https://polyester.dev/problems/timestamp-skew",
  "title": "API Key Timestamp Skew",
  "status": 401,
  "detail": "API key timestamp is outside the request's receive window",
  "code": "TIMESTAMP_SKEW",
  "timestampWindow": {"serverTimeMs": "1763337600000", "recvWindowMs": 5000, "maxFutureMs": 1000}
}
```

## Migration

None: the RPC, the message and the fields are new. A client that ignores
unknown fields and problem members behaves as before.
