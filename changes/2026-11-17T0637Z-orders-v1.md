## What and why

No field, message or enum value changes, and existing clients still encode and
decode every message. This is a breaking behavior change: clients that follow
the earlier retry advice, or treat only `ERROR_CODE_ORDER_ALREADY_TERMINAL` as
"already ended", must change (see Migration). It applies to `CancelOrder`,
`ModifyOrder`, `BatchCancelOrders` and `BatchReplaceOrders`.

1. A cancel or modify naming an order ID the exchange never placed now returns
   `ERROR_CODE_ORDER_UNKNOWN`. Some such IDs used to return
   `ERROR_CODE_ORDER_ALREADY_TERMINAL`, which told a client to treat an order
   that never existed as done.
2. An order that has ended is now reported as follows:
   - **By client order ID:** `ERROR_CODE_ORDER_ALREADY_TERMINAL` for at least
     a minute after the order ends, as before. Later the client order ID may
     name no order, and the request returns `ERROR_CODE_ORDER_UNKNOWN`.
   - **By order ID:** `ERROR_CODE_ORDER_ALREADY_TERMINAL` while the exchange
     can still confirm that it placed an order under that ID. After some
     exchange maintenance, such as a market listing or a recovery, an order
     that ended before it can no longer be confirmed. A cancel or modify of
     it by order ID then returns `ERROR_CODE_ORDER_UNKNOWN`, as an order ID
     that was never placed does. Before this change, every ended order
     returned `ERROR_CODE_ORDER_ALREADY_TERMINAL` by order ID.
3. The two codes map to different errors: `ERROR_CODE_ORDER_ALREADY_TERMINAL`
   is ConnectRPC `failed_precondition` (REST HTTP 400), and
   `ERROR_CODE_ORDER_UNKNOWN` is ConnectRPC `not_found` (REST HTTP 404). So
   for an ended order, the same request can now surface as a not-found error
   where it used to surface as a precondition error.

`ERROR_CODE_ORDER_UNKNOWN` therefore no longer proves that an order never
existed. The earlier advice to retry a cancel by order ID to tell an ended
order from an unknown one is withdrawn: a retry by order ID can itself return
`ERROR_CODE_ORDER_UNKNOWN` for an ended order.

## How clients use it

When a cancel or modify of an order returns `ERROR_CODE_ORDER_UNKNOWN`:

- If the client already knows the order ended (it saw the order's final
  update, or this is a retry of a cancel that timed out), treat the cancel as
  done. Nothing of the order is open: an open order is never reported unknown
  under its own order ID and market.
- Otherwise, retry by client order ID while it is within its window (at
  least a minute after the order ends), or read the order. A retry by client
  order ID returns `ERROR_CODE_ORDER_ALREADY_TERMINAL` for an ended order
  within that window. Reading the order is definitive at any time:

```text
POST /orders.v1.OrdersReadService/GetOrder
{"orderId": "<the order ID>", "includeExecutionHistory": false}

GET /v1/spot/orders/{order_id}
```

An order found with an ended status (filled, canceled, expired or rejected)
has ended, and nothing is left to cancel or modify. The cancel and modify
calls themselves are unchanged:

```text
POST /orders.v1.OrdersService/CancelOrder
{"orderId": "<the order ID>"}

POST /v1/orders/cancel
```

## Migration

1. Anywhere a client treats `ERROR_CODE_ORDER_ALREADY_TERMINAL` from a cancel
   or modify as "already done", also treat `ERROR_CODE_ORDER_UNKNOWN` as done
   for an order it placed and knows ended, or confirm by reading the order.
2. Anywhere a client treats `ERROR_CODE_ORDER_UNKNOWN` from a cancel or modify
   as "order lost" (an alarm, a resubmission), first read the order. It may
   simply have ended.
3. Drop any logic that retries a cancel by order ID to tell an ended order
   from an unknown one. Retry by client order ID within its window, or read
   the order.
