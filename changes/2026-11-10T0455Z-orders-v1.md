## What and why

SBE trading WebSocket clients can bound when an order request is submitted.
Schema 7 stays at version 36 and advances to semantic version 1.2.0. Six new
templates add request timing to the existing order commands; their command
types and acknowledgement templates stay the same. REST, ConnectRPC and
protobuf trading WebSocket formats do not change.

## How clients use it

Send a timed template on `/ws/trade.sbe` with the same order fields as its
untimed counterpart, plus the following fixed-block suffix before variable
data or repeating groups:

```text
CreateOrderTimed          template 11
CancelOrderTimed          template 12
ModifyOrderTimed          template 13
BatchCreateOrdersTimed    template 14
BatchReplaceOrdersTimed   template 15
BatchCancelOrdersTimed    template 16

timestampMs:  int64, Unix milliseconds; zero means unset
recvWindowMs: uint32, milliseconds; zero means default

Example: timestampMs = current Unix milliseconds, recvWindowMs = 2500
```

A timestamp with a zero receive window uses 5000 ms. An explicit window must
be from 1 to 60000 ms and requires a timestamp. A timestamp may be at most
1000 ms ahead of the server clock. With both fields zero, no per-request
window applies. The last accepted millisecond is `timestampMs + recvWindowMs`
(using the default when the window is zero). One timing pair covers the
whole batch; individual items carry no timing fields.

Expiry returns one `CommandReject` with `REQUEST_DEADLINE_EXCEEDED` (308):
nothing in the request was submitted. This rejection consumes the request's
sequence and leaves the connection usable. Malformed timing returns
`BAD_REQUEST` and consumes no sequence. Once submitted, a request may apply
even if its window ends before its acknowledgement arrives; retain the
existing outcome-unknown handling.

## Migration

None for existing untimed clients: their templates, block lengths and schema
version are unchanged. Regenerate from the semantic-version-1.2.0 XML to use
the new timed templates and recognize rejection 308. Refresh timing on a
retry without changing the order payload or batch correlation ID; timing is
excluded from batch retry identity. A receive window is separate from GTD
order expiry and does not bound an order's lifetime.
