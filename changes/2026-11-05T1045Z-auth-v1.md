## What and why

A `/v1/auth/*` REST request whose body is over the size limit now returns the
same HTTP 413 problem as every other REST service. A body-size limit is a
transport error rather than an account error, so clients need one rule for
oversized bodies on every service. The problem code changes from
`AUTH_REQUEST_TOO_LARGE` to `REQUEST_TOO_LARGE`, its type from
`https://polyester.dev/problems/auth-request-too-large` to
`https://polyester.dev/problems/request-too-large`, its title from
`Request Too Large` to `Request Entity Too Large`, and its detail from
`request body too large` to `request too large`. The 128 KiB limit and when it
is enforced do not change. No protobuf message or RPC changes.

## How clients use it

For example, `POST https://<api-host>/v1/auth/wallet-challenge` with more than
128 KiB of body data returns:

```http
HTTP/1.1 413 Request Entity Too Large
Content-Type: application/problem+json
X-Content-Type-Options: nosniff

{"type":"https://polyester.dev/problems/request-too-large","title":"Request Entity Too Large","status":413,"detail":"request too large","code":"REQUEST_TOO_LARGE"}
```

This holds for known-length and chunked bodies, on public routes and on
routes called with a session token or an API-key signature. An API-key-signed
request previously received a plain-text 413 body. The same oversized message
sent over ConnectRPC, public or with a session token, for example to
`/auth.v1.AuthService/CreateWalletChallenge`, still fails with
`resource_exhausted`, whether it is over the limit on the wire or only once
decompressed.

## Migration

Clients that branch on `code: AUTH_REQUEST_TOO_LARGE` or on the
`auth-request-too-large` problem type for `/v1/auth/*` REST requests, or that
read a plain-text 413 body, must branch on `code: REQUEST_TOO_LARGE` instead.
Keep status-based HTTP 413 handling and reduce the body to fit the existing
limit before sending another request. ConnectRPC clients, protobuf encoding
and generated request and response types need no changes.
