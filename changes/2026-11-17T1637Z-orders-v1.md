## What and why

A REST request body that names the same member twice in one JSON object is
now refused with `400`, at any depth. Members whose names differ only in
letter case (`postOnly` and `PostOnly`) count as the same member. Before, the
last occurrence silently won, and a trailing `null` reset an optional field
to unset. A body such as
`{"limitGtc":{"price":"1","postOnly":true,"postOnly":null}}` was applied as a
taker-capable order, and `"maxAmount":"12","maxAmount":"1000000"` stored the
larger bound, while anything that read the first occurrence (a client's own
log, a proxy, an audit trail) saw the other value. Refusing the body removes
that ambiguity.

The REST routes of these services change:

The two internal-transfer routes also now refuse a member the request does
not define, with the same `400` `INVALID_REQUEST`, as every other REST body
above already did. Before, they ignored it.

A refused body has no effect: nothing is placed, changed, transferred or
claimed. ConnectRPC is unchanged; its JSON decoding already refused repeated
members.

## How clients use it

Send each member once per object. A body that repeats a member is refused
while the request body is decoded, before the request takes any effect. Checks
that run earlier, such as authentication, the body size limit or an
unparseable body, can still answer first, and a repeated member and an unknown
member in one body may be reported either way:

```text
POST /v1/orders
{"order":{"symbol":"BTC-USDT","side":"BUY","baseQty":"1",
 "limitGtc":{"price":"1","postOnly":true,"postOnly":null}}}

400 application/problem+json
{"code":"BAD_REQUEST","status":400,
 "detail":"duplicate JSON member \"order.limitGtc.postOnly\"", ...}
```

Orders and triggers name the repeated member in `detail` as a dotted path of
member names, without array indexes (`items.attachedRisk.stopLoss`). The
other routes answer `"detail":"invalid request body"`. The same member name in
different objects, including different elements of an array, is not a
repeat.

## Migration

1. Make sure your client serializes each member once per object. Standard
   JSON encoders do; hand-built bodies, string templates and merged objects
   may not.
2. Do not send the same name in two letter cases, for example `postOnly` and
   `PostOnly`.
3. To leave an optional field unset in a request, omit it. Do not send a
   value followed by `null`. Omitting a field leaves it unset in that request;
   it does not by itself clear state an earlier request stored.
4. For `POST /v1/trading/internal-transfers` and
   `/v1/trading/internal-transfers/batch`, send only the documented members.
