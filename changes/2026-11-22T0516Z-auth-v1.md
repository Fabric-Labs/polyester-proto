## What and why

Each account activity event now says who acted, which item they changed, and what changed. `ActivityEvent` is returned by `ListAccountActivity` and `ListSubaccountActivity`.

- **Who acted.** `actor` (`ActivityActor`) is always set, and its `kind` says which actor it is:
  - `USER` is a signed-in account. `account_id` and `username` name it. For a sub-account member, that is the member's own account.
  - `API_KEY` is a request signed with an API key. It carries the account fields as for `USER`, plus `api_key_id`, `api_key_kind` (the new `ActivityApiKeyKind`: `STANDARD`, `ASSISTANT`, `ADMIN`, `STRATEGY_BOT` or `BROKER`) and `api_key_label`.
    - `api_key_id` is the `ak_…` ID that `ApiKey.key_id` shows, or a QuickSwap broker key's `key_id`. A broker key acts for the broker's account.
    - The kind and label are the key's at the time of the event.
  - `SYSTEM` means Polyester made the change by itself. `system_reason` says why, for example `ASSISTANT_PRESET_UPDATED`. A system event's `source` is the new `ACTIVITY_SOURCE_SYSTEM`, and it has no IP address or user agent.
  - `UNAUTHENTICATED` is a request nobody authenticated, such as a refused sign-in on the account. It names no account. The event's `ip`, `user_agent` and `source` say where the attempt came from.
- **A QuickSwap broker allowlist change being reconciled** is an `UPDATED` event with the system reason `BROKER_ALLOWLIST_CHANGE_RECONCILING`, while the broker API shows the change as pending. A later `APPLIED` or `FAILED` event with `BROKER_ALLOWLIST_CHANGE_SETTLED` records how it ended.
- **Which item.** `item` (`ActivityItem`) names the item. Exactly one ID field of its `id` oneof is set, and that field says what the item is:
  - `account_id`, `subaccount_id`, `invite_id`, `subaccount_policy_id`, `api_policy_id`, `address_book_entry_id`, `broker_allowlist_change_id` or `connected_app_id` (opaque IDs);
  - `api_key_id` or `mfa_factor_id` (the string IDs those APIs use).

  `name` is the item's display name when the event was recorded: a policy name, a key or address-book label, a sub-account label, a member's username, an MFA factor label, a connected app's name, or a session's device. A sign-in, a failed sign-in and the recovery codes have a name but no ID.
- **What changed.** `details` (`ActivityDetails`) is a oneof with one message per kind of item: account, session, API key, policy, sub-account, member, invitation, address-book destination, QuickSwap broker allowlist change, and security. Each change is a typed `{from, to}` pair, and only the fields the event changed are set. Policy actions are listed as the `PolicyAction` values added and removed. An address-book note is reported only as changed, never with its text.
- **Removed:** `ActivityEvent.payload_json` (free-form JSON), `actor_account_id` and `actor_api_key_id`.
- **Changed:** `ListAccountActivityRequest.api_key_id` is now the API key's `ak_…` string ID instead of an opaque number. `sources` and the REST `sources` parameter accept `SYSTEM`.

This is a deliberate breaking change before v1. The old fields could not say who acted (an automatic change showed an empty actor) or which item changed, and they exposed raw permission bitmasks.

## How clients use it

```http
POST /auth.v1.AccountActivityService/ListAccountActivity
{"includeMainAccount": true, "limit": 20}
```

```http
GET /v1/auth/activity?includeMainAccount=true&limit=20
GET /v1/auth/subaccounts/{subaccountId}/events?limit=20
```

One event, in REST JSON:

```json
{
  "createdAt": "2026-11-22T05:16:00Z",
  "entityKind": "POLICY",
  "eventAction": "UPDATED",
  "source": "SYSTEM",
  "actor": {"kind": "SYSTEM", "systemReason": "ASSISTANT_PRESET_UPDATED"},
  "item": {"apiPolicyId": "4Gw2Lq8vRd1", "name": "Polyester AI - Read only (main account)"},
  "details": {"policy": {"actions": {"added": ["READ_FUNDING_FLOWS"]}, "assistantPreset": "READ_ONLY"}}
}
```

Paging, ordering (newest first), limits and filters are unchanged, apart from `api_key_id`, which now takes a string.

Page tokens issued before this change:

- **`ListAccountActivity`:** a token of a request without `api_key_id` keeps working. A token of a request filtered by `api_key_id` fails with `INVALID_ARGUMENT`, because the filter's value changes; start again from the first page.
- **`ListSubaccountActivity`:** every token changes format and fails with `INVALID_ARGUMENT`; start again from the first page.

## Migration

1. Read `actor` instead of `actor_account_id` and `actor_api_key_id`. Show "System" for `ACTIVITY_ACTOR_SYSTEM`, with its `system_reason`, and an unauthenticated attempt for `ACTIVITY_ACTOR_UNAUTHENTICATED`.
2. Read `item` and `details` instead of parsing `payload_json`.
3. Pass the API key's `ak_…` ID (`ApiKey.key_id`) as `ListAccountActivityRequest.api_key_id`.
4. Discard `ListSubaccountActivity` page tokens issued before this change, and `ListAccountActivity` tokens of requests filtered by `api_key_id`.
