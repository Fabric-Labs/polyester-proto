## What and why

A batch item's own result now names the item's own fields, without the
item's index, on every transport. A `FieldViolation.field_path` is relative
to the message its error answers: a per-item result answers its item alone.
Two results change: a BatchReplaceOrders item's error, and, over REST only, a
BatchCreateOrders item's rejection.

Before, a rejected replace item's `BatchReplaceAdmissionItem.error` named its
fields in the whole request, index included. Now:

| Item refusal | Before | Now |
| --- | --- | --- |
| Attached leg refused | `items[0].new_attached_risk.stop_loss` | `new_attached_risk.stop_loss` |
| Attached-risk price off the tick (ConnectRPC and REST) | `items[1].new_attached_risk.take_profit.trigger_price_ticks` | `new_attached_risk.take_profit.trigger_price_ticks` |
| New price off the tick (ConnectRPC and REST) | `items[1].new_price_ticks` | `new_price_ticks` |
| New quantity off the step (ConnectRPC and REST) | `items[1].new_qty_scaled` | `new_qty_scaled` |
| Order ID that does not decode for the account | `items[1].order_id` | `order_id` |

An order ID that decodes for the account but names no order is rejected
`ORDER_UNKNOWN` with no violation, as before.

The item is the result's `item_index`. REST names the same fields by the
REST item's field names, also without the index: `newAttachedRisk.stopLoss`,
`newAttachedRisk.takeProfit.triggerPrice`, `newPrice`, `newQtyScaled`,
`orderId`. The protobuf WebSocket's batch replace answer uses the same
canonical field names as ConnectRPC for the violations it carries. Over
the WebSocket the order service alone decides whether an item is
refused. For a price off the tick or a quantity off the step, the
WebSocket names the field only when it is the only field of the item the
refusal can be: a replace's `new_price_ticks` (with no
attached price in the item) or `new_qty_scaled`, and in a batch create a
limit order's `order.limit_gtc.price_ticks` (with no attached price) or a
base-sized order's `order.base_qty_scaled`. Otherwise it gives the order
service's own detail: an attached leg's refusal names the leg
(`new_attached_risk.take_profit`), and any other refusal carries the code
with no field violation. That can be coarser than ConnectRPC's answer for
the same item. Read the code, not the violation, to decide what to
change.

Over ConnectRPC, a BatchCreateOrders item's rejection (`BatchCreateRejected`)
already named the item's fields under `order`, as a CreateOrderRequest
carrying the item would; that is unchanged. Over REST it named them under the
item's index; it now names them as a REST create carrying the item would,
under `order`, matching ConnectRPC:

| REST create item rejection | Before | Now |
| --- | --- | --- |
| Attached leg refused | `items[0].attachedRisk.stopLoss` | `order.attachedRisk.stopLoss` |
| Price off the tick | `items[1].limitGtc.price` | `order.limitGtc.price` |
| Quantity off the step | `items[0].baseQty` | `order.baseQty` |
| Iceberg display off the step | `items[0].limitGtc.displayQty` | `order.limitGtc.displayQty` |

The item is the result's position in `results`.

A request refused as a whole is unchanged: its error still names the field
under the item's index, for example
`items[1].new_attached_risk.trailing_stop.limit_price_ticks` for an attached
risk whose shape is invalid. Error codes, rule IDs, messages, and which items
are rejected are unchanged; only the paths of item results change.

## How clients use it

Read a rejected replace item's violations against the request item at the
result's `item_index`:

```http
POST /orders.v1.OrdersService/BatchReplaceOrders
{"requestId":"r1","symbolId":1,"items":[
  {"clientOrderId":"a","newPriceTicks":"70000000000000"},
  {"clientOrderId":"b","newPriceTicks":"70000001000000"}]}
```

The second item is rejected alone:

```json
{"itemIndex":1,"status":"BATCH_REPLACE_ITEM_ADMISSION_STATUS_REJECTED",
 "code":"PRICE_TICK_SIZE",
 "error":{"code":"ERROR_CODE_PRICE_TICK_SIZE",
          "violations":[{"fieldPath":"new_price_ticks","ruleId":"tick_size"}]}}
```

REST: `POST /v1/orders/replace-batch` answers the same item with
`"fieldPath":"newPrice"`. A REST batch create (`POST /v1/orders/batch`) item
priced off the tick is rejected with `"fieldPath":"order.limitGtc.price"`,
the field a REST create (`POST /v1/orders`) of that order names.

## Migration

A client that matched a replace item's violation against the whole request,
or parsed its `items[i]` prefix, now reads the path against the request item
at `item_index`: drop the `items[i].` prefix from any path it compares. A REST
client that read a batch create item's rejection under `items[i]` now reads
it under `order`, as for a REST create, against the item at the result's
position. Errors that refuse the whole request keep the `items[i]` prefix.
