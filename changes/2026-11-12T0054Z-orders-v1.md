## What and why

`batch_request_id`, the server-issued identity of a batch replace, is now an
opaque public ID derived with a server key. Before, a client that knew its
own `request_id` could relate the value to account data; now the value
carries no meaning outside the account that submitted the batch. No field,
type or method changes; only the values of `batch_request_id` do.

It is the same public value everywhere it appears:

- `orders.v1.OrdersService`: `BatchReplaceOrdersResponse.batch_request_id`,
  on ConnectRPC, REST and the trading WebSocket's batch replace
  acknowledgement.
- `orders.v1.OrdersReadService`: `Order.batch_request_id` of an order a batch
  replace admitted (also in the private WebSocket order updates), and
  `GetBatchReplaceStatus`, which takes it and answers it.

`GetBatchReplaceStatus` finds only a batch of the caller's account (or
selected sub-account). A `batch_request_id` that is not one of them answers
`not_found`, as for a batch the account never submitted.

## How clients use it

Pass the `batch_request_id` the batch replace answered back unchanged:

```bash
curl -sS https://<api-host>/orders.v1.OrdersReadService/GetBatchReplaceStatus \
  -H 'Content-Type: application/json' -d '{"batchRequestId": "<batch_request_id from BatchReplaceOrders>"}'
```

ConnectRPC JSON carries the decimal string of the `fixed64`; REST shows it in
base58, as every public ID. The status answers the same `batch_request_id`
it was asked for.

## Migration

This is a breaking change for clients that kept `batch_request_id` values.

1. A `batch_request_id` received before the change is answered `not_found`
   by `GetBatchReplaceStatus` after it. Reconcile those batches by their
   orders, as for a batch whose status window ended.
2. If you correlate `Order.batch_request_id` with a batch replace response,
   compare values received after the change only.
3. Do not derive anything from the value; compare it only with other
   `batch_request_id` values of the same account.
