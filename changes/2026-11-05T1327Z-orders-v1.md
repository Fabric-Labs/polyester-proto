## What and why

`GetBatchReplaceStatus` now answers from the venue's own record of the batch,
so an accepted batch can be read as soon as `BatchReplaceOrders` returns.
Before, a read issued right after acceptance could answer NOT_FOUND although
the replacement had succeeded.

The error meanings change, and the documentation now states them:

- A batch's status is retained for 60 seconds from its acceptance. That is the
  same time-limited window in which an identical `BatchReplaceOrders` retry
  replays its admission.
- UNAVAILABLE means the status cannot be established yet. It is retryable.
- NOT_FOUND means the account has no retained batch with this identity: none
  was accepted for it, or the window ended. It never proves that a replacement
  was rejected.
- Each item's execution phase advances asynchronously after acceptance.
- For an item refused after its admission, `updatedTsNs` is when the refusal
  was recorded, or a later time at which the service recovered and observed
  it. Two reads may show different times for the same refusal, so never use
  it to identify the refusal. The batch's `updatedTsNs` is the latest of its
  acceptance and its items' times.

No message, field, enum value or RPC changes.

## How clients use it

Read the batch with the `batchRequestId` that `BatchReplaceOrders` returned,
within 60 seconds of its acceptance:

```text
POST /orders.v1.OrdersReadService/GetBatchReplaceStatus
{"batchRequestId": "3456127831927370872"}
-> {"batchRequestId": "3456127831927370872", "admissionStatus": "BATCH_REPLACE_ADMISSION_STATUS_ADMITTED",
    "items": [{"itemIndex": 0, "actionTaken": "REPLACED", "phase": "BATCH_REPLACE_PHASE_WORKING", ...}], ...}
```

On UNAVAILABLE, retry the same request while the window lasts. On NOT_FOUND,
or once the window has ended, reconcile through the individual order reads
(`GetOrder` with the old and replacement order IDs). Never submit an accepted
batch again because its status is not found: a resubmission after the window
is admitted as a new batch.

## Migration

None required. Clients that treated an early NOT_FOUND as a transient miss can
drop that workaround. Clients that retried on NOT_FOUND should retry only on
UNAVAILABLE.
