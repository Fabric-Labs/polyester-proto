## What and why

`ProposeDeploy` and `GetDeployStatus` now record and read deploy proposals.
The contract is unchanged; comments now state the current behaviour:

- `ProposeDeploy` requires the version's behaviour examples to have passed
  (`RunScenarios`). A finished backtest will be required once backtests are
  available, so `BACKTEST_MISSING` is not returned yet.
- `INDICATOR_SETTINGS_LIMIT_REACHED` is not returned until the limit is
  enforced.
- A proposal expires 24 hours after it is recorded.

## How clients use it

```json
POST /strategies.v1.StrategiesService/ProposeDeploy
{"versionId": "sha256:…", "botName": "Weekly DCA",
 "settings": [{"name": "budget", "value": "100"}],
 "funding": [{"asset": "USDT", "amount": "200"}],
 "idempotencyKey": "propose-7f3a"}

{"proposalId": "…", "deployUrl": "https://<app-host>/bots/deploy/<proposal-id>",
 "summary": {"versionId": "sha256:…", "botName": "Weekly DCA",
             "moneyCard": {…}, "settings": [{"name": "budget", "value": "100"},
             {"name": "threshold", "value": "75"}],
             "funding": [{"asset": "USDT", "amount": "200"}], "scenariosPassed": 2},
 "expiresAt": "…"}

POST /strategies.v1.StrategiesService/GetDeployStatus
{"proposalId": "…"}
```

- Run `RunScenarios` first: a version whose examples failed, or never ran,
  is `SCENARIOS_FAILING`.
- The summary lists every setting with its value, defaults filled in, in
  settings-form order.
- The same idempotency key and request return the same proposal; another
  request under that key is `IDEMPOTENCY_CONFLICT`.
- `INSUFFICIENT_FUNDS` lists the missing amounts. It is checked when the
  proposal is recorded, and again when it is deployed.
- `funding_subaccount_id` must name an active subaccount of the caller's
  main account. Any other, a disabled one included, is
  `FUNDING_SUBACCOUNT_NOT_FOUND`.
- `GetDeployStatus` answers `PROPOSED` until the proposal is deployed, or
  `EXPIRED` after 24 hours.

## Migration
