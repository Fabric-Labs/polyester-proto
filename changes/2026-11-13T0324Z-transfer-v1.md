## What and why

`transfer.v1.InternalTransferService` adds `BatchCreateInternalTransfers`: up
to 10 Trading to Trading transfers in one request, authorized by one MFA
check. Moving several assets, or moving funds from several of the caller's
accounts, no longer needs a fresh step-up per transfer.

New messages: `BatchCreateInternalTransfersRequest`,
`BatchCreateInternalTransfersResponse`, `InternalTransferBatchLeg` and
`InternalTransferBatchLegResult`; new enums `InternalTransferBatchStatus` and
`InternalTransferBatchLegStatus`.

## How clients use it

Each leg takes the fields of `CreateInternalTransfer` without the idempotency
key: an optional source `subaccount_id`, one destination, `asset_id` and
`amount_e18`. The batch carries one `idempotency_key`, scoped to the
authenticated caller (the session's account, or the API key).

```text
POST /transfer.v1.InternalTransferService/BatchCreateInternalTransfers
X-Auth-Step-Up: <fresh step-up token, when the batch needs one>
{
  "idempotencyKey": "rebalance-2026-11-13-1",
  "legs": [
    {"destinationSmartAccountAddress": "0x2222…", "assetId": 1, "amountE18": {"hi": "0", "lo": "500000000000000000"}},
    {"subaccountId": "<public id>", "destinationSmartAccountAddress": "0x2222…", "assetId": 3, "amountE18": {"hi": "0", "lo": "1000000000000000"}}
  ]
}
```

REST: `POST /v1/trading/internal-transfers/batch`, with `amount` as a decimal
string in whole asset units, as on `POST /v1/trading/internal-transfers`.

- Every leg passes the same checks as a single transfer before any leg runs.
  If one fails, the response has `status: BATCH_REFUSED`, the failed legs
  carry `LEG_REFUSED` with an `error_code`, the others `LEG_NOT_SUBMITTED`, and
  nothing moves: no funds and no step-up are used.
- Otherwise `status: BATCH_SUBMITTED` and legs run in order, independently.
  They are not atomic: a leg can be `LEG_REFUSED` (for example
  `ERROR_CODE_INSUFFICIENT_FUNDS`) after earlier legs were `LEG_ACCEPTED`.
  `LEG_PENDING` means the outcome is not known yet and completes without the
  caller; `LEG_NOT_SUBMITTED` in a submitted batch means the request ended
  before the leg started.
- MFA is judged once for the batch: recent MFA when the root owner moves funds
  between its own accounts or to explicitly whitelisted destinations, one
  fresh step-up otherwise. API keys need none.
- Retry with the same `idempotency_key` and the same legs: accepted legs
  answer the same transfers, a retry needs no new step-up, and legs not yet
  accepted run again. Different legs under the key answer
  `ERROR_CODE_IDEMPOTENCY_CONFLICT`.
- When the service cannot read whether a leg already ran (a storage outage
  during a retry), the batch answers `ERROR_CODE_SERVICE_UNAVAILABLE` with
  `Retry-After` instead of any leg status: retry with the same key. An
  accepted leg is never reported refused or not submitted.
- Each leg's `request_id` and `transfer_id` work with `GetInternalTransfer`.
- At most 10 legs: an 11-leg batch is refused with `INVALID_ARGUMENT`
  (`ERROR_CODE_INVALID_REQUEST`) naming the `legs` item count, before any rate
  limit or MFA check.
- Rate limits charge one unit per leg against the internal-transfer budget, as
  if each leg were sent on its own.

## Migration

None: the RPC is new and `CreateInternalTransfer` behaves as before.

The reference now marks fields required that the API already refused when
missing: `asset_id` and `idempotency_key` on `CreateInternalTransfer`, and
`idempotency_key` and each leg's `asset_id` on the batch (proto
`google.api.field_behavior = REQUIRED`; REST `assetId` and `idempotencyKey`
in the request schema's `required`). Requests that worked keep working.
