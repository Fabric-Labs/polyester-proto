## What and why

OrderIntent gains an optional StaticPeg with a BEST_BID or BEST_ASK reference
and signed offset_ticks. A limit order can select its price once at entry,
without first reading the book. The limit execution still requires price_ticks:
a BUY cap or SELL floor. A derived price beyond that bound is rejected.
The selected price remains fixed for the order's lifetime.

## How clients use it

Call `/orders.v1.OrdersService/CreateOrder` with the usual subaccount selection
and an order such as:

```json
{"order":{"symbolId":1,"side":"BUY","baseQtyScaled":"1000","limitGtc":{"priceTicks":"110000000000","postOnly":true},"peg":{"reference":"BEST_BID","offsetTicks":"0"}}}
```

REST `POST /v1/orders` uses the same peg inside its decimal order intent.
Offsets count configured price increments, signed and added to the reference;
they do not count occupied levels. GTC, GTD, IOC and FOK limit execution are
supported with base quantity only. Market execution, quote-budget sizing and
attached risk cannot carry a peg. Read orders or subscribe to order updates for
the selected price; the create acknowledgement confirms account admission.
An empty reference side rejects with PEG_REFERENCE_UNAVAILABLE, an exceeded
cap/floor with PEG_LIMIT_VIOLATION, and unsupported terms with INVALID_PEG.

## Migration

Existing protobuf order intents need no change: the fields and error codes are additive.
Binary Trade WebSocket clients must regenerate for schema version 47 and deploy
with the new contract. Existing CreateOrder and BatchCreateOrders fixed blocks
grow by the peg fields; older binary request frames are rejected.
