## What and why

Every refusal on the reward REST routes now answers `application/problem+json` with a stable `code`. Before, the routes mixed two shapes: refusals on `GET /v1/rewards/awards` and `PUT /v1/rewards/awards/{award_id}/destination`, and validation, body and server failures on `POST /v1/rewards/awards/{award_id}/acknowledge`, answered `text/plain`; only authentication refusals and the acknowledge route's domain refusals answered `application/problem+json`. A REST client can now branch on `code` for every refusal, and a reward `404` is distinguishable from a missing route.

HTTP statuses are unchanged. ConnectRPC responses are unchanged.

## How clients use it

The REST routes and their ConnectRPC equivalents. The list accepts a session token for the root account or a main-account API key with `READ_REWARDS`; the destination and acknowledge writes accept only a session token:

- `GET /v1/rewards/awards?limit=<n>&pageToken=<token>`, ConnectRPC `POST /rewards.v1.RewardCampaignService/ListMyRewardAwards`. `limit` defaults to 50, maximum 100; `pageToken` is the opaque `nextPageToken` of the previous page. Awards are newest first.
- `PUT /v1/rewards/awards/{award_id}/destination`, ConnectRPC `POST /rewards.v1.RewardCampaignService/SetMyRewardDestination`.
- `POST /v1/rewards/awards/{award_id}/acknowledge`, ConnectRPC `POST /rewards.v1.RewardCampaignService/AcknowledgeMyRewardAward`.

Read the problem body of any non-2xx REST response. For example, an unknown award:

```http
PUT /v1/rewards/awards/00000000-0000-0000-0000-000000000001/destination
Content-Type: application/json
Authorization: Bearer <session-token>

{"destinationAddress":"u1recipient","expectedRevision":"1","requestId":"request-1"}
```

```http
HTTP/1.1 404 Not Found
Content-Type: application/problem+json

{"code":"NOT_FOUND","detail":"reward campaign record not found","status":404,"title":"Not Found","type":"https://polyester.dev/problems/not-found"}
```

The body always carries `type`, `title`, `status`, `detail` and `code`. Codes by status:

- `400` `INVALID_ARGUMENT`: an invalid `limit` or page token, a malformed or unknown-field body, a body `awardId` that differs from the path, or a request that fails validation.
- `401` and `403`: the existing `AUTH_*` authentication, session-kind and API-key permission codes, unchanged. A session token without a session identifier answers `401` `UNAUTHENTICATED`.
- `404` `NOT_FOUND`: the award does not exist or belongs to another account. Both cases answer the same body.
- `412` `FAILED_PRECONDITION`: a stale `expectedRevision` on the destination route, or a delivery mark before payment on the acknowledge route.
- `500` `INTERNAL_ERROR`: any other failure, including a server timeout; retry with backoff.

`detail` is human-readable text for logs and support; branch on `code`, not on `detail`.

## Migration

REST clients of these three routes must change how they decode refusals. ConnectRPC clients need no change.

1. Old shape: a refusal that is not an authentication refusal answered `Content-Type: text/plain; charset=utf-8` with a one-line body such as `invalid limit`, `invalid request`, `Bad Request`, `Not Found` or `Precondition Failed`. New shape: `Content-Type: application/problem+json` with the JSON body above. Stop reading the body as text; parse it as JSON for every non-2xx status.
2. Branch on `code` (and `status`), never on the text. Where a client matched the old text, use: `invalid limit`, `invalid request` and `Bad Request` → `INVALID_ARGUMENT`; `Not Found` → `NOT_FOUND`; `Precondition Failed` → `FAILED_PRECONDITION`; `Internal Server Error` → `INTERNAL_ERROR`.
3. The acknowledge route's server failure changes `code` from `INTERNAL` to `INTERNAL_ERROR`. Replace any match on `INTERNAL` with `INTERNAL_ERROR`.
4. The acknowledge route's `404` and `412` keep their shape and `code`; their `detail` now carries the service's message (for example `reward campaign record not found`) instead of the HTTP status text.
