## What and why

Every order book surface now uses one depth vocabulary, the shared enum
`polyester.type.v1.DepthTier`: `DEPTH_1`, `DEPTH_5`, `DEPTH_10`, `DEPTH_20`,
`DEPTH_50`, `DEPTH_100`, `DEPTH_200`, `DEPTH_500`, `DEPTH_1000` and
`DEPTH_5000` levels per side.

- `GetOrderBookRequest.depth` is a `DepthTier` again. This reverts the
  integer depth that only devnet pre-releases carried. Every tier is served,
  including the new deepest one, 5000 levels per side. `DEPTH_UNSPECIFIED`
  selects `DEPTH_50`. A value that is no tier is refused with
  INVALID_ARGUMENT instead of being served at a depth nothing can stream.
- `GetOrderBookResponse.max_depth` is removed. The response now names the
  tier it served in `depth`.
- The heatmap's `HeatmapDepth` enum is replaced by `DepthTier`, with the same
  value numbers and names. The heatmap serves every tier except
  `DEPTH_5000`, which it refuses with INVALID_ARGUMENT.
- REST spells a tier one way on every order book surface, as its level count
  (`"20"`) in requests and responses, and refuses enum names such as
  `DEPTH_20`; ConnectRPC uses the enum names. The heatmap's REST endpoint
  follows this too: it now returns `"depth": "20"` instead of
  `"depth": "DEPTH_20"` and refuses `depth=DEPTH_20`.
- The order book stream publishes the tiers 1, 20, 50, 200 and 500, a subset
  of `DepthTier`. A subscription at any other depth is refused with error
  code 107 (bad request).

## How clients use it

ConnectRPC takes the enum value name; REST takes the tier's level count and
returns the served tier as a level count string.

```text
POST https://<api-host>/orderbook.v1.OrderbookService/GetOrderBook
{"symbolId": 1, "depth": "DEPTH_20"}
-> {"symbolId": 1, "bookSeq": "984321", "bookEpoch": "3", "depth": "DEPTH_20", "available": true, ...}

GET https://<api-host>/v1/orderbook/BTC-USDT?depth=20
-> {"symbol": "BTC-USDT", "bookSeq": "984321", "bookEpoch": "3", "depth": "20", ...}

POST https://<api-host>/marketdata.v1.HeatmapService/GetOrderbookHeatmap
{"symbolId": 1, "interval": "INTERVAL_1M", "depth": "DEPTH_200", "quantityMode": "PEAK", "limit": 100,
 "timeRange": {"startTime": "2026-11-17T00:00:00Z"}}

GET https://<api-host>/v1/spot/markets/BTC-USDT/heatmap?interval=1m&depth=200
-> {"depth": "200", "symbolId": 1, ...}
```

To follow a book in real time, subscribe to the order book stream at a
streamed tier (1, 20, 50, 200 or 500), then fetch `GetOrderBook` at exactly
that tier and stitch on `bookSeq`. The REST `depth` query parameter defaults
to 50 and accepts only 1, 5, 10, 20, 50, 100, 200, 500, 1000 or 5000.

## Migration

1. `GetOrderBook` on ConnectRPC: send `depth` as a `DepthTier`
   (`"DEPTH_20"` in JSON, the enum in generated code) instead of an integer.
   An integer depth that is no tier, for example 37, is now refused.
2. Read the served tier from the response's `depth`; `max_depth` is gone.
   The deepest tier is `DEPTH_5000`.
3. Heatmap clients: replace `HeatmapDepth` with `DepthTier`. Value names and
   numbers are unchanged, so encoded requests stay the same.
4. REST clients that already send a tier's level count, such as `depth=20`,
   need no change. Other counts are now refused with 400.
5. Heatmap REST clients: send `depth` as a level count (`depth=200`), not an
   enum name, and read the response's `depth` as a level count string
   (`"200"`).
