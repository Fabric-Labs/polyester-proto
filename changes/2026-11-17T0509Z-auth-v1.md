## What and why

The documentation of two `auth.v1.PolicyAction` values, `CONVERT_DUST` and
`READ_FUNDING_FLOWS`, called them account permissions. The `PolicyAction`
documentation defines account permissions as API-key-only actions that a
sub-account policy refuses, so the reference wrongly suggested that a
sub-account policy cannot carry them.

Both are product actions, and the reference now documents them as such. Like
every product action, they apply to both sub-account policies and API-key
policies. A sub-account policy accepts both, and every sub-account policy
always includes `READ_FUNDING_FLOWS`, because it belongs to the mandatory
read-only actions. Converting dust on a sub-account with an API key needs
`CONVERT_DUST` on the key's API-key policy and on the sub-account's policy.

Only the documentation changed. Enum names, numbers and the behavior of every
call stay the same.

## How clients use it

Grant `CONVERT_DUST` on a sub-account policy in the same way as any other
product action, for example when creating one with a session token. Over
ConnectRPC:

```bash
curl -sS https://<api-host>/auth.v1.PolicyService/CreateSubaccountPolicy \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer <session-token>' \
  -d '{"policy": {"name": "dust", "actions": ["READ_BALANCES", "CONVERT_DUST"]}}'
```

Over REST, use `POST /v1/auth/policies/subaccounts` with the same body.
Grant `CONVERT_DUST` on the API-key policy as well, through
`/auth.v1.PolicyService/CreateApiPolicy` (REST
`POST /v1/auth/policies/api-keys`) or `UpdateApiPolicy`.

## Migration

None. Only the documentation changed. A client that left `CONVERT_DUST` off
sub-account policies because of the earlier wording should add it to the
sub-account policies that need to convert dust.
