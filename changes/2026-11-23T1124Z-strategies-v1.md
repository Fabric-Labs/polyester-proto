## What and why

`DeployBot` is now served: it deploys a deploy proposal the user approved,
creating the bot's subaccount, setting the bot's limits and trading key, and
recording the bot's start. Before, it answered UNIMPLEMENTED.

Once the bot's limits are set, the exchange takes a moment to apply them, and
the bot must not start before they apply. A call therefore waits up to about
20 seconds for the exchange to apply the bot's limits, then answers
`SETTING_ACCESS`: call again to continue. The documentation of
`DeployBot`, `DeployBotResponse.status` and `DeployStatus.State.SETTING_ACCESS`
now says so. The messages and fields are unchanged.

## How clients use it

Call `DeployBot` with the user's recently MFA-elevated session, and call it
again with the same proposal while the status reads `SETTING_ACCESS`:

```http
POST /strategies.v1.StrategiesService/DeployBot
{"proposalId": "123456789"}
```

```json
{"status": {"proposalId": "123456789", "state": "SETTING_ACCESS"}}
```

A later call answers `DEPLOYING` once the bot's start is recorded, then
`LIVE`, or `FAILED` with `failedAt` and `failure`. Each call returns
within about 25 seconds. Calling again never starts a second bot.
`GetDeployStatus` reads the same status without continuing the deploy.

## Migration

None: no client could call `DeployBot` before. A deploy page should treat
`SETTING_ACCESS` as in progress and call `DeployBot` again, after a short
pause, until the state is `DEPLOYING`, `LIVE` or `FAILED`.
