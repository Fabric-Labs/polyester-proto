## What and why

An attached take-profit, stop-loss or trailing stop whose order self-trade
prevention expired against another of the account's resting orders no longer
fires again at every new trade or price update while that order blocks it.
Before, a leg watching the index price could send a new order at every index
update, each one expired against the same resting order. Now the leg waits
while the other order is first in line at the best price. Once that order is
gone (filled or canceled) or no longer first there, the leg fires again if its
trigger condition still holds. This holds whatever price the leg watches.

The comments on `EVENT_FIRE_REFUSED`, `TRIGGER_FAILURE_REASON_SELF_TRADE_PREVENTED`
(249) and `ERROR_CODE_SELF_TRADE_PREVENTED` (307) now describe this. No field,
enum value, status or event is added or removed.

## How clients use it

Nothing new to call. The trigger's history shows one `EVENT_FIRE_REFUSED` with
`TRIGGER_FAILURE_REASON_SELF_TRADE_PREVENTED` when the first order is expired,
as before, and now no further fired orders while the blocking order stays
first at the best price.

```bash
# Authenticate as for any private read (omitted here).
curl -sS https://<api-host>/triggers.v1.TriggersService/ListTriggerEvents \
  -H 'Content-Type: application/json' -d '{"triggerId": "<trigger-id>"}'
# While the user's own order blocks the leg:
#   one EVENT_FIRED (its order expired by self-trade prevention), then one
#   EVENT_FIRE_REFUSED with fireRefusalReason
#   "TRIGGER_FAILURE_REASON_SELF_TRADE_PREVENTED", and nothing more until
#   that order is gone or no longer first at the best price.
```

## Migration

None: the contract's shape is unchanged. A client that counted repeated
fired-and-expired orders as a sign of a blocked leg now sees a single one;
the `EVENT_FIRE_REFUSED` with the self-trade reason remains the signal.
