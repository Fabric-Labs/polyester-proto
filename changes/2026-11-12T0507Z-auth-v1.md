## What and why

Every REST endpoint now answers a request refused for its credentials with the
same problem body: the documented `code` and HTTP status, and one `title` and
one non-empty `detail` per code. Before, the same refusal could carry a
different title on each endpoint and, on some endpoints, an empty `detail`.
`MISSING_HEADERS`, for example, now reads "Missing API Key Headers" / "API key
timestamp and signature headers are required" on every endpoint, and
`SIGNATURE_INVALID` reads "Invalid API Key Signature" / "API key signature is
invalid".

Three REST surfaces answered some of these refusals with a code or status other
than the documented one. They now answer the documented one.

Account and security endpoints (`/v1/auth/...`):

| Refusal | Before | Now |
| --- | --- | --- |
| No credentials, or a missing, malformed or expired session token | `401 AUTH_AUTHENTICATION_REQUIRED` | `401 UNAUTHENTICATED` |
| API-key request without its timestamp or signature header | `401 AUTH_AUTHENTICATION_REQUIRED` | `401 MISSING_HEADERS` |
| Signature does not verify, the key is unknown, or the signed request was already used | `401 AUTH_AUTHENTICATION_REQUIRED` | `401 SIGNATURE_INVALID` |
| Timestamp outside the receive window | `401 AUTH_AUTHENTICATION_REQUIRED` | `401 TIMESTAMP_SKEW` |
| Invalid `X-API-RECV-WINDOW` | `401 AUTH_AUTHENTICATION_REQUIRED` | `401 RECV_WINDOW_INVALID` |
| Expired key | `401 AUTH_AUTHENTICATION_REQUIRED` | `401 KEY_EXPIRED` |
| Disabled or revoked key | `401 AUTH_AUTHENTICATION_REQUIRED` | `401 KEY_DISABLED` |
| Source IP not in the key's allowlist | `401 AUTH_AUTHENTICATION_REQUIRED` | `401 IP_NOT_ALLOWED` |
| Authentication temporarily unavailable | `401 AUTH_AUTHENTICATION_REQUIRED` | `503 AUTH_TEMPORARILY_UNAVAILABLE` |

Before, these endpoints put the reason in `detail`, for example
`"detail": "SIGNATURE_INVALID"`. The replay-capacity refusal already answered
`429 REPLAY_CAPACITY_EXHAUSTED` and keeps that code and status; only its title
changes.

Daily claim (`/v1/trading/daily-claim`, `/v1/trading/daily-claim/claim`) and
rewards (`/v1/rewards/awards...`), for a request that carries API-key headers:

| Refusal | Before | Now |
| --- | --- | --- |
| API-key headers together with a session token | `401 AUTH_AUTHENTICATION_REQUIRED` | `401 UNAUTHENTICATED` |
| Missing timestamp or signature header | `401 AUTH_MISSING_HEADERS` | `401 MISSING_HEADERS` |
| Signature does not verify, the key is unknown, or the signed request was already used | `401 AUTH_SIGNATURE_INVALID` | `401 SIGNATURE_INVALID` |
| Timestamp outside the receive window | `401 AUTH_TIMESTAMP_SKEW` | `401 TIMESTAMP_SKEW` |
| Invalid `X-API-RECV-WINDOW` | `401 AUTH_RECV_WINDOW_INVALID` | `401 RECV_WINDOW_INVALID` |
| Expired key | `401 AUTH_KEY_EXPIRED` | `401 KEY_EXPIRED` |
| Disabled or revoked key | `401 AUTH_KEY_DISABLED` | `401 KEY_DISABLED` |
| Source IP not in the key's allowlist | `401 AUTH_IP_NOT_ALLOWED` | `401 IP_NOT_ALLOWED` |
| Too many signed requests within their receive windows (daily claim) | `429 AUTH_REPLAY_CAPACITY_EXHAUSTED` | `429 REPLAY_CAPACITY_EXHAUSTED` |
| Too many signed requests within their receive windows (rewards) | `500 AUTH_REPLAY_CAPACITY_EXHAUSTED` | `429 REPLAY_CAPACITY_EXHAUSTED` |
| Authentication temporarily unavailable | `503 AUTH_TEMPORARILY_UNAVAILABLE` | `503 AUTH_TEMPORARILY_UNAVAILABLE` (unchanged) |

A rewards request without API-key headers and without valid session
credentials changes from `401 AUTH_AUTHENTICATION_REQUIRED` to
`401 UNAUTHENTICATED`. A daily-claim request without API-key headers already
answered `401 UNAUTHENTICATED`; only its `detail` changes.

A REST path the API does not serve, including a trailing slash and an unknown
ConnectRPC procedure, now answers `404 application/problem+json` with code
`NOT_FOUND`, instead of a plain-text 404 on some paths.

ConnectRPC codes and error details are unchanged. One ConnectRPC message
changes: the daily claim's `UNAUTHENTICATED` error (`claims.v1.ErrorDetail`)
reads "authentication required" instead of "unauthenticated", the same text
as its REST `detail`.

## How clients use it

A signed REST request without its signature header:

```http
GET /v1/trading/daily-claim
X-API-KEY-ID: ak_...
X-API-TIMESTAMP: 1762920000000
```

```json
{
  "type": "https://polyester.dev/problems/missing-headers",
  "title": "Missing API Key Headers",
  "status": 401,
  "detail": "API key timestamp and signature headers are required",
  "code": "MISSING_HEADERS"
}
```

An unknown procedure, such as `POST /orders.v1.OrdersService/NoSuchMethod`:

```json
{
  "type": "https://polyester.dev/problems/not-found",
  "title": "Not Found",
  "status": 404,
  "detail": "No API operation matches this method and path.",
  "code": "NOT_FOUND"
}
```

## Migration

1. On `/v1/auth/...`, replace a match on `AUTH_AUTHENTICATION_REQUIRED` with
   the codes in the first table: `UNAUTHENTICATED` for session credentials, and
   the API-key code of each refusal. Stop reading the refusal reason from
   `detail`.
2. On the daily claim and rewards endpoints, drop the `AUTH_` prefix from every
   API-key refusal code in the second table, and match `UNAUTHENTICATED` where
   you matched `AUTH_AUTHENTICATION_REQUIRED`.
3. Treat `503 AUTH_TEMPORARILY_UNAVAILABLE` from `/v1/auth/...` as retryable
   with backoff, and `429 REPLAY_CAPACITY_EXHAUSTED` from rewards as retryable
   after a short wait, as on every other endpoint.
4. If you compared the daily claim's ConnectRPC `UNAUTHENTICATED` message text,
   expect "authentication required". Keep branching on codes, not on `title`,
   `detail` or message text.
