## What and why

Three changes make a refused order modify visible in one place and keep it out
of order history.

1. **Batch status shows refusals after admission.** `BatchReplaceOrders` is
   answered at admission, so an item can be admitted and then refused when
   applied. Examples: a post-only order moved to a price that would cross, or
   a new price the book has no room for. `GetBatchReplaceStatus` now reports
   such an item as `BATCH_REPLACE_PHASE_REJECTED` with the refusal's code.
   Before, it stayed `BATCH_REPLACE_PHASE_ADMITTED` with no code. The modify
   changed nothing: the order keeps its previous price and quantity, and no
   replacement order exists.
2. **No phantom orders in history.** A refused modify that would have
   replaced the order no longer adds a REJECTED order, under a new order ID,
   to order history or open-order reads. This holds for a single
   `ModifyOrder` and for a batch item. A modify replaces the order when it
   changes the price, raises the total quantity, sets a new client order ID or
   uses `REPLACE_ONLY`. An order that was refused when placed still ends
   REJECTED, as before.
3. **Trading WebSocket text fixed.** The `tradews` SBE schema text now says
   what `BatchReplaceOrders` already does: each item amends its order in place
   or replaces it (the `AMEND_OR_REPLACE` behavior). The ConnectRPC and REST
   contracts already said so in 9.2. Only descriptions changed: no wire
   change and no version bump of its own (9.2.1's `tradews` 35 comes from
   the market-halt change). `RejectCode`
   `BATCH_REPLACE_ONLY_REQUIRED` (229) is documented as no longer returned
   and reserved.

Released in 9.2.1. Not in 9.2.

## How clients use it

`GetBatchReplaceStatus` is ConnectRPC only; there is no REST route. Pass the
`batch_request_id` that `BatchReplaceOrders` returned
(`POST /v1/orders/replace-batch` on REST). Status is kept for 60 seconds from
acceptance.

```bash
curl -sS https://<api-host>/orders.v1.OrdersReadService/GetBatchReplaceStatus \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer <token>' \
  -d '{"batchRequestId": "1234567890123456789"}'
```

An item refused after admission:

```json
{"itemIndex": 0, "phase": "BATCH_REPLACE_PHASE_REJECTED",
 "oldOrderId": "1234567890123450001", "code": "POST_ONLY_CROSS",
 "updatedTsNs": "1793594333241957468"}
```

- `code` is the refusal's error code without the `ERROR_CODE_` prefix, the
  same code a single `ModifyOrder` returns. Examples: `POST_ONLY_CROSS`,
  `PRICE_LEVELS_EXHAUSTED`, `CHILD_QTY_RAISE_NOT_ALLOWED`.
- `replacement_order_id` is 0, `action_taken` and `order_status` are
  unspecified. ConnectRPC JSON omits all three.
- `updated_ts_ns` is when the batch's latest refusal was recorded. When
  several items of one batch are refused, each shows the time of the most
  recent refusal, never earlier than its own.
- `admission_status`, `accepted_count` and `rejected_count` still describe
  admission, so the refused item counts as accepted. Retrying the same batch
  request returns the original admission answers.

## Migration

- Clients that polled `GetBatchReplaceStatus` until an item left `ADMITTED`
  now get `REJECTED` with a code. Before, such an item never left
  `ADMITTED`. Treat `REJECTED` as final for the item, and keep tracking
  `old_order_id`, which is unchanged.
- Clients that looked up a refused replacement under its planned new order ID
  (from the admission answer) now find no order. That ID never becomes an
  order.
