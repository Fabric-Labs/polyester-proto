## What and why

`GetOrderBook` serves deeper books, and its depth limit is one setting
rather than a fixed list:

- `GetOrderBookRequest.depth` is now an integer level count per side
  (`uint32`, field 3), from 1 to the maximum the service reports. The
  `Depth` enum (`DEPTH_1` … `DEPTH_1000`) and the old enum field 2 are
  removed. 0 or unset still selects the default of 50.
- `GetOrderBookResponse.max_depth` (field 8) reports that maximum in every
  response, available or not, so clients never hard-code it. It is 5,000
  levels per side by default.
- `GetOrderBookResponse.book_epoch` (field 7) is the epoch of `book_seq`.
  Snapshots order by `(book_epoch, book_seq)`: a higher epoch is newer
  whatever its `book_seq`, and a new epoch may restart `book_seq`. It is 0
  while `available` is false.
- A depth above the maximum is rejected with `INVALID_ARGUMENT` (REST: HTTP
  400, problem code `INVALID_DEPTH`) and a detail naming the maximum. It is
  never truncated.

The REST view follows: the `depth` query parameter takes any level count
from 1 to `maxDepth`, and the body gains `bookEpoch` (decimal string) and
`maxDepth` (number).

## How clients use it

ConnectRPC:

```http
POST /orderbook.v1.OrderbookService/GetOrderBook
Content-Type: application/json

{"symbolId": 1, "depth": 2500}
```

```json
{
  "symbolId": 1,
  "bookSeq": "984321",
  "bookEpoch": "3",
  "maxDepth": 5000,
  "available": true,
  "ts": "2026-11-15T20:58:00Z",
  "bids": [{"priceTicks": "65000000000000", "qtyScaled": "125000000"}],
  "asks": [{"priceTicks": "65001000000000", "qtyScaled": "50000000"}]
}
```

REST:

```http
GET /v1/orderbook/BTC-USDT?depth=2500
```

```json
{"symbol": "BTC-USDT", "bookSeq": "984321", "bookEpoch": "3", "maxDepth": 5000,
 "available": true, "ts": 1794776280000, "asks": [["65001", "0.5"]], "bids": [["65000", "1.25"]]}
```

A deep snapshot is a frozen view at its own `(bookEpoch, bookSeq)`. Keep it
apart from a live stream's book and never apply live updates to it. Drop it
when a newer epoch appears, and fetch it again to refresh it.

## Migration

1. Replace `Depth` enum values with level counts: `DEPTH_1` → `1`,
   `DEPTH_20` → `20`, `DEPTH_1000` → `1000`, and so on. In JSON, send a
   number (`"depth": 20`), not the enum name; the enum name is now rejected.
2. Binary clients built on the old contract still encode depth in field 2,
   which the service now ignores, so they get the default 50 levels.
   Regenerate them.
3. Read `maxDepth` from any response instead of assuming 1,000. Treat
   `INVALID_DEPTH` / `INVALID_ARGUMENT` as "ask for at most `maxDepth`".
4. Compare snapshots by `(bookEpoch, bookSeq)`, not by `bookSeq` alone.
