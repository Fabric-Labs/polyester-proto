## What and why

The REST API reference now states the true range of every unsigned 32-bit
integer. Fields, query parameters and update fields that hold an unsigned
32-bit value (for example an order's `version`, asset ids, basis points, and
second timestamps such as `startTsSec`) were documented as signed 32-bit
integers (`"format": "int32"`). A generated client could then use a signed
32-bit type and overflow on values above 2147483647. They are now documented
as `"type": "integer", "format": "int64"` with `"minimum": 0` and
`"maximum": 4294967295`, or the tighter bounds a field already had. Signed
32-bit and 64-bit integers are documented as before. Nothing changes on the
wire: REST sends and accepts these values as JSON numbers, as it always did,
and the ConnectRPC contract is unchanged.

## How clients use it

Calls are unchanged. A REST client generated from the reference now types
unsigned 32-bit values as 64-bit integers, which hold every value the API
returns. For example, an order's `version` in a REST order response:

```json
{"orderId": "4ZbL...", "version": 3}
```

is documented as `{"type": "integer", "format": "int64", "minimum": 0,
"maximum": 4294967295}`.

## Migration

None required: requests and responses are unchanged. Clients that generate
code from the REST reference may see unsigned 32-bit fields change from a
32-bit to a 64-bit integer type after regenerating; values that fit before
still fit.
