## What and why

API keys can now read more account data and claim the daily reward, each call gated by its own permission on the key's API-key policy. `PolicyAction` gains seven account permissions, valid on API-key policies only:

| Permission | Calls it opens to an API key | Scope |
| --- | --- | --- |
| `READ_PROFILE` | `GetProfile`, `GetUsernameHistory` | Main-account keys only. |
| `READ_ACCOUNT_DIRECTORY` | `ResolveAccount` | Any key; the lookup returns no account's private data. |
| `READ_WITHDRAW_VALIDATION` | `ValidateWithdrawDestination` | The key's scope; a sub-account target's policy must still allow external withdrawals. |
| `READ_DAILY_CLAIMS` | `GetDailyClaimStatus` | Main-account keys only. |
| `CLAIM_DAILY_REWARD` | `ClaimDailyReward` | Main-account keys only; the reward goes to the main account or a sub-account it owns, as for a session. |
| `READ_CHECKPOINTS` | `ListMyCheckpoints` | Main-account keys only. |
| `READ_REWARDS` | `ListMyRewardAwards` | Main-account keys only. |

Each permission grants exactly its calls and implies no other permission. `CLAIM_DAILY_REWARD` is the only write; `AcknowledgeMyRewardAward`, `SetMyRewardDestination` and the profile writes stay session-only. Interactive sessions behave as before.

`ValidateWithdrawDestination` changes for API keys: it checks a destination and moves no value, so a key now needs `READ_WITHDRAW_VALIDATION` instead of `EXTERNAL_WITHDRAW`.

## How clients use it

Grant the permissions on the key's API-key policy with an interactive session, for example over ConnectRPC `/auth.v1.PolicyService/UpdateApiPolicy`:

```json
{
  "policyId": "<decimal-fixed64-policy-id>",
  "policy": {"actions": ["READ_SPOT", "READ_PROFILE", "READ_DAILY_CLAIMS", "CLAIM_DAILY_REWARD"]},
  "updateMask": "actions",
  "expectedRevision": "3"
}
```

The key then signs the calls as any API-key request:

| Call | ConnectRPC | REST |
| --- | --- | --- |
| Profile | `/auth.v1.ProfileService/GetProfile` with `{}` | `GET /v1/auth/profile` |
| Username history | `/auth.v1.ProfileService/GetUsernameHistory` with `{}` | `GET /v1/auth/profile/username-history` |
| Resolve an account | `/auth.v1.ResolveService/ResolveAccount` with `{"query": "alice"}` | `GET /v1/auth/accounts:resolve?query=alice` |
| Validate a destination | `/chain.withdraw.v1.WithdrawService/ValidateWithdrawDestination` | `POST /v1/chain/withdraws:validate-destination` |
| Daily claim status | `/claims.v1.ClaimsService/GetDailyClaimStatus` with `{}` | `GET /v1/trading/daily-claim` |
| Claim the daily reward | `/claims.v1.ClaimsService/ClaimDailyReward` with `{}` | `POST /v1/trading/daily-claim/claim` |
| Checkpoints | `/checkpoints.v1.CheckpointService/ListMyCheckpoints` with `{}` | `GET /v1/checkpoints` |
| Reward awards | `/rewards.v1.RewardCampaignService/ListMyRewardAwards` with `{"limit": 50}` | `GET /v1/rewards/awards?limit=50` |

A key without the permission is refused with `PERMISSION_DENIED` and `AUTH_API_KEY_ACCESS_DENIED`, and the message names the missing permission. A key scoped to a sub-account calling a main-account call is refused the same way. `ValidateWithdrawDestination` is the exception: like every withdraw call, it refuses with `PERMISSION_DENIED` and the withdraw error code `ERROR_CODE_PERMISSION_DENIED`, and its message names `READ_WITHDRAW_VALIDATION`. A sub-account policy that names an account permission is refused with `INVALID_ARGUMENT`.

## Migration

1. Existing API-key policies that grant `EXTERNAL_WITHDRAW` were granted `READ_WITHDRAW_VALIDATION` when this change was deployed, so their keys keep validating destinations. Nothing to do for them.
2. A client that creates or updates API-key policies and wants their keys to validate destinations must include `READ_WITHDRAW_VALIDATION`. `EXTERNAL_WITHDRAW` alone no longer opens `ValidateWithdrawDestination` to an API key.
3. A client that rewrites a policy's whole `actions` list must keep the account permissions it read back, including `READ_WITHDRAW_VALIDATION`, or the update removes them.
