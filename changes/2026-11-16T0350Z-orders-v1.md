## What and why

`orders.v1.OrdersService.PreviewOrder` is now rate limited, as its published
rate-limit policy says: operation `orders.preview`, policy class
`TRADING_READ`, weight 1 per preview. The limit applies to the account
across all its sub-accounts, and to each API key and sub-account a request
uses. Without it, an account could send previews without bound and slow its
own order flow.

A preview over the limit is refused, and is not evaluated:

- ConnectRPC: `resource_exhausted` with the `polyester.ratelimit.v1.RateLimitDetail`
  error detail (`reason` `QUOTA_EXCEEDED`, `operation_id` `orders.preview`,
  `policy_class` `TRADING_READ`, `limit`, `remaining`, `retry_after_ms`).
- REST: HTTP 429 with the problem code `RATE_LIMIT_EXCEEDED` and the same
  decision in the problem's `rateLimit` member (`operationId`, `policyClass`,
  `reason`, `scope`, `limit`, `remaining`, `retryAfterMs`, `policyVersion`;
  the integers as decimal strings).

Both carry the `Retry-After`, `RateLimit-Limit`, `RateLimit-Remaining`,
`RateLimit-Reset` and `X-Polyester-RateLimit-Policy-Version` headers. When
the limit cannot be checked, the preview is refused with ConnectRPC
`unavailable` or REST HTTP 503 `RATE_LIMIT_AUTHORITY_UNAVAILABLE`; retry
later. Orders are not affected: creating, modifying and canceling orders
keep their own trading limits.

## How clients use it

Call PreviewOrder as before:

```bash
curl -sS https://<api-host>/orders.v1.OrdersService/PreviewOrder \
  -H 'Content-Type: application/json' \
  -d '{"order": {"symbolId": 1, "side": "BUY", "baseQtyScaled": "100000000",
                 "limitGtc": {"priceTicks": "1000000"}}}'
curl -sS -X POST https://<api-host>/v1/orders/preview \
  -H 'Content-Type: application/json' \
  -d '{"order": {"symbol": "BTC-USDT", "side": "BUY", "baseQty": "1",
                 "limitGtc": {"price": "1"}}}'
```

On a refusal, wait `Retry-After` seconds (or `retry_after_ms`) before the
next preview. The refusal's `limit` and the `RateLimit-Limit` header give the
limit in force; `ratelimit.v1.RateLimitService/GetTradingRateLimits` reports
the place and cancel limits only.

## Migration

None for clients that already handle `RATE_LIMIT_EXCEEDED` on order
creation. A client that previews in a loop, for example on every keystroke,
should debounce previews and back off on `resource_exhausted` or HTTP 429
instead of retrying at once.
