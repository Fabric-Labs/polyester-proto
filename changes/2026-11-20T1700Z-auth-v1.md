## What and why

A strategy bot can now read its own profit and loss. `SetStrategyBotAccess`
gives the bot's `STRATEGY_BOT` key an API policy that also allows
`READ_PNL`, alongside spot trading and the reads of its orders and balances.
The bot's sub-account policy already allowed `READ_PNL`, so the key can now
call the profit and loss reads for its own sub-account. It still allows no
action that moves value out of the account.

Only the `SetStrategyBotAccess` comment changes; no message, field or enum
value does.

## How clients use it

Nothing changes for clients: the deploy flow calls `SetStrategyBotAccess`,
and SDKs don't wrap it. The policy of a bot's key, as `GetApiPolicy`
(`POST /auth.v1.PolicyService/GetApiPolicy`) returns it, now lists
`READ_PNL` among its actions:

```json
{"policy": {"actions": ["TRADE_SPOT", "READ_BALANCES", "READ_SPOT", "READ_PNL"]}}
```

The bot's key is scoped to its own sub-account, so it reads that
sub-account's profit and loss without naming it. A request signed with the
bot's key, as every API key request is:

```http
POST /pnl.v1.ProfitAndLossService/GetProfitAndLoss
Content-Type: application/json
Connect-Protocol-Version: 1
X-API-KEY-ID: <the bot's key ID>
X-API-TIMESTAMP: <milliseconds>
X-API-SIGNATURE: <signature>

{"window": "PROFIT_AND_LOSS_WINDOW_DAYS_7"}
```

REST: `GET /v1/pnl?window=DAYS_7`, signed with the same headers.

A page that shows a bot key's permissions read-only shows the profit and
loss read with the others.

## Migration

None. Bot keys created before this change keep their policy; a bot gets the
new policy when the deploy flow next gives it access.
