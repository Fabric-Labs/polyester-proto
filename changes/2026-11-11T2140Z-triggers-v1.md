## What and why

Trigger IDs are now opaque public IDs, like order IDs. A trigger ID is
issued by the exchange and identifies one trigger of one account (or
sub-account): it is valid only for that account, and its value carries no
other meaning. No field, type or method changes; only the values of trigger
IDs do.

Every trigger ID the API answers is the public one:

- `triggers.v1.TriggersService`: `trigger_id` in `CreateTrigger`,
  `GetTrigger`, `ListTriggers`, `ListTriggerEvents`, `CancelTrigger`,
  `ModifyTrigger`, `PauseTrigger`, `ResumeTrigger` and each
  `BatchCancelTriggers` result, and `take_profit_trigger_id` and
  `stop_loss_trigger_id` of `CreateOco`.
- `orders.v1.OrdersService`: `take_profit_trigger_id`,
  `stop_loss_trigger_id` and `trailing_stop_trigger_id` of `CreateOrder`,
  `BatchCreateOrders` and `ModifyOrder`.
- `orders.v1.OrdersReadService`: an order's `origin.trigger_id` and its
  attached legs' `attached_risk.*.state.trigger_id`.
- The trading WebSocket's create and OCO acknowledgements, and the private
  WebSocket's trigger state and trigger event streams (`triggerId`).

Every request that names a trigger takes the public ID: the trigger
methods above, `BatchCancelTriggers`'s `trigger_ids`, and the `trigger_id`
filter of `GetOpenOrders` and `GetOrderHistory`. An ID that is not one of
the caller's triggers is refused as a trigger that does not exist.

## How clients use it

Use a trigger ID only as the API gave it, for the account that owns it:

```bash
curl -sS https://<api-host>/triggers.v1.TriggersService/GetTrigger \
  -H 'Content-Type: application/json' -d '{"triggerId": "<trigger_id from CreateTrigger>"}'
curl -sS 'https://<api-host>/v1/triggers/<trigger_id>'
curl -sS 'https://<api-host>/v1/orders/open?triggerId=<trigger_id>'
```

REST shows a trigger ID in base58, as every public ID; ConnectRPC JSON
carries the decimal string of the `fixed64` (`uint64` for the attached-leg
fields of order responses). A trigger ID and an order ID never coincide.

Refusals of an ID that is not the caller's trigger:

| Call | Answer |
| --- | --- |
| `GetTrigger`, `ListTriggerEvents` | `not_found` (HTTP 404) |
| `CancelTrigger`, `ModifyTrigger`, `PauseTrigger`, `ResumeTrigger` | `TRIGGER_NOT_FOUND` |
| `BatchCancelTriggers` | that item `REJECTED` with `TRIGGER_NOT_FOUND`; the others are answered as usual |
| `GetOpenOrders`, `GetOrderHistory` with `trigger_id` | `INVALID_TRIGGER_ID`, `invalid_argument` (HTTP 400) |

## Migration

This is a breaking change for clients that kept trigger IDs. After the
change, every existing trigger has a new ID, and an ID read before it is
refused as above.

1. Drop stored trigger IDs, and read your triggers again with `ListTriggers`
   to get their current IDs.
2. A `ListTriggers` or `ListTriggerEvents` page token issued before the
   change is refused with `invalid_argument`: start that listing again from
   the first page. An order listing filtered by `trigger_id` starts again
   too, with the trigger's new ID; other order listings are unaffected.
3. If you deduplicate private WebSocket trigger events or states by
   `triggerId`, expect each trigger's ID to change once, at the change.
4. Do not derive anything from a trigger ID's value; compare it only with
   other trigger IDs of the same account.
