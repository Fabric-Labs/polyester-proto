## What and why

The consent methods of `auth.v1.ConnectedAppService` are renamed so that they
name what the website's "Connect an app" page answers: a pending app
connection request. Any outside app can ask to connect, such as an AI
assistant, a spreadsheet, a portfolio tracker or another tool. Every field
number, rule and flow is unchanged.

| Before | After |
| --- | --- |
| RPC `GetAppAuthorization` | RPC `GetAppConnectionRequest` |
| RPC `ApproveAppAuthorization` | RPC `ApproveAppConnectionRequest` |
| RPC `DenyAppAuthorization` | RPC `DenyAppConnectionRequest` |
| message `AppAuthorization` | message `AppConnectionRequest` |
| message `GetAppAuthorizationRequest` | message `GetAppConnectionRequestRequest` |
| message `GetAppAuthorizationResponse` | message `GetAppConnectionRequestResponse` |
| message `ApproveAppAuthorizationRequest` | message `ApproveAppConnectionRequestRequest` |
| message `ApproveAppAuthorizationResponse` | message `ApproveAppConnectionRequestResponse` |
| message `DenyAppAuthorizationRequest` | message `DenyAppConnectionRequestRequest` |
| message `DenyAppAuthorizationResponse` | message `DenyAppConnectionRequestResponse` |
| field `GetAppAuthorizationResponse.authorization` (JSON `authorization`) | field `GetAppConnectionRequestResponse.connection_request` (JSON `connectionRequest`), still number 1 |

The three consent methods serve only the website's consent page, so they are
now left out of the public API reference. They stay in the contract and in the
SDKs. `ApproveAppConnectionRequest` now declares that it needs a fresh MFA
step-up, as creating an API key does; that was already enforced.

`ConnectedApp`, `ConnectedAppClient`, `ListConnectedApps`,
`RevokeConnectedApp` and `AUTH_CONNECTED_APP_LIMIT_REACHED` (73) do not
change.

## How clients use it

Every method needs the website session token; an API key is refused.

```text
POST /auth.v1.ConnectedAppService/GetAppConnectionRequest
{"requestId": "<from the consent page's request query parameter>"}
→ {"connectionRequest": {"client": {"clientId": "...", "name": "..."},
                         "scopes": ["account:read"], "resource": "...",
                         "redirectHost": "...", "expiresAt": "..."}}

POST /auth.v1.ConnectedAppService/ApproveAppConnectionRequest
X-Auth-Step-Up: <fresh step-up proof from an MFA challenge>
{"requestId": "<request ID>"}
→ {"redirectUrl": "https://app.example/callback?code=...&state=..."}

POST /auth.v1.ConnectedAppService/DenyAppConnectionRequest
{"requestId": "<request ID>"}
→ {"redirectUrl": "https://app.example/callback?error=access_denied&state=..."}
```

After approving or denying, the client navigates the browser to
`redirectUrl`. An unknown, expired or already answered request is NotFound. An
account with 20 connected apps gets FailedPrecondition with
`AUTH_CONNECTED_APP_LIMIT_REACHED`. None of the methods has a REST route.

## Migration

1. Call the new paths: `GetAppConnectionRequest`,
   `ApproveAppConnectionRequest` and `DenyAppConnectionRequest`. The old paths
   no longer exist.
2. Rename the generated types you use as the table above shows.
3. Read the pending request from the `connection_request` field (JSON
   `connectionRequest`) instead of `authorization`.

Request bodies, the `X-Auth-Step-Up` header, responses and errors are
otherwise unchanged. `ListConnectedApps` and `RevokeConnectedApp` need no
change.
