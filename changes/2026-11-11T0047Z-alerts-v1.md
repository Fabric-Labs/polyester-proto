## What and why

**Availability:** `PriceAlertService` and its two policy actions,
`READ_PRICE_ALERTS` and `MANAGE_PRICE_ALERTS`, are devnet only. They are not
available on testnet yet; the service isn't deployed or routed there.
`PolicyService` itself is unchanged and available everywhere.

Mark `PriceAlertService` and the two actions devnet-only in the SDK docs and
package docs. Don't present them as available on testnet, and don't mark
`PolicyService` or its other actions devnet-only.

`PolicyAction` gains two API-key permissions for price alerts:

- `READ_PRICE_ALERTS` (36): list the main account's price alerts
  (`ListAlerts`).
- `MANAGE_PRICE_ALERTS` (37): create, update and cancel the main account's
  price alerts (`CreateAlert`, `UpdateAlert`, `CancelAlert`). It does not
  allow listing them.

Each grants exactly the calls it names and implies no other permission. Like
the other main-account permissions, they apply to API-key policies only and
work only for an API key scoped to the main account.

`PriceAlertService` now checks them. An API key whose policy does not grant the
call's permission is refused with `PERMISSION_DENIED` and the auth error code
`AUTH_API_KEY_ACCESS_DENIED`, before the call reads or changes any alert. A
key with a restrictive policy, such as one that only reads spot orders, can no
longer create, change or cancel price alerts. Session tokens are unchanged, and
an API key scoped to a subaccount is still refused with
`SUBACCOUNT_KEY_REFUSED`.

## How clients use it

Grant the permissions on the key's API-key policy, with the other actions it
holds. Changing an API-key policy takes a session token, as before:

```http
POST /auth.v1.PolicyService/UpdateApiPolicy
Content-Type: application/json

{"policyId": "1234", "expectedRevision": "3", "updateMask": "actions",
 "policy": {"actions": ["READ_SPOT", "READ_PRICE_ALERTS", "MANAGE_PRICE_ALERTS"]}}
```

A key without the permission gets `permission_denied` with an
`auth.v1.AuthErrorDetail` of code `AUTH_API_KEY_ACCESS_DENIED`, and a message
that names the missing permission, for example `API key policy does not grant
MANAGE_PRICE_ALERTS`.

## Migration

An API key that calls the Price Alert API needs its policy to grant
`READ_PRICE_ALERTS` to list alerts and `MANAGE_PRICE_ALERTS` to create, update
or cancel them:

1. Find the API-key policy attached to each key that calls the Price Alert API.
2. Add `READ_PRICE_ALERTS`, `MANAGE_PRICE_ALERTS` or both, as the key needs.

Session-token clients need no change.
