## What and why

An attached trailing stop's buy-back maximum, `TrailingStopPolicy.limit_price_ticks`,
is now refused with the same specific error codes as a standalone trailing
stop's `limit_price_ticks`, and with a field violation that names the attached
field. Before, `CreateOrder`, `PreviewOrder` and `BatchCreateOrders` answered
a maximum set on a BUY parent, missing on a SELL parent or below the
activation price with `TRIGGER_PRICE_INVALID`, and one off the tick with
`PRICE_TICK_SIZE`, each with no violation. `TRIGGER_PRICE_INVALID` pointed an
OCO bracket's user at the take-profit's trigger price instead of the trailing
stop's maximum.

The rule itself is unchanged. The parent order's side decides the rule: a SELL
parent's trailing stop buys back, so it requires a maximum; a BUY parent's
trailing stop sells, so it takes none. Messages and paths change; no field or
enum value is added.

`CreateOrder`, `PreviewOrder` and each `BatchCreateOrders` item now answer:

| Mistake | Code | `field_path` | `rule_id` |
| --- | --- | --- | --- |
| Set on a BUY parent | `BAD_PRICE` | `order.attached_risk.trailing_stop.limit_price_ticks` | `sell_unset` |
| Missing on a SELL parent | `TRIGGER_BUY_REQUIRES_LIMIT` | same | `buy_required` |
| Not a multiple of the pair's tick size | `PRICE_TICK_SIZE` | same | `tick_size` |
| Below `activation_price_ticks` | `BAD_PRICE` | same | `buy_at_least_activation` |

These are the codes and rule IDs a standalone trailing stop's
`trigger.strategy.trailing_stop.limit_price_ticks` gets in `CreateTrigger`.
Over REST the violation names the REST request field instead:
`order.attachedRisk.trailingStop.limitPrice`, and
`items[N].attachedRisk.trailingStop.limitPrice` for batch item `N`.

`ModifyOrder` and `BatchReplaceOrders` do not carry the parent's side. They
check the maximum's tick (`PRICE_TICK_SIZE`, `tick_size`) and its floor at the
activation price (`BAD_PRICE`, `buy_at_least_activation`) with a violation on
`new_attached_risk.trailing_stop.limit_price_ticks`, or
`items[N].new_attached_risk.trailing_stop.limit_price_ticks` for batch replace
item `N`. Over REST these are `newAttachedRisk.trailingStop.limitPrice` and
`items[N].newAttachedRisk.trailingStop.limitPrice`.
The side rule is checked when the order is changed, and answers `BAD_PRICE`
with no violation, both for a maximum set on a BUY parent and for one missing
on a SELL parent.

## How clients use it

A SELL parent with an attached trailing stop and no maximum, previewed over
ConnectRPC:

```bash
curl -sS https://<api-host>/orders.v1.OrdersService/PreviewOrder \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer <token>' \
  -d '{"order": {"symbolId": 1, "side": "SELL", "baseQtyScaled": "20000",
       "limitGtc": {"priceTicks": "69000000000000"},
       "attachedRisk": {"trailingStop": {"trailingDistanceTicks": "3000000000000"}}}}'
```

```json
{
  "admissible": false,
  "rejection": {
    "code": "ERROR_CODE_TRIGGER_BUY_REQUIRES_LIMIT",
    "violations": [{
      "fieldPath": "order.attached_risk.trailing_stop.limit_price_ticks",
      "ruleId": "buy_required",
      "message": "limit_price_ticks is required when the parent order sells"
    }]
  },
  "evaluatedAt": "2026-11-02T18:12:00Z"
}
```

`CreateOrder` answers the same refusal as an `invalid_argument` error whose
`ErrorDetail` carries the code and the violation. `BatchCreateOrders` answers
it in the item's `rejected.error`. Over REST, the maximum is the decimal
`attachedRisk.trailingStop.limitPrice`: `POST /v1/orders` answers HTTP 400
with the same code, `POST /v1/orders/batch` an item rejection, and
`POST /v1/orders/preview` HTTP 200 with `admissible: false` and the rejection's
code, field and rule, as over ConnectRPC. Each REST violation names the REST
field, as listed above.

To fix the request: on a SELL parent, set the maximum on the tick and at least
the activation price. On a BUY parent, leave it unset.

## Migration

None required. A client that matched `TRIGGER_PRICE_INVALID` to detect a wrong
trailing-stop maximum on create, preview or batch create should match the codes
in the table above instead. `TRIGGER_PRICE_INVALID` still answers take-profit
and stop-loss trigger prices.
