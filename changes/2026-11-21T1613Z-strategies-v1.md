## What and why

The contract for deploying a bot from its deploy page. Until now a deploy
proposal could be recorded and read, but nothing deployed it.

**Not usable yet:** this release publishes the contract only. `DeployBot`
answers `UNIMPLEMENTED` to an eligible caller (the user's own recently
MFA-elevated session) until the deploy flow is enabled in a later release;
API keys and connected-app sessions are already refused as described below.
Build against the contract, but don't ship a client that depends on it yet.

- **`DeployBot`** (new RPC) deploys one deploy proposal of the caller. It
  checks the version again, prepares the bot's subaccount, sets the bot's
  limits and trading key, and starts the bot. The steps run in the call; once
  the bot's start is recorded, the bot starts without the user.
  - Only the user's own session may call it, and that session must be
    recently MFA-elevated (`MFA_RECENT`, as auth defines it). API keys and
    sessions a connected app holds are refused with
    `AUTH_SESSION_KIND_NOT_ALLOWED` (PERMISSION_DENIED).
  - A proposal is deployed at most once. Calling again (after an error, a
    timeout or from another tab) continues the same deploy and answers its
    status; it never starts a second bot.
  - A step that fails ends the deploy as `FAILED`, answered as a status with
    `failed_at` and `failure`, not as an error.
- **`SubaccountAuthorization`** (new message): the user's signed
  authorization for the bot's new subaccount, exactly what
  `auth.v1 CreateSubaccountChallenge` returned plus the smart account's
  signature. Needed only when the deploy creates a subaccount.
- **`DeployStatus.State.SETTING_ACCESS`** (new value, 9): setting the bot's
  limits and its trading key, between `CREATING_SUBACCOUNT` and `FUNDING`.
  `failed_at` may name it.
- **New error codes:**
  - `MFA_ELEVATION_REQUIRED` (32, PERMISSION_DENIED): complete MFA and deploy
    again; nothing was started.
  - `PROPOSAL_EXPIRED` (33, FAILED_PRECONDITION): propose the deploy again.
  - `SUBACCOUNT_AUTHORIZATION_REQUIRED` (34, FAILED_PRECONDITION): the deploy
    needs a new subaccount and the request has no authorization, or one that
    can no longer be used (a challenge since replaced or expired). Get a new
    challenge, have the user sign it, and call again; the deploy keeps its
    progress.

## How clients use it

When the deploy creates a subaccount, get and sign a challenge first
(`POST /v1/auth/subaccounts/challenge`), then deploy:

```http
POST /strategies.v1.StrategiesService/DeployBot
Content-Type: application/json
Connect-Protocol-Version: 1

{
  "proposalId": "1234",
  "subaccountAuthorization": {
    "smartAccountAddress": "0x0000000000000000000000000000000000000000",
    "message": "<the challenge's exact message>",
    "signature": "0x…"
  }
}
```

```json
{
  "status": {
    "proposalId": "1234",
    "state": "DEPLOYING",
    "botId": "5678",
    "subaccountId": "9012"
  }
}
```

Read progress afterwards with `GetDeployStatus`. On
`SUBACCOUNT_AUTHORIZATION_REQUIRED`, request a new challenge and call
`DeployBot` again with it. On `MFA_ELEVATION_REQUIRED`, complete MFA and call
again. `DeployBot` is ConnectRPC only; it has no REST path.

## Migration

None: the RPC, message, state value and error codes are new. A client that
switches on `DeployStatus.State` should handle `SETTING_ACCESS`.
