## What and why

The private realtime streams of a main account now carry only records the subscriber may read. Each stream that used to mix the account's own records with records it reaches through a delegated subaccount role is split in two:

- The existing stream carries the account's own records. Any caller whose read returns them can subscribe: an API key with the read's permission, or the account's signed-in session.
  - `private:auth:subaccounts:{account_id}:proto`: the subaccounts the account owns (`READ_SUBACCOUNTS`).
  - `private:auth:api-policies:{account_id}:proto`: the account's own API-key policies (`READ_API_POLICIES`).
  - `private:auth:subaccount-policies:{account_id}:proto`: the account's own subaccount policies (`READ_SUBACCOUNT_POLICIES`).
  - `private:auth:address-books:{account_id}:proto`: invalidations of the account's own address book (`READ_ADDRESS_BOOK`).
- A new stream carries the rest, for the account's signed-in session only. API keys are refused with `AUTH_SESSION_KIND_NOT_ALLOWED`.
  - `private:auth:subaccounts:delegated:{account_id}:proto`: subaccounts the account holds a delegated role on, with that role, including the removal update.
  - `private:auth:api-policies:delegated:{account_id}:proto`: API-key policies of keys on subaccounts the account administers through a delegated role.
  - `private:auth:subaccount-policies:delegated:{account_id}:proto`: policies of subaccounts the account holds a delegated role on.
  - `private:auth:address-books:subaccounts:{account_id}:proto`: invalidations of the address books of subaccounts the account reads through a subaccount role, owned or delegated.

Subscription tokens for every private stream are now issued exactly when the stream's read would answer the caller. A refusal carries that read's own error code and message, for example `AUTH_API_KEY_ACCESS_DENIED` "API key policy does not grant READ_API_KEYS". The funding-flow stream `private:chain:lifecycle:flows:{account_id}[:proto]` needs `READ_FUNDING_FLOWS`, as listing account flows does. Message types are unchanged.

## How clients use it

Request a subscription token per stream, then subscribe as today:

```http
GET /v1/rt/subscribe?channel=private:auth:subaccounts:delegated:3gDmDv6tjHJ:proto
```

The token is refused with the stream's read error when the caller may not read it, for example an API key on a delegated stream, or a key without the read's permission on an owned stream.

## Migration

- API-key clients: nothing to change for owned records. The owned streams keep working with the read's permission; they no longer carry delegated records, which the key's reads never returned. Grant the key the read permission named above if it lacked it.
- Signed-in session clients that show delegated subaccounts, their policies or subaccount address books live: also subscribe to the matching new stream. Until they do, those records load through the unary reads but do not update live.
