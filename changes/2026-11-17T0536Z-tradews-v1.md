## What and why

The last refusals that answered in one fixed shape now answer in the caller's
protocol, like every other refusal: an RPC call gets its RPC error, and any
other request gets `application/problem+json` with a `code`, `title` and
`detail`. Statuses stay the same except for two changes below: the
unreadable body (now `400`), and a plain `POST` to the market-data WebSocket
(`426`, now `405`).

**Trade WebSocket upgrade refusals** (`wss://<api-host>/ws/trade.proto` and `wss://<api-host>/ws/trade.sbe`). A refused
upgrade used to answer its code as plain text. It now answers the problem with
the same code and status. Authentication refusals carry the same `code`,
`title` and `detail` as on every REST endpoint, and
`AUTH_TEMPORARILY_UNAVAILABLE` carries `Retry-After`.

| Refusal | Status | Code |
| --- | --- | --- |
| No credentials or an invalid login | 401 | `UNAUTHENTICATED`, `SIGNATURE_INVALID`, `TIMESTAMP_SKEW`, `RECV_WINDOW_INVALID`, `MISSING_HEADERS`, `KEY_EXPIRED`, `KEY_DISABLED`, `IP_NOT_ALLOWED`, `REPLAY_DETECTED` |
| A login that is not an API key | 401 | `API_KEY_REQUIRED` |
| The key's signed logins fill their receive windows | 429 | `REPLAY_CAPACITY_EXHAUSTED` |
| Login freshness cannot be checked | 503 | `AUTH_TEMPORARILY_UNAVAILABLE` |
| Too many sessions | 429 | `TOO_MANY_SESSIONS_API_KEY`, `TOO_MANY_SESSIONS_ACCOUNT` |
| A cancel-on-disconnect lease the account cannot take | 400, 403, 429, 503 or 504 | the lease refusal's code, for example `CANCEL_ALL_AFTER_TIMEOUT_INVALID` |

**Market-data WebSocket** (`wss://<api-host>/ws/market.sbe`). A request that cannot be upgraded
used to get the WebSocket library's plain text. Now a method other than `GET`
answers `405 METHOD_NOT_ALLOWED` with `Allow: GET`, and a `GET` without
WebSocket upgrade headers answers `426 UPGRADE_REQUIRED` with
`Upgrade: websocket`. A plain `POST` without upgrade headers used to answer
`426`; it now answers `405`, since the endpoint only upgrades `GET` requests.

**A method a REST endpoint does not serve.** An endpoint that serves only
some methods used to answer any other method with an empty `405`. Now it answers the
`405 METHOD_NOT_ALLOWED` problem; `Allow` still lists the methods the
endpoint serves.

**A signed request whose body cannot be read** (before authentication, though
within the size limit). Every API now answers it the same way. A REST caller
gets `400 BAD_REQUEST` with detail "The request body could not be read.", and
an RPC caller gets `invalid_argument`. Before, each API answered differently:

| API | Before (REST) | Before (RPC) |
| --- | --- | --- |
| Account and security (`auth.v1`, through the `/v1/auth` and `auth.v1` paths), collaboration whiteboards, rewards, swap, statement exports | plain-text 400 | plain-text 400 |
| Order reads (`orders.v1.OrdersReadService`, `triggers.v1.TriggersService` reads) | `400 VALIDATION_ERROR` | the same problem |
| Order writes (`orders.v1.OrdersService`, `triggers.v1.TriggersService` writes), balances (`ledger.read.v1.LedgerReadService`) | `400 BAD_REQUEST` | the same problem |
| Account flows (`chain.lifecycle.v1.LifecycleReadService`) | `400 INVALID_REQUEST` | the same problem |
| Account reads (`auth.v1` reads, `vip.v1`, `fees.v1`, `ratelimit.v1`, `checkpoints.v1`, `system.v1`) | `503 AUTH_UPSTREAM_ERROR` | the same problem |
| Deposit addresses, guard signer | `503 UPSTREAM_ERROR` | the same problem |
| Withdrawals (`chain.withdraw.v1`), internal transfers (`transfer.v1`) | `503 SERVICE_UNAVAILABLE` | the same problem |
| Daily claim (`claims.v1`) | a ConnectRPC error with `claims.v1` `ERROR_CODE_INVALID_REQUEST` | the same |
| Price alerts (`alerts.v1`) | plain-text 413 | plain-text 413 |

**A signed request over the body limit** (before authentication). Price alerts
and the daily claim now answer it as every other API does: `413
REQUEST_TOO_LARGE` for REST and `resource_exhausted` for RPC. Price alerts
answered plain text. The daily claim answered a ConnectRPC error with
`ERROR_CODE_REQUEST_TOO_LARGE`, to REST callers too.

## How clients use it

Read the refusal from the problem's `code` (REST and WebSocket upgrades) or
from the RPC code and its error detail, never from body text:

```text
GET https://<api-host>/ws/trade.proto
X-API-KEY-ID: <key id>
...

HTTP/1.1 401 Unauthorized
Content-Type: application/problem+json

{"type":"https://polyester.dev/problems/signature-invalid","title":"Invalid API Key Signature",
 "status":401,"detail":"API key signature is invalid","code":"SIGNATURE_INVALID"}
```

Retry `AUTH_TEMPORARILY_UNAVAILABLE` after its `Retry-After`. Resend a request
whose body could not be read (`400 BAD_REQUEST`, RPC `invalid_argument`) with a
complete body.

## Migration

1. Trade WebSocket clients that compared the refused upgrade's body with a
   code must read `code` from the JSON problem instead. Statuses are unchanged.
2. Market-data WebSocket clients that matched the plain-text 405 or 426 body
   must read the problem's `code`.
3. Clients that retried the unreadable-body `503` from account reads, deposit
   addresses, the guard signer, withdrawals or internal transfers get
   `400 BAD_REQUEST` now: resend the request with a complete body instead of
   backing off.
4. Clients that matched `VALIDATION_ERROR`, `INVALID_REQUEST`,
   `AUTH_UPSTREAM_ERROR`, `UPSTREAM_ERROR` or `SERVICE_UNAVAILABLE` for an
   unreadable body must match `BAD_REQUEST`.
5. Daily-claim REST clients get `413 REQUEST_TOO_LARGE` and `400 BAD_REQUEST`
   problems instead of ConnectRPC errors. RPC clients get
   `resource_exhausted` and `invalid_argument` without the `claims.v1` detail.
