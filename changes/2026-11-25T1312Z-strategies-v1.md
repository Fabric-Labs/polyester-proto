## What and why

A strategy bot's subaccount can no longer fund another bot's deploy.
`ProposeDeploy` now refuses a `funding_subaccount_id` that is, or was, a
strategy bot's subaccount, with the new error code `FUNDING_SOURCE_IS_BOT`.
A bot's funds return to the owner only through the bot funds return, never
into another bot.

- The refusal applies whether the bot is still running or has stopped, and
  also when the proposal moves no funding.
- A deploy is funded from the main account (`funding_subaccount_id` 0) or a
  subaccount no bot has held.
- The check comes after the ownership check: a subaccount the caller does
  not own is still `FUNDING_SUBACCOUNT_NOT_FOUND`.

## How clients use it

`POST /strategies.v1.StrategiesService/ProposeDeploy` with a bot's
subaccount as `funding_subaccount_id` fails with the Connect code
`failed_precondition`. Its `strategies.v1.ErrorDetail` has `code`
`FUNDING_SOURCE_IS_BOT` and `field_path` `funding_subaccount_id`, and the
message reads "a strategy bot's subaccount can't fund a deploy; fund it from
the main account or a subaccount no bot has held".

```json
// POST /strategies.v1.StrategiesService/ProposeDeploy
{"strategyId": "5905316723483801479", "revision": 1, "botName": "Weekly DCA",
 "fundingSubaccountId": "13703464673950623009",
 "funding": [{"asset": "USDT", "amount": "200"}],
 "idempotencyKey": "deploy-1"}
// -> failed_precondition, ErrorDetail {code: FUNDING_SOURCE_IS_BOT,
//    fieldPath: "funding_subaccount_id"} when that subaccount is a bot's
```

Show the deploy page's funding source choice without bot subaccounts, and
treat this code as "choose another funding source".

## Migration

None: no existing client proposes a deploy funded by a bot's subaccount on
purpose. A client that did now gets `FUNDING_SOURCE_IS_BOT` and should ask
the user for another source.
