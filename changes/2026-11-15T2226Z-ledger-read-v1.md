## What and why

The ledger REST routes now answer `503 Service Unavailable` instead of `502 Bad Gateway` when ledger data is temporarily unavailable (`UPSTREAM_ERROR`, `WALLET_RESOLUTION_UNAVAILABLE`). This covers `GET /v1/statements`, `/v1/transfers`, `/v1/balances`, `/v1/balances/history` and the equity routes.

A ledger read that runs past its deadline now answers `503` too, instead of `504 Gateway Timeout`, with the same `code` and a `detail` that starts with `request_deadline_exceeded`. Every ledger route is a read, so a retry is always safe.

The body is the same `application/problem+json` as before, with the same `code` and `detail`. A `502` or `504` never delivered it: the public edge replaces either with its own plain-text page (`error code: 502`), so clients got neither CSV nor a problem document. The ConnectRPC methods are unchanged: they already answer `unavailable` and `deadline_exceeded`.

## How clients use it

Retry a `503` with backoff, honouring `Retry-After` when it is present:

```http
GET https://<api-host>/v1/statements?startTime=2026-11-14T00:00:00Z&endTime=2026-11-15T00:00:00Z

HTTP/1.1 503 Service Unavailable
Content-Type: application/problem+json

{"type": "...", "title": "Upstream Error", "status": 503, "code": "UPSTREAM_ERROR", "detail": "upstream_unavailable: Ledger data is temporarily unavailable."}
```

## Migration

None required. A client that retries `502` or `504` should also retry `503`; most HTTP retry policies already treat all three as retryable.
