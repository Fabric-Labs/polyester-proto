## What and why

The documentation of `CancelAllOrders`, `CancelAllAfter` (the dead-man
switch) and `CancelTrigger` now states plainly what a cancel-all cancels.
Behavior is unchanged; it was not documented, and a bot relying on the
dead-man switch could believe that all trading stopped when it fired.

Cancel-all and the dead-man switch cancel open orders, never triggers. Open
orders that triggers placed are canceled like any other order in scope: a
TWAP's working slice, a ladder's levels, the order a fired stop placed and an
attached leg's working exit. The triggers themselves are not canceled and
keep their reserved funds:

- A stop-loss, take-profit or trailing stop that has not fired stays armed
  and places its order when its condition is met.
- A TWAP keeps running and places its next slice when it is due.
- A ladder ends once none of its levels remains open: `STATUS_CANCELED` with
  `TRIGGER_CANCEL_REASON_USER_REQUEST` when none of them filled,
  `STATUS_COMPLETED` when any did.
- An attached leg whose working exit is canceled ends `STATUS_CANCELED` with
  `TRIGGER_CANCEL_REASON_USER_REQUEST`, and so do the parent's other legs
  when `oco` is set. Attached legs without a working exit keep protecting the
  parent's filled position, even when the parent order is canceled; they end
  only if the parent is canceled before any fill.
- A paused trigger stays paused.

`CancelAllOrdersResponse.matched_orders` counts the open orders triggers
placed, never the triggers. The comments on `CancelAllOrders`,
`CancelAllOrdersRequest`, `CancelAllOrdersResponse.matched_orders`,
`CancelAllAfter`, `CancelAllAfterRequest`, `DeadManSwitchScope`,
`CancelTrigger` and `TriggerCancelReason.TRIGGER_CANCEL_REASON_USER_REQUEST`
say so. No field, enum value or method changed.

## How clients use it

To stop all automated trading, cancel each live trigger first, then the
orders: a trigger that fires before its cancel places an order that the
cancel-all then cancels. List the live triggers, attached legs included,
cancel each one, then cancel all orders:

```bash
curl -sS https://<api-host>/triggers.v1.TriggersService/ListTriggers \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer <token>' \
  -d '{"status": ["STATUS_CREATED", "STATUS_ARMED", "STATUS_RUNNING", "STATUS_PAUSED"], "limit": 1000}'
curl -sS https://<api-host>/triggers.v1.TriggersService/CancelTrigger \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer <token>' \
  -d '{"triggerId": "1234567890123456789"}'
curl -sS https://<api-host>/orders.v1.OrdersService/CancelAllOrders \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer <token>' \
  -d '{"requestId": "stop-all-1"}'
```

REST:

```bash
curl -sS 'https://<api-host>/v1/triggers?status=ARMED' -H 'Authorization: Bearer <token>'
curl -sS -X DELETE https://<api-host>/v1/triggers/3sDK21t5nHJ -H 'Authorization: Bearer <token>'
curl -sS -X POST https://<api-host>/v1/orders/cancel-all \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer <token>' \
  -d '{"requestId": "stop-all-1"}'
```

Over REST, list each live status (`CREATED`, `ARMED`, `RUNNING`, `PAUSED`)
in turn. `ListTriggers` returns at most 1000 triggers per page, newest first;
follow `next_page_token` until it is empty. Canceling a TWAP or a ladder also
cancels its open child orders. The dead-man switch cannot do this for a
client that stopped: when it fires, the client's triggers stay live.

## Migration

None: behavior is unchanged. A client that expected cancel-all or the
dead-man switch to stop its triggers should also cancel them with
`CancelTrigger`, as above.
