## What and why

Users can link a Telegram account to their Polyester account, so the Polyester
assistant can talk to them on Telegram and alerts can be delivered there. Telegram
linking reuses social verification:

- `SocialProvider` gains `TELEGRAM` (3).
- `SocialVerificationStatus` gains `STATUS_AWAITING_CONFIRMATION` (8): a Telegram
  account sent the code to the Polyester bot, and the user must confirm that
  account before it is linked.
- `SocialVerification` gains `display_name` (17), the Telegram account's name. For
  Telegram, `handle` is its username (empty when it has none) and, while the status
  is `STATUS_AWAITING_CONFIRMATION`, `provider_user_id` is its numeric Telegram user
  ID.
- `StartSocialVerificationResponse` gains `action_url` (4): for Telegram, the
  `https://t.me/...?start=<code>` link that opens the Polyester bot with the code.
- New `ConfirmSocialVerification` links the Telegram account that sent the code.
  A linked Telegram account becomes a channel to the account, so it requires
  enrolled MFA and a fresh step-up proof, like creating an API key.
- New `UnlinkSocialAccount` unlinks the Telegram account, or cancels a link in
  progress.

A Telegram account links at most one Polyester account, by its numeric user ID.
Codes are single use and expire 15 minutes after they are issued.

## How clients use it

Every call needs a signed-in session.

```bash
# 1. Start: returns challengeCode, expiresAt and actionUrl; open actionUrl.
curl -sS https://<api-host>/auth.v1.SocialVerificationService/StartSocialVerification \
  -H 'Authorization: Bearer <session>' -H 'Content-Type: application/json' \
  -d '{"provider": "TELEGRAM"}'
# 2. Poll until status is STATUS_AWAITING_CONFIRMATION, then show handle,
#    displayName and providerUserId and ask the user to confirm.
curl -sS https://<api-host>/auth.v1.SocialVerificationService/GetSocialVerification \
  -H 'Authorization: Bearer <session>' -H 'Content-Type: application/json' \
  -d '{"provider": "TELEGRAM"}'
# 3. Complete an MFA challenge for fresh step-up, then confirm exactly the
#    account shown, with the step-up token.
curl -sS https://<api-host>/auth.v1.SocialVerificationService/ConfirmSocialVerification \
  -H 'Authorization: Bearer <session>' -H 'X-Auth-Step-Up: <step-up token>' \
  -H 'Content-Type: application/json' \
  -d '{"provider": "TELEGRAM", "providerUserId": "7654321098"}'
# Unlink, or cancel a link in progress; repeating it changes nothing.
curl -sS https://<api-host>/auth.v1.SocialVerificationService/UnlinkSocialAccount \
  -H 'Authorization: Bearer <session>' -H 'Content-Type: application/json' \
  -d '{"provider": "TELEGRAM"}'
```

REST: `POST /v1/auth/social/verification:start`, `GET
/v1/auth/social/verification?provider=TELEGRAM`, `POST
/v1/auth/social/verification:confirm` and `POST /v1/auth/social/verification:unlink`
take the same JSON bodies. REST status values drop the `STATUS_` prefix.

Errors:

- `ConfirmSocialVerification`: `AUTH_MFA_NOT_ENROLLED` (enroll MFA first),
  `AUTH_STEP_UP_REQUIRED` or `AUTH_STEP_UP_PROOF_UNAVAILABLE` (complete a new
  fresh step-up and retry), `AUTH_RESOURCE_NOT_FOUND` (no verification),
  `AUTH_SOCIAL_VERIFICATION_EXPIRED` (start again),
  `AUTH_SOCIAL_VERIFICATION_INVALID_STATE` (no submitted account awaits
  confirmation, or `provider_user_id` is not the one that submitted the code) and
  `AUTH_SOCIAL_ACCOUNT_ALREADY_LINKED` (that Telegram account is linked to another
  Polyester account; the verification fails). The checks that need no proof
  (missing, expired or mismatched verification) answer before the MFA checks,
  and a retried confirmation of an existing link needs no new proof.
- `StartSocialVerification` for Telegram answers
  `AUTH_SOCIAL_VERIFICATION_INVALID_STATE` while a Telegram account is linked:
  unlink it first.
- `SocialVerificationReady` is not used for Telegram and answers
  `AUTH_SOCIAL_VERIFICATION_INVALID_STATE`.

## Migration

None: the provider, status, fields and methods are new, and existing providers
behave as before.
