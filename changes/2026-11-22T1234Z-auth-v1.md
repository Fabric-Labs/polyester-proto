## What and why

Creating a sub-account can now be retried safely. `CreateSubaccountRequest` gains an optional `idempotency_key`: 1 to 128 letters, digits, `.`, `_`, `:` or `-`, unique within the root account and never reused, even after its sub-account is deleted.

- **The identical request again:** the same challenge `message`, `label`, `icon` and `color`, for the same smart account address and with a valid signature, under the same key, returns the sub-account the first request created with `replayed` set to `true`. It consumes no challenge, and this holds even where the request would otherwise fail with `AUTH_SMART_ACCOUNT_ALREADY_LINKED`.
- **The identical request after the sub-account was deleted** fails with `NOT_FOUND` and `AUTH_RESOURCE_NOT_FOUND`. It never returns the deleted sub-account and never creates a new one. The key stays used.
- **Any other request under that key** fails with `ALREADY_EXISTS` and the new `AuthErrorCode` `AUTH_SUBACCOUNT_IDEMPOTENCY_CONFLICT` (77, HTTP 409). It creates nothing, and the response never carries the existing sub-account. A resent or stale signed challenge therefore never creates a second sub-account.

`CreateSubaccountResponse` gains `replayed`: `true` when the response describes the sub-account an earlier identical request created, `false` when this call created it. A replay returns the sub-account's current `revision`.

**Compatibility with the earlier, unpublished name.** Earlier unpublished builds called these `client_request_id` and `AUTH_SUBACCOUNT_CLIENT_REQUEST_ID_CONFLICT`. Fields 9 and 17 and error value 77 keep their numbers, so binary protobuf clients are unaffected. JSON clients (REST and ConnectRPC JSON) see the new names: `idempotency_key` (`idempotencyKey` in ConnectRPC JSON) and `AUTH_SUBACCOUNT_IDEMPOTENCY_CONFLICT`.

`Subaccount` gains `idempotency_key`: the key of the request that created the sub-account, or empty when it had none. `ListSubaccounts` and `GetSubaccount` return it to the sub-account's owner on an interactive session only. Real-time updates omit it.

## How clients use it

Send the key with the create:

```http
POST /v1/auth/subaccounts
{"smart_account_address": "0x…", "message": "<challenge message>", "signature": "0x…", "label": "Bot", "idempotency_key": "deploy-1842"}
```

The ConnectRPC path is `/auth.v1.SubaccountService/CreateSubaccount`.

**Reading the response:** `replayed: false` means this call created the sub-account. `replayed: true` means an earlier request under the same key had already created it: the response describes that sub-account, and nothing new was created and no challenge was used. Treat both as success and keep the `subaccount_id`.

**After a lost response:**
1. **Resend the identical request**, same challenge and same key. This returns the sub-account, with `replayed: true`, if the first request created one. `NOT_FOUND` with `AUTH_RESOURCE_NOT_FOUND` means it did, but the sub-account has since been deleted: don't retry under that key; use a new key and a new challenge if you want a new sub-account.
2. **On `AUTH_SUBACCOUNT_IDEMPOTENCY_CONFLICT`**, call `ListSubaccounts` (`GET /v1/auth/subaccounts`) and take the sub-account whose `idempotency_key` is yours. This is what happens after you request a new challenge: once a sub-account is created, the next challenge names the next smart account address, so a request carrying it conflicts.
3. **When no sub-account carries the key,** don't conclude the first request created nothing. The list can lag a just-committed create, and it leaves out deleted sub-accounts, whose keys stay used. Retry the create with a new challenge under the same key: it either creates the sub-account or answers the conflict again, in which case list again, after a short wait. It never creates a second one.

## Migration

None. The field is optional. Clients that don't send it see no change.
