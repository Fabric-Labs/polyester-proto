## What and why

When the exchange cancels a ladder's levels while it recovers the user's
account, and none of them filled, the ladder now ends `STATUS_COMPLETED` with
nothing executed and no cancel reason. Before, it ended `STATUS_CANCELED` with
`TRIGGER_CANCEL_REASON_USER_REQUEST`, although the user canceled nothing. Each
level's own order still says `ACCOUNT_REPAIR`.

An attached take-profit or stop-loss whose working exit order the exchange
cancels the same way now stays active and protects the position again, as it
does after any other system cancel of its exit. Before, it ended
`STATUS_CANCELED` with a user request reason, as if the user had canceled that
exit.

Cancels by the user, a cancel-all and the dead man's switch the user set are
unchanged: a ladder they drain with nothing filled ends `STATUS_CANCELED`
with a user request reason, and an attached leg whose exit they cancel ends
the same way.

The comment on `TriggerStatus.STATUS_CANCELED` says so. No field, enum value
or method changed.

## How clients use it

Nothing new to call. Read the trigger's status and reason from the trigger
reads, the trigger history and the private stream, as for any trigger:

```bash
curl -sS https://<api-host>/triggers.v1.TriggersService/GetTrigger \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer <token>' \
  -d '{"triggerId": "1234567890123456789"}'
# A ladder whose levels the exchange canceled during an account recovery,
# none filled: {"trigger": {"type": "LADDER", "status": "STATUS_COMPLETED",
#   "ladderState": {"executedLevels": 0, ...}, ...}}
```

## Migration

None: the contract's shape is unchanged. A client that needs to know why a
ladder's levels ended reads each level's own order status and reason.
