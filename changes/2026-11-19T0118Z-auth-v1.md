## What and why

`auth.v1.AccountScopeType` moves from `auth/v1/address_book.proto` to its own
file, `auth/v1/account_scope.proto`. Its name, package, values and numbers
stay the same: `SCOPE_UNSPECIFIED = 0`, `SCOPE_ROOT = 1`,
`SCOPE_SUBACCOUNT = 2`.

`MeResponse.api_key_scope` uses this enum, so `auth/v1/auth.proto` imported the
whole address book file, and with it sub-accounts, policies, API keys and
ledger reads. Generated descriptors load every import at runtime, so a client
that only used `AuthService` loaded all of them. It now loads only the auth
files plus the small enum file. A browser client that calls only `Me` is
about 20 KB smaller after gzip.

## How clients use it

Requests and responses are unchanged, in binary and in JSON.

```http
POST /auth.v1.AuthService/Me
{}
-> {"accountId": "<main account id>", "apiKeyId": "ak_...", "apiKeyScope": "SCOPE_SUBACCOUNT", "subaccountId": "<sub-account id>"}
```

The address book messages (`AccountScopeRef.scope_type` and the
`target_scope_type` fields) keep the same enum, with the same values.

## Migration

Wire and JSON are unchanged, and so is the enum's full name,
`auth.v1.AccountScopeType`. Two kinds of code change: code that imports the
enum from the generated address book module, and code that looks the enum up
in the address book file's descriptor. The enum is no longer in
`auth/v1/address_book.proto`'s descriptor, so a lookup there finds nothing.

1. TypeScript: import `AccountScopeType` and `AccountScopeTypeSchema` from
   `auth/v1/account_scope_pb` instead of `auth/v1/address_book_pb`:

   ```ts
   // before
   import { AccountScopeType, AccountScopeTypeSchema } from "@polyester/sdk/unstable/gen/auth/v1/address_book_pb";
   // after
   import { AccountScopeType, AccountScopeTypeSchema } from "@polyester/sdk/unstable/gen/auth/v1/account_scope_pb";
   ```

   For a descriptor lookup, use `file_auth_v1_account_scope` from the same
   module instead of `file_auth_v1_address_book`, or look the enum up by its
   full name, for example `registry.getEnum("auth.v1.AccountScopeType")`.

2. Python: import the enum and its module-level `SCOPE_*` constants from
   `auth.v1.account_scope_pb2` instead of `auth.v1.address_book_pb2`:

   ```python
   # before
   from polyester.gen.auth.v1.address_book_pb2 import AccountScopeType, SCOPE_ROOT
   # after
   from polyester.gen.auth.v1.account_scope_pb2 import AccountScopeType, SCOPE_ROOT
   ```

   For a descriptor lookup, use
   `account_scope_pb2.DESCRIPTOR.enum_types_by_name["AccountScopeType"]`, or
   look it up by full name:
   `descriptor_pool.Default().FindEnumTypeByName("auth.v1.AccountScopeType")`.

3. Go: references such as `authv1.AccountScopeType_SCOPE_ROOT` are
   unchanged. Code that looks the enum up in the address book file's descriptor
   changes:

   ```go
   // before: nil after this change
   authv1.File_auth_v1_address_book_proto.Enums().ByName("AccountScopeType")
   // after: the enum's own file
   authv1.File_auth_v1_account_scope_proto.Enums().ByName("AccountScopeType")
   // or by full name
   protoregistry.GlobalTypes.FindEnumByName("auth.v1.AccountScopeType")
   ```

   `AccountScopeType_SCOPE_ROOT.Descriptor().ParentFile().Path()` is now
   `auth/v1/account_scope.proto`.

4. Rust and other languages: enum references in the `auth.v1` package are
   unchanged. Any descriptor lookup by file must use
   `auth/v1/account_scope.proto`, or look the enum up by its full name,
   `auth.v1.AccountScopeType`.
