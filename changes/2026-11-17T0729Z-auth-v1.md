## What and why

`Me` now tells an API key which account it is scoped to. `MeResponse` gains
`api_key_scope` (`SCOPE_ROOT` for a key of the main account,
`SCOPE_SUBACCOUNT` for a key bound to one sub-account) and `subaccount_id`,
the bound sub-account's ID, present only for a sub-account key. A
sub-account key's private realtime channels and account reads name that
sub-account, so a client no longer has to configure the ID by hand: before,
`Me` returned only the main account's ID, and subscribing to that account's
channels with a sub-account key is refused.

Both fields are empty when the request was authenticated with a session
rather than an API key.

## How clients use it

Call `Me` with the API key, then build channel names from the answer.

```http
GET /v1/auth/me
-> {"accountId": "<main account id>", "apiKeyId": "ak_...", "apiKeyScope": "SUBACCOUNT", "subaccountId": "<sub-account id>"}
```

ConnectRPC: `/auth.v1.AuthService/Me` with `{}` returns `apiKeyScope`
`SCOPE_SUBACCOUNT` and `subaccountId`. A sub-account key then subscribes to
`private:ledger:balances:<subaccountId>` (and the other private channels of
that sub-account); a main-account key (`apiKeyScope` `ROOT` in REST,
`SCOPE_ROOT` in ConnectRPC) uses `accountId`.

## Migration

None: the fields are new and optional. Clients that configured a
sub-account ID for a sub-account key can read it from `Me` instead.
