## What and why

A `BatchReplaceOrders` item is answered when it is admitted. If the item is
then refused when it applies, a client had no event naming it and could not
settle that item. Now:

- The trading WebSocket sends one `BatchReplaceItemReject` (SBE template 32,
  tradews `semanticVersion` 2.7.0, schema version unchanged) for each
  admitted item refused when it applied. It names the batch
  (`batchRequestId`) and the order (`orderId`), with the order's `version`
  (null when the order had already ended), the successor of a refused
  replacement (`replacementOrderId`, null for an in-place amend) and the
  reason `code`. The item changed nothing: the order is as it was, at its old
  price, quantity and client order ID unless it had ended, and a refused
  replacement's successor never exists as an order. On the connection that sent the batch it follows the batch's
  `BatchReplaceAck`; on the account's other connections, and before the
  response of a batch sent through `OrdersService.BatchReplaceOrders`, it can
  arrive first. A code there always means the item was admitted, then
  refused: a refusal at admission is reported in the batch's answer alone.
- An admitted item that amends or replaces its order and has not applied 2
  seconds after its admission is refused with the new
  `ERROR_CODE_MODIFY_APPLY_EXPIRED` (319), so no admitted item applies later.
- For 60 seconds from the batch's acceptance, `GetOrder` of a refused
  replacement's successor answers `REJECTED` with the same code, at version 1:
  its order ID, `batch_request_id`, the batch's admission as its created time,
  and its own lineage at generation 1. It has no terminal time; the refusal's
  own time is its `BatchReplaceItemReject`'s `eventTsNs`. It carries no order
  terms: REST omits `symbol`, `side`, `orderType`, `tif`, `stpMode` and
  `feeAsset` (Connect leaves them unset), and reports `price`, `origQty` and the
  other quantities as `"0"` placeholders. Take its terms from the batch you
  sent. After that window it is not found. A successor that is not found
  while the order it would have replaced is not `CANCELED` with
  `CANCEL_REASON_REPLACED` never becomes an order: the item was refused, or it
  applied by ending that order at its filled quantity, which that order's
  `CANCEL_REASON_QTY_AT_OR_BELOW_FILLED` shows unless a later change of yours
  ended it so.

## How clients use it

Settle an admitted batch item by `(batchRequestId, orderId)` when its
`BatchReplaceItemReject` arrives; the item changed nothing of the order, and
never track `replacementOrderId` as an order. Subscribe to the `orders` channel to
receive it.

```text
BatchReplaceItemReject { symbolId: 1, orderId: 2001504781434687192, version: 2,
  batchRequestId: <BatchReplaceAck.batchRequestId>, replacementOrderId: null,
  code: MODIFY_APPLY_EXPIRED, eventTsNs, gatewayTsNs }
```

```http
POST /orders.v1.OrdersReadService/GetOrder
{"orderId": "<a refused replacement's successor>"}
→ {"order": {"status": "REJECTED", "rejectReason": "ERROR_CODE_POST_ONLY_CROSS", "version": 1, ...}}
```

The same holds for `GET /v1/spot/orders/{order_id}`.

## Migration

None for the wire: the template is additive and the schema version is
unchanged. An SBE client must skip a template it does not know: one that
fails its session on an unknown template must update before the server
sends `BatchReplaceItemReject`.

In the REST order responses (`GET /v1/spot/orders/{order_id}`, open orders and
order history), `symbol`, `side`, `orderType`, `tif`, `stpMode` and `feeAsset`
are now optional: every order still carries them, except a refused
replacement read through `GetOrder`. A typed REST client generated from the
OpenAPI sees these properties become optional; Connect and protobuf types are
unchanged, and the six fields read unset there for a refused replacement.
