## What and why

`triggers.v1.TriggersService.CancelAllTriggers` cancels, in one request, every trigger of the account that matches a list of symbols, a side and a list of trigger types, and cancels no order. It is meant for a per-table "Cancel all" on trigger views (take-profit and stop-loss, trailing, TWAP, ladder), which previously had to list the triggers and cancel them in batches of 50.

It gives the same guarantees as `OrdersService.CancelAllOrders` with `include_triggers`: what it cancels is fixed when its `request_id` is first accepted (triggers created later keep running), each matching trigger ends canceled with reason `TRIGGER_CANCEL_REASON_CANCEL_ALL` and releases its reserved funds, none places an order after the response, and a dry run returns the count without canceling. A TWAP's working slice, a ladder's open levels and an attached leg's working exit are canceled with their trigger; an order a stop already placed stays open.

`trigger_types` matches the type `ListTriggers` reports. An order's attached take-profit, stop-loss and trailing legs end together, and so do an OCO's two legs: when any of them matches, all of them are canceled and counted.

While a cancel of triggers (this method, or `CancelAllOrders` with `include_triggers`) is ending an order's attached legs, a modify of that order that adds or changes an attached take-profit, stop-loss or trailing leg is rejected with the retryable `ERROR_CODE_ORDER_MODIFY_IN_PROGRESS`; retry it once the legs have ended. A leg added after a cancel-all was accepted is therefore never canceled by it.

The documentation of `CancelAllOrdersRequest`, `CancelAllAfterRequest`, `DeadManSwitchScope`, `TriggersService.CancelTrigger` and `CreateOco` no longer says that cancel-all and the dead-man switch never cancel triggers; it names `include_triggers` and points at `CancelAllTriggers`. That documentation fix changes no behavior; the changes to `CancelAllOrders` retry charging and to modifies of an order whose legs are being cancelled are described above and below.

## How clients use it

ConnectRPC `POST /triggers.v1.TriggersService/CancelAllTriggers`:

```json
{
  "symbolIds": [1, 2],
  "side": "SELL",
  "triggerTypes": ["STOP_LOSS", "TAKE_PROFIT"],
  "dryRun": false,
  "requestId": "ui-tpsl-cancel-all-7f3a"
}
```

REST `POST /v1/triggers/cancel-all` takes symbols by name:

```json
{
  "symbols": ["BTC-USDT"],
  "triggerTypes": ["TWAP"],
  "requestId": "ui-twap-cancel-all-7f3b"
}
```

The answer is `status` (`SUBMITTED` or `DRY_RUN`), `matchedTriggers`, `ts` and `tsNs`; it lists no trigger IDs, so refresh the trigger list afterwards.

- `symbol_ids` (REST `symbols`): at most 100; empty matches every symbol.
- `side`: unset matches both sides; a trigger matches the side its orders trade on.
- `trigger_types`: at most 5 distinct types; empty matches every type.
- `request_id`: required, 1 to 64 characters of `[A-Za-z0-9._:/-]`. A retry with the same key and criteria within two minutes returns the original count and cancels nothing again; the same key with other criteria is rejected with `ERROR_CODE_CONFLICT_IDEMPOTENCY_KEY_REUSE`. It is a separate key space from `CancelAllOrders`.
- Rate limit: every request counts 10 units of the cancel limit, however many triggers it cancels, a dry run and a retry included. The same now holds for `OrdersService.CancelAllOrders`: a retry with the same `request_id` always counts 10, wherever it is sent, and returns the original result.
- An unknown outcome (`ERROR_CODE_ORDER_CANCEL_OUTCOME_UNKNOWN`): retry with the same `request_id`.
- Delegated sessions: a connected app may call it as it may call `CancelTrigger`, `BatchCancelTriggers` and `CancelAllOrders`, with a scope that covers canceling; the `account:read` scope does not.

## Migration

None: the method is new. Clients that cancel a trigger table with `ListTriggers` and `BatchCancelTriggers` can replace that loop with one `CancelAllTriggers`, using `dry_run` for a confirmation count.
