## What and why

REST authentication refusals for internal transfers, deposit addresses, trading withdrawals, account reads and reward awards now include the canonical problem `type`. Responses use `application/problem+json` and the service's normal `title`, `status`, `detail` and `code` fields, so clients can handle early authentication failures like other REST failures. Internal-transfer, deposit-address, withdrawal and account-read authentication refusals retain HTTP 401, their authentication code and empty message. Reward-award refusals retain HTTP 401 and the message `unauthenticated`, now represented by code `AUTH_AUTHENTICATION_REQUIRED`. Realtime token authorization refusals also include the normal problem fields while retaining their code and HTTP status.

## How clients use it

Calls and authentication requirements are unchanged. For example, an anonymous request to the REST internal-transfer endpoint receives HTTP 401:

```http
POST /v1/trading/internal-transfers HTTP/1.1
Host: <api-host>
Content-Type: application/json

{}
```

The response now includes `"code":"UNAUTHENTICATED"` and `"type":"https://polyester.dev/problems/unauthenticated"`, with an empty `detail`. The corresponding ConnectRPC method remains `/transfer.v1.InternalTransferService/CreateInternalTransfer`; this note concerns REST error bodies, not successful transfer responses or request formats.

## Migration

None: `type` and the other problem metadata are additive. Clients may use `type` to identify a refusal or continue matching `code`. Accept `application/problem+json` when decoding REST errors. Reward-award REST clients can read `detail` for the existing `unauthenticated` message instead of treating the body as plain text.
