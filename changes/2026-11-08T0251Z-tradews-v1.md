## What and why

The SBE trading WebSocket gets the receive window the signed Orders API and
the protobuf WebSocket already have: a command names when it was sent and
how long it may wait, and one that arrives, or waits to be sent on for
admission, past its window is refused with `REQUEST_DEADLINE_EXCEEDED`
instead of being processed late. The window is now also enforced at
admission itself: a signed Orders API request, or a WebSocket command, whose
window ends while it waits to be admitted is refused the same way and
changes nothing.

**Breaking for SBE clients:** `tradews.xml` (schema 7) moves from version 36
to **41** and `semanticVersion` from 1.2.0 to **2.0.0**. Trading WebSocket
readers check the schema version exactly, so a client encoding version 36 is
refused (`BAD_SBE`, unexpected SBE schema version) until it regenerates its
codecs from the version 41 schema.

- New fields, appended to the fixed block of every command (`CreateOrder`,
  `CancelOrder`, `ModifyOrder`, `CancelAllOrders`, `BatchCreateOrders`,
  `BatchReplaceOrders`, `BatchCancelOrders`, `CancelAllAfter`):
  - `timestampMs` (`ZeroNullUint64`, Unix milliseconds, UTC): zero sets no
    window, as before.
  - `recvWindowMs` (`ZeroNullUint32`, milliseconds, 1 to 60000): zero uses
    5000.
- The command is processed only until `timestampMs + recvWindowMs`. Past
  then it is answered `CommandReject` with `RejectCode`
  **`REQUEST_DEADLINE_EXCEEDED` = 308** (the public `ErrorCode` 308); it
  changed nothing, and it has taken its `seq`.
- A `timestampMs` more than 1 second ahead of the server clock, a
  `recvWindowMs` above 60000, or a `recvWindowMs` without a `timestampMs` is
  answered `BAD_REQUEST` and takes no `seq`.
- New `RejectCode` value `REQUEST_DEADLINE_EXCEEDED = 308`.
- The six timed templates of semanticVersion 1.2.0 are removed:
  `CreateOrderTimed` (11), `CancelOrderTimed` (12), `ModifyOrderTimed` (13),
  `BatchCreateOrdersTimed` (14), `BatchReplaceOrdersTimed` (15) and
  `BatchCancelOrdersTimed` (16). The base commands carry the same window, so
  a frame with template 11 to 16 is refused `BAD_SBE`.
- No other message changes. `Ping` and `Subscribe` carry no window.
- The Orders API and the protobuf WebSocket contracts do not change; their
  window is now also enforced at admission, with the same
  `REQUEST_DEADLINE_EXCEEDED` (308) answer, nothing changed.

## How clients use it

An SBE `CancelOrder` that must not be processed more than 2 seconds after it
was sent:

```text
CancelOrder { seq: 7, correlationId: 7001, orderId: 0, symbolId: 9,
              timestampMs: 1762560000123, recvWindowMs: 2000,
              clientOrderId: "c-1" }
```

Leave both fields zero to send a command without a window, exactly as with
version 36.

## Migration

For SBE trading WebSocket clients, in the release that ships version 41:

1. Regenerate the SBE codecs from the version 41 `tradews.xml`. Every
   command's fixed block grows by 12 bytes, so version 36 encoders are
   refused.
2. Set `timestampMs` and `recvWindowMs` to zero to keep today's behavior
   (no window), or to the send time and a window from 1 to 60000 ms.
3. Handle `RejectCode` 308 `REQUEST_DEADLINE_EXCEEDED`: nothing changed;
   send the command again with a fresh `timestampMs` and the next `seq`.
4. A client that sends the timed templates 11 to 16 sends their base
   commands (2, 3, 4, 7, 8 and 9) instead, with the same `timestampMs` and
   `recvWindowMs`. `timestampMs` becomes a `ZeroNullUint64`.

Protobuf WebSocket and Orders API clients need no change.
