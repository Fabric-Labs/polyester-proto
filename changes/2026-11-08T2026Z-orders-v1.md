## What and why

Orders that cancel-on-disconnect cancels now carry their own cancel reason,
`CANCEL_REASON_CANCEL_ON_DISCONNECT = 21` (`CancelReason` in
`orders/v1/orders_read.proto`), instead of `CANCEL_REASON_CANCEL_ALL_AFTER`.
A client can now tell an order its own cancel-all-after timer cancelled from
one cancelled because its opted-in trading WebSocket sessions all
disconnected and none opted in again within its grace period. The trading
WebSocket's SBE `CancelReason` gains the same value, `CANCEL_ON_DISCONNECT =
21`, and the REST views read `CANCEL_ON_DISCONNECT`.

An order the account's own cancel-all-after timer cancels (`CancelAllAfter`
on the Orders API or on the WebSocket) still ends `CANCEL_ALL_AFTER`. If
both timers fire close together, an order both would cancel reads either
reason. Cancel-on-disconnect's scope is unchanged: the whole
account the API key is bound to. This supersedes the cancel reason that
`2026-11-07T2213Z-tradews-v1.md` names for cancel-on-disconnect.

## How clients use it

Read the reason wherever an order's cancel reason appears: order reads and
order history (`/orders.v1.OrdersReadService/GetOrder` and
`GetOrderHistory`, and their REST views), private order events, and the
trading WebSocket's order events.

```json
{"status": "ORDER_STATUS_CANCELED", "cancelReason": "CANCEL_REASON_CANCEL_ON_DISCONNECT"}
```

On the SBE trading WebSocket, `OrderEvent.cancelReason` is
`CANCEL_ON_DISCONNECT` (21).

## Migration

None for the wire: the value is additive. A client that treated
`CANCEL_ALL_AFTER` as "my session disconnected" should also handle
`CANCEL_ON_DISCONNECT`, and an exhaustive switch over `CancelReason` needs
the new case. An unknown value should be handled as a venue cancel, as
before.
