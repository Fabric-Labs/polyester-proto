## What and why

The auth REST endpoints now refuse a malformed request the same way every
time. A path ID that is not a valid base58 public ID, a blank path ID, a
malformed query parameter or a body that is not valid JSON is answered
`400 application/problem+json` with `code` `AUTH_INVALID_REQUEST`, and the
`detail` names the parameter, for example `invalid tag_id`. Before, some of
these answered `400 text/plain` with no `code`, depending on which check
failed: `DELETE /v1/auth/address-book-tags/1` answered plain text while
`/v1/auth/address-book-tags/2` answered problem JSON.

The API reference also documents public-ID path parameters with IDs in the
form the API returns, such as `AAo8yKqygTg`, instead of `2`, and the PATCH
endpoints that take a resource ID in the path now show one in their examples.

## How clients use it

Nothing changes for well-formed requests. A malformed one returns:

```http
DELETE /v1/auth/address-book-tags/1

HTTP/1.1 400 Bad Request
Content-Type: application/problem+json

{"type":"https://polyester.dev/problems/auth-invalid-request","title":"Invalid Request","status":400,"detail":"invalid tag_id","code":"AUTH_INVALID_REQUEST"}
```

ConnectRPC calls are unchanged.

## Migration

None: the status stays 400. Clients that handled these refusals as plain text
can now read `code` and `detail` from the problem body like any other auth
error.
