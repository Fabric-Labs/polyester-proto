## What and why

An HTTP 429 that a service itself returns now reaches the client unchanged.
This applies to the public wallet sign-in calls (`/v1/auth/wallet-challenge`,
`/v1/auth/login/wallet`, `/auth.v1.AuthService/CreateWalletChallenge`,
`/auth.v1.AuthService/LoginWithWallet`) and to the public catalog calls
(subaccount roles, VIP tiers, rate-limit configuration, changelog). Until now
the gateway replaced every 429 on these calls with its own body,
`{"code":"resource_exhausted","message":"rate limit exceeded, retry later"}`,
and its own `Retry-After`. The real refusal was lost: the per-wallet quota
state, a refusal that is not a rate limit at all (no new account can be
created), and the service's retry time.

The gateway's own per-address refusal is unchanged: HTTP 429,
`Content-Type: application/json` and the body above. When the address used up
its request count for the window, the refusal also carries `X-RateLimit-*` and
`Retry-After`, set to the seconds until the window resets; a refusal for too
many concurrent requests carries neither. No protobuf message or RPC changes.

## How clients use it

A 429 from these calls now has one of two origins.

The service refused the request. The body is the service's typed error, with
the service's own headers. A quota refusal carries `Retry-After` and
`RateLimit-*`; the other refusals below need not. Over REST, a wallet sign-in
that exhausts the wallet's or the address's quota returns:

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/problem+json
RateLimit-Limit: 30
RateLimit-Remaining: 0
RateLimit-Reset: 2
Retry-After: 2

{"code":"RATE_LIMIT_EXCEEDED","detail":"Rate limit exceeded","rate_limit":{"reason":"QUOTA_EXCEEDED","limit":"30","remaining":"0","retry_after_ms":"1409","policy_version":"5","operation_id":"auth.wallet_challenge","policy_class":"AUTH_PUBLIC","scope":"AUTH_SUBJECT","refill_model":"CONTINUOUS"},"status":429,"title":"Rate limit exceeded","type":"https://polyester.dev/problems/rate-limit-exceeded"}
```

Over ConnectRPC, for example `/auth.v1.AuthService/CreateWalletChallenge`,
the same refusal is `resource_exhausted` carrying a
`polyester.ratelimit.v1.RateLimitDetail` in `details`, with the same headers:

```json
{"code":"resource_exhausted","message":"rate limit exceeded","details":[{"type":"polyester.ratelimit.v1.RateLimitDetail","value":"<base64 RateLimitDetail>"}]}
```

A sign-in that cannot
create a new account is `resource_exhausted` with its own message over
ConnectRPC, and the `AUTH_RESOURCE_EXHAUSTED` problem over REST. A ConnectRPC
request body over the size limit is `resource_exhausted` with a size message.
Neither is a rate limit, and neither needs to carry `Retry-After` or
`RateLimit-*`.

The gateway refused the request. The body is
`{"code":"resource_exhausted","message":"rate limit exceeded, retry later"}`
with no `details`, as before.

## Migration

Clients that treated every 429 on these calls as the gateway body must read
the body they receive:

1. Over REST, branch on the problem `code`: `RATE_LIMIT_EXCEEDED` is a quota
   refusal and carries `rate_limit`; `AUTH_RESOURCE_EXHAUSTED` is a capacity
   refusal that waiting does not resolve. A JSON body with
   `code: resource_exhausted` is the gateway's own refusal.
2. Over ConnectRPC, keep handling `resource_exhausted`, and read the
   `RateLimitDetail` in `details` when present.
3. Before retrying a quota refusal, wait for the response's `Retry-After`
   when it has one.

Clients that only check the HTTP status or the ConnectRPC code keep working.
