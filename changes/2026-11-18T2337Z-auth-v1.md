## What and why

No field, message or enum value changes. The documentation now matches what
the API sends, and one REST answer changes, which REST clients of admin API
keys must follow:

- REST problem codes of `AuthErrorCode` values are the full enum name. The
  documentation of the assistant-key registration errors
  (`AUTH_ASSISTANT_KEY_PROOF_INVALID`, `AUTH_ASSISTANT_KEY_REGISTRATION_EXPIRED`,
  `AUTH_ASSISTANT_KEY_DEADLINE_TOO_FAR`), the social account limits
  (`AUTH_SOCIAL_ACCOUNT_COOLDOWN`, `AUTH_SOCIAL_CHANGE_LIMIT_REACHED`) and the
  admin-key errors (`AUTH_ADMIN_KEY_REQUIRED`, `AUTH_ADMIN_KEY_ESCALATION_DENIED`,
  `AUTH_ADMIN_KEY_SCOPE_EXCEEDED`, `AUTH_ADMIN_KEY_FORBIDDEN_TARGET`,
  `AUTH_ADMIN_KEY_ALLOWLIST_INVALID`, `AUTH_ADMIN_KEY_ACTION_NOT_ALLOWED`) named
  them without the `AUTH_` prefix. The HTTP statuses were already right.
- API key request refusals keep their short REST codes, such as
  `IP_NOT_ALLOWED`, `KEY_DISABLED` and `KEY_EXPIRED` (HTTP 401). Over
  ConnectRPC the same refusal is `unauthenticated` with `AUTH_IP_NOT_ALLOWED`,
  `AUTH_KEY_DISABLED` or `AUTH_KEY_EXPIRED` in the `AuthErrorDetail`. An admin
  key call can also be refused when it is processed, just after its key's
  allowlist was narrowed or the key was disabled or expired. On REST that
  refusal answered the long `AUTH_` code with another title and problem
  type; it now answers the same short code, title and type as every other
  API key refusal (see Migration). ConnectRPC answers are unchanged.
- `CancelAllOrdersRequest.include_triggers` also stops standalone OCOs (both
  legs). With it, a cancel-all, or the cancel-all-after expiry, ends both legs
  of every matching OCO canceled with `TRIGGER_CANCEL_REASON_CANCEL_ALL`.
  Without it, an OCO keeps running; only an OCO leg's working order that the
  cancel-all cancels ends the OCO. The trade WebSocket's `CreateOco` and
  `includeTriggers` descriptions say the same.

## How clients use it

Match REST problems on the documented code:

```text
POST /v1/auth/api-keys            -> 401 {"code":"IP_NOT_ALLOWED", ...}
POST /auth.v1.ApiKeyService/CreateApiKey
  -> unauthenticated, AuthErrorDetail.code = AUTH_IP_NOT_ALLOWED

POST /v1/orders/cancel-all
{"requestId": "stop-1", "includeTriggers": true}
```

The second call requests cancellation of every matching order and stops the
matching triggers, standalone OCOs included. `matched_orders` counts the
matching orders and `matched_triggers` the matching triggers. A requested
order cancellation is not a final state: an order can execute before its
cancellation takes effect, and `failed_cancels` counts orders whose
cancellation could not be submitted, so follow order updates for each
order's outcome.

## Migration

REST clients of admin API keys must update how they match these refusals.
When an admin key call to the API key or policy endpoints is refused as it is
processed, the REST problem now carries the short code, as every other API
key refusal already did:

| Refusal | Old REST `code` / `title` / `type` | New REST `code` / `title` / `type` |
| --- | --- | --- |
| Source address outside the key's allowlist | `AUTH_IP_NOT_ALLOWED` / `IP Not Allowed` / `https://polyester.dev/problems/auth-ip-not-allowed` | `IP_NOT_ALLOWED` / `API Key IP Not Allowed` / `https://polyester.dev/problems/ip-not-allowed` |
| Key disabled or revoked | `AUTH_KEY_DISABLED` / `Key Disabled` / `https://polyester.dev/problems/auth-key-disabled` | `KEY_DISABLED` / `API Key Disabled` / `https://polyester.dev/problems/key-disabled` |
| Key expired | `AUTH_KEY_EXPIRED` / `Key Expired` / `https://polyester.dev/problems/auth-key-expired` | `KEY_EXPIRED` / `API Key Expired` / `https://polyester.dev/problems/key-expired` |

1. Match the new codes (or problem types) wherever the old ones were matched.
   A client that already handles the short codes for its other API key
   requests needs no new branch.
2. Nothing else changes: the HTTP status stays 401, the `detail` text is the
   same, and ConnectRPC still answers `unauthenticated` with
   `AUTH_IP_NOT_ALLOWED`, `AUTH_KEY_DISABLED` or `AUTH_KEY_EXPIRED` in the
   `AuthErrorDetail`.

The other corrections are documentation only. A REST client that matched the
admin-key, assistant-key or social codes without the `AUTH_` prefix never
matched; match the full names, which the API has always sent.
