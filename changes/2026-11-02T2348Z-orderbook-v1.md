## What and why

The REST order book now always sends the fields its published schema
requires. A market whose book is still being built, or was invalidated, used
to answer without `ts`, for example right after a market opens. It now sends
`ts: 0` with `available: false`, `bookSeq: "0"` and empty `asks` and `bids`.

The REST `ts` field is now documented as 0 while `available` is false.

ConnectRPC `GetOrderBook` is unchanged.

## How clients use it

REST, `GET /v1/orderbook/{symbol}` with an optional `depth` query parameter
(levels per side: 1, 5, 10, 20, 50, 100, 200, 500 or 1000; default 50):

```bash
curl -sS 'https://<api-host>/v1/orderbook/BTC-USDT?depth=50'
# A book still being built:
# {"symbol":"BTC-USDT","bookSeq":"0","available":false,"ts":0,"asks":[],"bids":[]}
```

Bids are ordered best price first (descending) and asks best price first
(ascending). Each level is a `[price, quantity]` tuple of decimal strings,
`bookSeq` is a decimal string, and `ts` is the snapshot time in Unix epoch
milliseconds. Read `available` before using the levels or `ts`: while it is
false the book's levels are unknown, not empty, and `ts` is 0. Request the
snapshot again later.

ConnectRPC, unchanged, JSON over POST to
`/orderbook.v1.OrderbookService/GetOrderBook`, with the numeric pair ID from
`GetSpotConfig` and the `Depth` enum (`DEPTH_UNSPECIFIED` means 50):

```bash
curl -sS -X POST 'https://<api-host>/orderbook.v1.OrderbookService/GetOrderBook' \
  -H 'Content-Type: application/json' \
  -d '{"symbolId":7,"depth":"DEPTH_50"}'
# A book still being built, default fields omitted:
# {"symbolId":7}
```

ConnectRPC levels carry scaled integers (`priceTicks` scaled by 1e9,
`qtyScaled` by the pair's base quantity scale) and `ts` is a protobuf
timestamp, unset while `available` is false.

## Migration

None: the response now matches the published schema. Clients that tested
whether `ts` was present, rather than whether `available` is true, now always
find it.
