## What and why

A main account had no place to read its own security history: the only
activity read, `SubaccountViewService.ListSubaccountActivity`, covers one
sub-account, and the main account's own events (sign-ins, API keys, MFA,
saved destinations, profile) belong to no sub-account. This change adds:

- `auth.v1.AccountActivityService.ListAccountActivity`: one feed, newest
  first, of the main account's events and every sub-account's, with filters
  by account (sub-accounts and the main account), entity kind, action,
  client channel, acting API key and time range.
- Sign-in history: a successful wallet sign-in records a
  `ACTIVITY_ENTITY_SESSION` / `ACTIVITY_ACTION_CREATED` event, and a refused
  one an `ACTIVITY_ACTION_FAILED` event, with the public client IP, the user
  agent, and a payload naming the method and the signing wallet address.
- Two `ActivityEvent` fields: `subaccount_id` (absent for the main account's
  own events) and `actor_api_key_id` (the API key the actor used, absent for
  a session; set by `ListAccountActivity`).
- The API-key account permission `PolicyAction.READ_ACCOUNT_ACTIVITY` (42),
  which opens `ListAccountActivity` and nothing else.

## How clients use it

ConnectRPC, with a session token or a signed API-key request:

```bash
curl -sS https://<api-host>/auth.v1.AccountActivityService/ListAccountActivity \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer <session-token>' \
  -d '{"limit": 50}'
```

Filters, all optional; an omitted filter matches everything the caller may
read:

```json
{
  "subaccountIds": ["<subaccount id>"],
  "includeMainAccount": true,
  "entityKinds": ["ACTIVITY_ENTITY_SESSION", "ACTIVITY_ENTITY_API_KEY"],
  "eventActions": ["ACTIVITY_ACTION_FAILED"],
  "sources": ["ACTIVITY_SOURCE_WEB"],
  "apiKeyId": "<api key id>",
  "startTime": "2026-11-01T00:00:00Z",
  "endTime": "2026-11-18T00:00:00Z",
  "pageToken": "<next_page_token>"
}
```

- `subaccount_ids` (at most 100) and `include_main_account` together select
  the accounts the feed covers: `include_main_account` alone is the main
  account only; neither covers the whole account.
- `start_time` is inclusive and `end_time` exclusive.
- `limit` defaults to 50, maximum 200. `next_page_token` is empty when no
  more results exist; reuse it only with the same filters and caller, or the
  call fails with `InvalidArgument`.

REST: `GET /v1/auth/activity?limit=50&includeMainAccount=true&entityKinds=SESSION&pageToken=...`.
Repeated filters repeat their parameter (`subaccountIds=<id>&subaccountIds=<id>`),
enum filters take the REST value names without the enum prefix (`SESSION`,
`CREATED`, `WEB`, as REST responses spell them), times are RFC 3339, and IDs are base58 as in
every REST body.

Authorization: the main account's own session reads the whole account. An
API key needs `READ_ACCOUNT_ACTIVITY` on its policy; a key scoped to a
sub-account reads only that sub-account's events and is refused
`include_main_account` with `PermissionDenied`. A sub-account outside the
caller's main account fails with `NotFound`.

## Migration

None: the service, the fields and the enum value are new, and
`ListSubaccountActivity` keeps its behavior. An API key that should read the
account feed needs `READ_ACCOUNT_ACTIVITY` added to its policy;
`READ_SUBACCOUNT_ACTIVITY` does not open it.
