## What and why

**Availability:** assistant keys are devnet only. `SetAssistantKeys` registers
a new assistant key only with the Polyester AI assistant's registration proof,
and the assistant runs on devnet only, so the presets below can be used on
devnet only. Mark them devnet-only in the SDK docs, like the other assistant
key fields.

Setting up the Polyester AI assistant now takes exactly one step-up MFA
confirmation. Before, a user who had no suitable API policy had to create one
first with `CreateApiPolicy`, which needs its own fresh step-up proof, so a
first-time set-up cost one confirmation per new policy plus one for the keys.

- New enum `AssistantKeyPreset`: `PRESET_UNSPECIFIED` (0), `READ_ONLY` (1) and
  `TRADE_WITH_APPROVAL` (2), a fixed permission set each:
  - `READ_ONLY`: read actions only: `READ_BALANCES`, `READ_SPOT`,
    `READ_INTERNAL_TRANSFERS`, `READ_AUTO_WITHDRAW`, `READ_API_KEYS`,
    `READ_SUBACCOUNTS` and `READ_DEPOSIT_ADDRESSES`; on the main account also
    `READ_PRICE_ALERTS`.
  - `TRADE_WITH_APPROVAL`: `READ_ONLY` plus `TRADE_SPOT`, `SWAP` and
    `CREATE_DEPOSIT_ADDRESS`; on the main account also `MANAGE_PRICE_ALERTS`.
    The assistant runs each trade or swap only after the user approves it.
  - No preset ever allows a money-out action (`EXTERNAL_WITHDRAW`,
    `INTERNAL_TRANSFER`, `MANAGE_ADDRESS_BOOK`, `MANAGE_AUTO_WITHDRAW`), API-key
    or policy management, or anything that weakens account security.
  - The presets will gain more read actions as the API adds them: a preset's
    contents can grow, so show the preset by name and read its policy's
    actions instead of hard-coding them.
- `AssistantKeySpec` gains `preset` (6). Each entry sets exactly one of
  `policy_id` and `preset`; `policy_id` is no longer required on its own.
- With `preset`, `SetAssistantKeys` binds the key to the preset's API policy in
  the key's main account, in the same all-or-nothing change and under the same
  single step-up proof: the existing policy with the preset's name and exactly
  its actions over all markets, or else a new one. Policies are named
  "Polyester AI - Read only (main account)", "Polyester AI - Read only
  (sub-account)", "Polyester AI - Trade with approval (main account)" and
  "Polyester AI - Trade with approval (sub-account)". A shared sub-account's
  preset policy belongs to its owner, like the key.
- The returned `ApiKey.policy_id` names the preset's policy. It is an ordinary
  API policy: `ListApiPolicies` and `GetApiPolicy` show it, and changing it
  later with `UpdateApiPolicy` needs a fresh step-up proof, as before.
- An entry with both or neither of `policy_id` and `preset`, or an unknown
  preset, returns `InvalidArgument` with `AUTH_INVALID_REQUEST`. No new error
  code.

The `policy_id` path, the registration proof and deadline rules, and the
step-up rules are unchanged.

## How clients use it

```http
POST /auth.v1.ApiKeyService/SetAssistantKeys
Authorization: Bearer <session>
X-Auth-Step-Up: <step-up token>
Content-Type: application/json

{ "keys": [
    { "publicKeyEd25519": "<base64>", "preset": "TRADE_WITH_APPROVAL",
      "registrationProof": "<base64>", "registrationDeadline": "2026-11-12T09:05:00.123Z" },
    { "subaccountId": "9000000001", "publicKeyEd25519": "<base64>", "preset": "READ_ONLY",
      "registrationProof": "<base64>", "registrationDeadline": "2026-11-12T09:05:00.123Z" } ] }
```

REST: `PUT /v1/auth/assistant-keys` with the same body. Entries may mix
`policyId` and `preset`.

## Migration

None: `policy_id` entries behave as before, and `preset` is new.
