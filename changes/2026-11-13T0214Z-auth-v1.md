## What and why

API-key updates return the same complete metadata as a read at the resulting
revision, including the attached policy ID, Ed25519 public key and creator.
API-key creation timestamps retain their stored fractional seconds in reads
and lists, matching create and update responses. Private WebSocket ApiKey
updates carry the same precise `createdAt`.

## How clients use it

Update metadata, status or expiry with the current revision, then use the
returned `apiKey` directly. An attached policy appears as `policyId`; the
public key is `publicKeyEd25519` and the creator is `createdByActor`.

```http
POST /auth.v1.ApiKeyService/UpdateApiKey
Content-Type: application/json

{"keyId":"ak_0123456789abcdef0123456789abcdef","apiKey":{"label":"desk"},"updateMask":"label","expectedRevision":"4"}
```

The REST equivalent uses a strong revision ETag:

```http
PATCH /v1/auth/api-keys/ak_0123456789abcdef0123456789abcdef
Content-Type: application/json
If-Match: "4"

{"label":"desk"}
```

Read the same metadata through `POST /auth.v1.ApiKeyService/GetApiKey` with
`{"keyId":"ak_0123456789abcdef0123456789abcdef"}`, or
`GET /v1/auth/api-keys/ak_0123456789abcdef0123456789abcdef`.
For example, a stored creation time of `2026-11-12T16:48:15.912958Z` retains
those fractional seconds.

## Migration

None: existing fields and request formats are unchanged. Clients can replace
cached key metadata with the update response without a follow-up read. Preserve
fractional seconds when parsing or displaying `createdAt`.
