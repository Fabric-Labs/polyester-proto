## What and why

The Polyester AI assistant acts for a user only through API keys the user
creates for it, bounded by the user's API policies and sub-account policies.
A root-level key covers only the main account and a sub-account key covers
exactly its sub-account, so a user who enables the assistant gets one
assistant key per enabled account:

- `ApiKeyPurpose` is new: `STANDARD` (1) for the user's own keys and
  `ASSISTANT` (2) for the assistant's keys.
- `ApiKey` gains `purpose` (27). Every key listing and read carries it, so
  assistant keys are listed, labelled ("Polyester AI") and revoked like any
  key.
- New `SetAssistantKeys` creates or replaces the caller's whole assistant key
  set with one fresh step-up proof: one entry per account, each with the
  Ed25519 public key the assistant signs with and the API policy that bounds
  it. All keys change or none do. An entry whose account keeps the same public
  key keeps its key (and status) and takes the requested policy; a new public
  key replaces the account's key; an account left out loses its key.
- New `ListAssistantKeys` lists the caller's non-revoked assistant keys,
  newest first.
- New `DeleteAssistantKeys` revokes the whole set. It only removes access, so
  it needs no step-up proof. As for `DeleteApiKey`, key management sees the
  revocation at once, and requests signed with a revoked key are refused within
  a few seconds of the response; a request sent right after it may still be
  served.
- Only the person who set up an assistant key uses it, so
  `RemoveSubaccountMember` (including leaving) and `UpdateSubaccountMemberRole`
  to a role that cannot manage API keys revoke that member's assistant keys on
  the sub-account with the change. Ordinary keys stay with the sub-account.
- `AuthErrorCode` gains `AUTH_ASSISTANT_KEY_ACTION_NOT_ALLOWED` (59). An
  assistant key can never be allowed an action that moves value out of the
  account or manages where it goes: `EXTERNAL_WITHDRAW`, `INTERNAL_TRANSFER`,
  `MANAGE_ADDRESS_BOOK` or `MANAGE_AUTO_WITHDRAW`. `SetAssistantKeys`,
  `SetApiKeyPolicy`, `CreateApiPolicy` with `assign_to_key_id`, and
  `UpdateApiPolicy` on a policy an assistant key holds return
  `FailedPrecondition` with this code instead of granting one.

## How clients use it

Every call needs a signed-in session; API keys cannot call these methods.

```bash
# Complete an MFA challenge for fresh step-up, then set the whole set: the main
# account (no subaccountId) and one sub-account. publicKeyEd25519 is base64.
curl -sS https://<api-host>/auth.v1.ApiKeyService/SetAssistantKeys \
  -H 'Authorization: Bearer <session>' -H 'X-Auth-Step-Up: <step-up token>' \
  -H 'Content-Type: application/json' \
  -d '{"keys": [
        {"publicKeyEd25519": "11qYAYKxCrfVS/7TyWQHOg7hcvPapiMlrwIaaPcHURo=", "policyId": "<policy id>"},
        {"subaccountId": "<subaccount id>", "publicKeyEd25519": "PUAXw+hDiVqStwqnTRt+vJyYLM8uxJaMwM1V8Sr0Zgw=", "policyId": "<policy id>"}
      ]}'
# List the set.
curl -sS https://<api-host>/auth.v1.ApiKeyService/ListAssistantKeys \
  -H 'Authorization: Bearer <session>' -H 'Content-Type: application/json' -d '{}'
# Revoke the whole set: no step-up proof.
curl -sS https://<api-host>/auth.v1.ApiKeyService/DeleteAssistantKeys \
  -H 'Authorization: Bearer <session>' -H 'Content-Type: application/json' -d '{}'
```

REST: `PUT /v1/auth/assistant-keys` (same body), `GET /v1/auth/assistant-keys`
and `DELETE /v1/auth/assistant-keys`. REST purpose values are `STANDARD` and
`ASSISTANT`.

Limits and rules: 1 to 64 keys per call, at most one per account, each public
key exactly 32 bytes and distinct within the set. The policy must belong to the
main account that owns the key's account: for a sub-account shared with the
caller, a policy of the sub-account's owner. A sub-account entry needs the same
access as `CreateApiKey` (owner, or a role that manages API keys) on an active
sub-account. The response lists the set in request order.

Errors of `SetAssistantKeys`: `AUTH_INVALID_REQUEST` (malformed set),
`AUTH_TERMS_NOT_ACCEPTED`, `AUTH_MFA_NOT_ENROLLED`, `AUTH_STEP_UP_REQUIRED` or
`AUTH_STEP_UP_PROOF_UNAVAILABLE` (complete a new fresh step-up; a proof is
spent only by a successful call), `AUTH_SUBACCOUNT_ACCESS_DENIED`,
`AUTH_RESOURCE_NOT_FOUND`, `AUTH_POLICY_SCOPE_MISMATCH` and
`AUTH_ASSISTANT_KEY_ACTION_NOT_ALLOWED`.

## Migration

None: the methods, enum and error code are new. `purpose` is a new field;
existing keys read as `STANDARD`.
