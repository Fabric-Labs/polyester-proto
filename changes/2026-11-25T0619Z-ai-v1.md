## What and why

An approval whose run ends before the user decides it, for example because the
user stopped the run with `CancelRun`, is now reported as cancelled instead of
expired. Before, such an approval was reported `EXPIRED` even when its expiry
time was still ahead, so an app could only show "Expired" for an approval the
user had stopped.

- `ApprovalStatus` has a new value, `APPROVAL_CANCELLED` (5): the run ended
  before a decision, for example stopped by the user; the action did not run.
- When a run ends with approvals still pending, each one ends
  `APPROVAL_CANCELLED`, or `EXPIRED` when its expiry had already passed. The
  run reports each in an `ApprovalResolved` event before its `RunFailed`
  event. `EXPIRED` now always means the approval's expiry time was reached.
- `ErrorCode` has a new value, `APPROVAL_RUN_ENDED` (22): `DecideApproval` on
  an approval whose run ended before it was decided fails with
  `FAILED_PRECONDITION` and this code. Nothing was executed.
- Only a pending approval changes when its run ends with `RunFailed`
  (stopped with `CancelRun`, or failed). An
  approval already decided keeps its decision, and the run reports that
  decision: an approved action may already have been sent, so it is never
  reported cancelled. For a run that is stopped or fails, the
  `ApprovalResolved` event of each approval it had not reported yet carries
  the state `DecideApproval` reports for it.
- `ErrorDetail` has a new field, `pending_approval_id` (2), set with
  `RUN_ACTIVE` when the conversation's active run is waiting for the user's
  decision on an approval that is still pending and not past its expiry. A
  client can then point the user at that approval's Approve and Reject
  choices instead of showing a generic "busy" message. It is unset when the
  run is not waiting for a decision, including when the approval was just
  decided but the run has not reported it yet.

This is a deliberate breaking change before v1 (see Migration).

## How clients use it

Nothing new to call. The status arrives on the run's `ApprovalResolved` event
from the server-streaming `WatchRun` RPC
(`/ai.v1.AssistantService/WatchRun`), for example after `CancelRun`:

```json
{ "seq": "9", "approvalResolved": { "approvalId": "8934673421928245038", "status": "APPROVAL_CANCELLED" } }
{ "seq": "10", "runFailed": { "category": "CANCELLED", "message": "The run was cancelled." } }
```

Show such an approval as canceled, with nothing done, for example
"Canceled: nothing was done". A late `DecideApproval` on it,
`POST /ai.v1.AssistantService/DecideApproval` with
`{ "approvalId": "8934673421928245038", "decision": "APPROVE" }`, fails with
`FAILED_PRECONDITION` and an `ai.v1.ErrorDetail` whose `code` is
`APPROVAL_RUN_ENDED`.

A message sent while the run waits for a decision,
`POST /ai.v1.AssistantService/SendMessage` with
`{ "conversationId": "…", "text": "cancel it", "idempotencyKey": "…" }`, fails
with `FAILED_PRECONDITION` and an `ai.v1.ErrorDetail` such as
`{ "code": "RUN_ACTIVE", "pendingApprovalId": "8934673421928245038" }`: show
that approval's choices. Without `pendingApprovalId`, the run is busy
answering: offer to wait or to cancel it with `CancelRun`.

## Migration

This is breaking for JSON clients. Update your generated code to this
contract before an approval can end `APPROVAL_CANCELLED`:

- **JSON (ProtoJSON) clients** built on the previous contract cannot read the
  new value. A strict decoder rejects the whole `WatchRun` event or
  `ErrorDetail` that carries `"APPROVAL_CANCELLED"` or `"APPROVAL_RUN_ENDED"`.
  A decoder that ignores unknown fields reads the status as
  `APPROVAL_UNSPECIFIED`. Regenerate from this contract, then handle the new
  values.
- **Binary (protobuf) clients** built on the previous contract keep decoding
  every message. They receive the new values as unknown enum values (5 and
  22). Regenerate from this contract and handle `APPROVAL_CANCELLED` and
  `APPROVAL_RUN_ENDED` by name. Until then, an unknown `ApprovalStatus` is
  not proof that the action did not run: show its outcome as unknown (for
  example, point the user at their orders) rather than as "nothing was done".

- **Exhaustive switches over `ApprovalStatus`** (or over `ErrorCode`): after
  regenerating, a switch that the compiler checks for exhaustiveness (a
  TypeScript `never` check, a Rust `match`, a Swift or Kotlin `when`) no
  longer compiles until it handles `APPROVAL_CANCELLED` (and
  `APPROVAL_RUN_ENDED`). Code built on the previous contract reaches its
  default branch at run time, or its "unreachable" branch if it has one,
  which may throw. Give the new values their own branch rather than folding
  them into `EXPIRED`.

Then:

1. Show `APPROVAL_CANCELLED` as a final state of its own, for example
   "Canceled: nothing was done". Stop treating `EXPIRED` as the outcome of
   stopping a run: it now always means the approval's expiry time passed.
2. Handle the `DecideApproval` error `APPROVAL_RUN_ENDED` like
   `APPROVAL_EXPIRED`, with its own wording.
3. Optionally, on `RUN_ACTIVE`, read `ErrorDetail.pending_approval_id`: when
   set, point the user at that approval. Clients that ignore it keep working
   (a new field).
