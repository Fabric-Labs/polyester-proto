## What and why

The REST reference now describes what the API has always accepted and
answered, for the policy operations and a few others the same corrections
reach. No request or response changes on the wire.

- Creating a policy (`POST /v1/auth/policies/subaccounts`,
  `POST /v1/auth/policies/api-keys`): `policy.actions`,
  `policy.spotMarketScope` and `policy.spotMarkets` are optional. The
  reference listed all three as required, though a policy without them was
  always accepted.
- Every REST policy write documents the MFA its ConnectRPC operation
  requires (`x-poly-mfa-requirement`). Creating or deleting a policy of
  either kind, and updating an API-key policy, need a fresh step-up
  (`fresh_step_up`). Updating a sub-account policy, and attaching a policy
  to a sub-account or an API key, need it depending on the request
  (`conditional`).
- Deleting a policy (`DELETE /v1/auth/policies/subaccounts/{policy_id}`,
  `DELETE /v1/auth/policies/api-keys/{policy_id}`) answers the empty
  object, and the reference now says so instead of naming a response schema
  it did not contain. Updating a policy keeps its own PATCH body in the same
  way.
- The other REST operations state their MFA requirement too, as their
  ConnectRPC operations do; most need none. Two besides the policy writes
  are `conditional`: updating an API key (`PATCH /v1/auth/api-keys/{key_id}`)
  and updating an address-book entry
  (`PATCH /v1/auth/address-book-entries/{address_book_entry_id}`).
- Four QuickSwap broker operations no longer name response schemas the
  reference did not contain: removing a member, setting a member's role
  and transferring ownership answer the empty object, as documented now.
  Reading a broker's QuickSwap (`GET
  /v1/quickswap/brokers/{broker}/quickswaps/{swap_id}`) is also documented
  as the empty object, though it answers `{"quickSwap": ...}`; that
  description is corrected separately.

## How clients use it

Create a policy with only the fields it needs. Without `spotMarketScope` the
scope is `ALL`. Without `actions`, a sub-account policy keeps its mandatory
read-only actions and an API-key policy grants no access:

```text
POST /v1/auth/policies/subaccounts
X-Auth-Step-Up: <fresh step-up proof>
{"subaccountId":"<subaccount id>","policy":{"name":"Read only"}}
```

ConnectRPC: `POST /auth.v1.PolicyService/CreateSubaccountPolicy` with
`{"subaccountId":"<subaccount id>","policy":{"name":"Read only"}}`.

Creating a policy without a valid fresh step-up answers `403` with
`"code":"AUTH_STEP_UP_REQUIRED"`, as before. A `conditional` write answers
the same when its request needs the step-up.

## Migration

None: the API accepts and answers exactly as before. A client generated from
the previous REST reference that always sent `actions`, `spotMarketScope`
and `spotMarkets` keeps working.
