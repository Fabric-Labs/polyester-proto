## What and why

`auth.v1.PolicyAction` gains `READ_NOTIFICATIONS = 41`, a main-account
permission for API-key policies. It lets an API key scoped to the main account
list, read, and count that account's notifications, so programmatic clients
can read the notification center as the website does.

`notifications.v1.NotificationService` now accepts a signed API key, besides a
session token, on its three reads: `ListNotifications`, `GetNotification`, and
`GetNotificationCounts`. The key's policy must grant `READ_NOTIFICATIONS`, and
the key must be scoped to the main account. `MarkNotificationsRead`,
`MarkNotificationsUnread`, and `MarkAllNotificationsRead` still take a session
token only.

## How clients use it

Grant the permission on an API-key policy (`actions` replaces the policy's
whole action list, so send every action it keeps), then call the reads with
that key's signed headers.

```http
POST /auth.v1.PolicyService/UpdateApiPolicy
{"policyId": "<id>", "expectedRevision": "<rev>", "policy": {"actions": ["READ_NOTIFICATIONS"]}, "updateMask": "actions"}

POST /notifications.v1.NotificationService/ListNotifications
{"limit": 25}

POST /notifications.v1.NotificationService/GetNotificationCounts
{}
```

Refusals, all `PERMISSION_DENIED` with `AuthErrorDetail.code`
`AUTH_API_KEY_ACCESS_DENIED`:

- the key's policy does not grant `READ_NOTIFICATIONS`;
- the key is scoped to a sub-account, even when its policy grants it.

A mark call with any API key is refused with `PERMISSION_DENIED` and
`AUTH_SESSION_KIND_NOT_ALLOWED`. Paging, ordering, and filters are unchanged.

## Migration

None. The enum value and the API-key reads are additive; session callers see no
change.
