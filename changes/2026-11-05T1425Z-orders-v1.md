## What and why

When the gateway itself refuses a request for exceeding the per-address rate
limit, the HTTP 429 now carries the error that the caller's protocol decodes.
REST clients get the same rate-limit problem the services return.
ConnectRPC clients get a Connect `resource_exhausted` error. Before, REST
calls to wallet sign-in and the public catalog got the Connect-shaped JSON
error, and order and trigger writes got an HTML page with no `Retry-After`.
A ConnectRPC client read that HTML page as `unavailable`.

This covers order and trigger writes (`/v1/orders*`, `/v1/triggers*`,
`/orders.v1.OrdersService/*` and `/triggers.v1.TriggersService/*`), wallet
sign-in, and the public catalog calls (subaccount roles, VIP tiers, rate-limit configuration, changelog). A
429 that a service returns itself still reaches the client unchanged. No
protobuf message or RPC changes.

## How clients use it

A REST call refused by the gateway, for example the 31st
`POST https://<api-host>/v1/auth/wallet-challenge` from one address within a
minute, returns:

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/problem+json
X-RateLimit-Limit: 30
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 59
Retry-After: 59

{"code":"RATE_LIMIT_EXCEEDED","detail":"Rate limit exceeded","rate_limit":{"reason":"QUOTA_EXCEEDED","scope":"CLIENT_IP"},"status":429,"title":"Rate limit exceeded","type":"https://polyester.dev/problems/rate-limit-exceeded"}
```

`POST https://<api-host>/v1/orders` refused for too many concurrent requests
from one address returns the same body, without the `X-RateLimit-*` and
`Retry-After` headers.

The code and type are the same as a service's rate-limit problem. The
gateway's `rate_limit` carries only `reason` and `scope`: `scope: CLIENT_IP`
means the calling address used up the gateway's budget. A service's own
refusal also names the operation, the policy class and the remaining quota.

A ConnectRPC call refused by the gateway, for example
`/orders.v1.OrdersService/CreateOrder`, fails with `resource_exhausted`:

```json
{"code":"resource_exhausted","message":"rate limit exceeded, retry later"}
```

On both protocols, a refusal because the address used up its request count
for the window carries `X-RateLimit-*` and `Retry-After`, set to the seconds
until the window resets. A refusal for too many concurrent requests, or for
too many requests in one instant, carries neither.

## Migration

1. REST clients that parsed the gateway's 429 as `{"code":"resource_exhausted"}`
   JSON, or read an HTML body on order and trigger writes, must read the
   problem instead: branch on `code: RATE_LIMIT_EXCEEDED`, as for a service's
   rate-limit refusal.
2. ConnectRPC clients of order and trigger writes that handled the gateway's
   429 as `unavailable` must handle `resource_exhausted`.
3. Before retrying, wait for the response's `Retry-After` when it has one.

Clients that only check the HTTP status keep working.
