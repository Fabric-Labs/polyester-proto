## What and why

Accounts can now hold **admin API keys**: elevated keys that manage the
account's other API keys and its sub-accounts' policies by API, without a
signed-in session and a fresh step-up proof for every change. Market makers
can script the setup of many sub-accounts with them.

- `ApiKeyPurpose` gains `ADMIN_KEY`. `CreateApiKeyRequest.purpose` (field 8)
  creates an admin key, and `ApiKeyUpdateSpec.purpose` (field 7, update mask
  path `purpose`) promotes a standard key or demotes an admin key. Only the
  main account's owner may, in a signed-in session with a fresh step-up
  proof. An admin key acts for the main account, needs a non-empty IP
  allowlist with no entry broader than /24 (IPv4) or /48 (IPv6), and its
  policy can never allow a money-out action.
- `PolicyAction` gains three admin permissions, honored only for an admin
  key: `MANAGE_API_KEYS` (43), `MANAGE_API_KEY_POLICIES` (44) and
  `MANAGE_SUBACCOUNT_POLICIES` (45).
- Six calls now accept an admin key, each with its admin permission:
  `ApiKeyService.CreateApiKey`, `UpdateApiKey` and `DeleteApiKey`
  (`MANAGE_API_KEYS`); `PolicyService.SetApiKeyPolicy`
  (`MANAGE_API_KEY_POLICIES`); `PolicyService.SetSubaccountPolicy` and
  `UpdateSubaccountPolicy` (`MANAGE_SUBACCOUNT_POLICIES`). Their
  `mfa_requirement` is now `MFA_CONDITIONAL`: a session still needs a fresh
  step-up proof; an admin key needs none.
- What an admin key can never do: create, promote, change or revoke an admin
  key, including itself (its allowlist, purpose and policy change only in the
  owner's session); attach an admin permission; touch an assistant key, a key
  or policy that allows a money-out action (it may revoke such a key), a
  locked sub-account policy, or a sub-account the main account does not own.
  A key it creates or changes needs an IP allowlist inside the admin key's
  own, and a sub-account key's policy stays within the sub-account's policy.
- `AuthErrorCode` gains `AUTH_ADMIN_KEY_REQUIRED` (67),
  `AUTH_ADMIN_KEY_ESCALATION_DENIED` (68), `AUTH_ADMIN_KEY_SCOPE_EXCEEDED`
  (69), `AUTH_ADMIN_KEY_FORBIDDEN_TARGET` (70),
  `AUTH_ADMIN_KEY_ALLOWLIST_INVALID` (71) and
  `AUTH_ADMIN_KEY_ACTION_NOT_ALLOWED` (72).
- Every change an admin key makes notifies the main account:
  `NotificationType.ADMIN_KEY_ACTION` (category `SECURITY`) with the new
  detail `AdminKeyActionNotice` (`Notification.admin_key_action`, field 14)
  and the enum `AdminKeyAction`.

## How clients use it

The owner creates the admin key in a session with a fresh step-up proof:

```http
POST /auth.v1.ApiKeyService/CreateApiKey
Authorization: Bearer <session token>
X-Auth-Step-Up: <fresh step-up token>

{"label": "provisioning", "publicKeyEd25519": "<base64>",
 "ipWhitelist": ["203.0.113.0/24"], "purpose": "ADMIN_KEY"}
```

A script then signs requests with the admin key, as with any API key, from
an address in its allowlist:

```http
POST /auth.v1.ApiKeyService/CreateApiKey          (REST: POST /v1/auth/api-keys)
{"label": "maker 1", "subaccountId": "<id>", "publicKeyEd25519": "<base64>",
 "ipWhitelist": ["203.0.113.10/32"]}

POST /auth.v1.PolicyService/SetApiKeyPolicy       (REST: PATCH /v1/auth/api-keys/{key_id}/policy)
{"keyId": "ak_...", "policyId": "<api policy id>"}

POST /auth.v1.PolicyService/SetSubaccountPolicy   (REST: PATCH /v1/auth/subaccounts/{subaccount_id}/policy)
{"subaccountId": "<id>", "policyId": "<sub-account policy id>"}
```

Policies themselves are created in a session; an admin key attaches and
updates them. The calls share the account-security rate limit: 60 weight
units a minute with a burst of 20, CreateApiKey, UpdateApiKey and
DeleteApiKey weighing 5 each and the three policy calls 2 each.

## Migration

None: existing keys stay standard or assistant keys, and sessions call these
RPCs as before. Clients that switch on `ApiKeyPurpose`, `PolicyAction`,
`AuthErrorCode`, `NotificationType` or the `Notification.detail` oneof should
handle the new values; an unrecognized notification type still shows its
title and text.
