## What and why

REST order writes now treat request decimals the way ConnectRPC treats the
values they spell, on every order write route.

- Zeros beyond a decimal's scale no longer change the answer. A `baseQty` of
  `"1.500"` on a pair with base scale 2, or `"0.000100000"` at base scale 8,
  is the exact quantity it spells and is admitted like `"1.5"` or
  `"0.0001"`. A price such as `"70000.0000000000"` is the price `"70000"`.
  Before, any digit beyond the scale answered `400 INVALID_ARGUMENT` "too
  many fractional digits", even a zero.
- A decimal with a nonzero digit beyond its scale is off the pair's step or
  tick, whatever the pair. REST now answers it as ConnectRPC answers a value
  off the step or tick on the same route:
  - `POST /v1/orders/batch`: only that item is rejected, with `QTY_STEP_SIZE`
    or `PRICE_TICK_SIZE` and the item's violation, such as
    `items[0].baseQty`. The other items are admitted or rejected on their
    own. Before, the whole batch answered `400 INVALID_ARGUMENT`.
  - `POST /v1/orders/preview`: the preview answers `200` with
    `"admissible": false` and a `rejection` carrying `QTY_STEP_SIZE` or
    `PRICE_TICK_SIZE` and the violation, such as `order.baseQty`. Before, it
    answered `400 INVALID_ARGUMENT`.
  - `POST /v1/orders/modify`: `newPrice` or a tick-checked `newAttachedRisk`
    price answers `400 PRICE_TICK_SIZE` with the violation, such as
    `newPrice`. Before, `400 INVALID_ARGUMENT`.
  - `POST /v1/orders/replace-batch`: an item's `newPrice` or tick-checked
    `newAttachedRisk` price answers `400 PRICE_TICK_SIZE` for the request,
    with the item's violation, such as `items[1].newPrice`. Before,
    `400 INVALID_ARGUMENT`.
  - `POST /v1/orders`: unchanged for the quantity and the limit, trigger and
    activation prices (`QTY_STEP_SIZE` or `PRICE_TICK_SIZE`). An attached
    trailing stop's `limitPrice` now answers `PRICE_TICK_SIZE` as well, where
    it answered `INVALID_ARGUMENT`.

The tick-checked prices are the limit price of each execution, and the
attached take-profit and stop-loss trigger and child limit prices and the
trailing-stop activation and limit prices. Other decimals, such as
`maxQuoteDebit`, `clientRefPrice` and `trailingDistance`, keep answering
`INVALID_ARGUMENT` for a nonzero digit beyond their scale; zeros beyond it
parse on them too.

## How clients use it

Units: a REST `baseQty` is a decimal string in base-asset units with at most
the pair's base scale of fractional digits, and a REST price is a decimal
string in quote-asset units per base-asset unit with at most 9 fractional
digits. Zeros beyond those digits are allowed. ConnectRPC carries the same
values as scaled integers: `baseQtyScaled` in units of 10^-baseScale of the
base asset, and `priceTicks` in units of 10^-9. Batch create takes up to 20
items.

A batch with one quantity finer than the pair's base scale (8), on REST
(`POST /v1/orders/batch`):

```bash
curl -sS -X POST https://<api-host>/v1/orders/batch \
  -H 'Authorization: Bearer <token>' -H 'Content-Type: application/json' \
  -d '{"requestId":"b-1","items":[
        {"symbol":"BTC-USDT","side":"BUY","baseQty":"0.000100001","limitGtc":{"price":"70000"}},
        {"symbol":"BTC-USDT","side":"BUY","baseQty":"0.000100000","limitGtc":{"price":"70000"}}]}'
```

```json
{
  "results": [
    {
      "rejected": {
        "error": {
          "code": "QTY_STEP_SIZE",
          "violations": [
            {
              "fieldPath": "items[0].baseQty",
              "ruleId": "step_size",
              "message": "quantity does not align with the pair step size"
            }
          ]
        }
      }
    },
    { "accepted": { "orderId": "<order-id>" } }
  ]
}
```

The same quantity on `POST /v1/orders/preview` answers `200` (excerpt):

```json
{
  "admissible": false,
  "rejection": {
    "code": "QTY_STEP_SIZE",
    "violations": [
      {
        "fieldPath": "order.baseQty",
        "ruleId": "step_size",
        "message": "quantity does not align with the pair step size"
      }
    ]
  }
}
```

ConnectRPC cannot send that quantity: a scaled integer carries no digit
beyond the scale. It answers the same way for a quantity off the pair's step,
for example `baseQtyScaled` `"10001"` (0.00010001) on a pair stepping by
0.000001:

```bash
curl -sS -X POST https://<api-host>/orders.v1.OrdersService/BatchCreateOrders \
  -H 'Authorization: Bearer <token>' -H 'Content-Type: application/json' \
  -d '{"requestId":"b-1","items":[
        {"symbolId":1,"side":"BUY","baseQtyScaled":"10001","limitGtc":{"priceTicks":"70000000000000"}},
        {"symbolId":1,"side":"BUY","baseQtyScaled":"10000","limitGtc":{"priceTicks":"70000000000000"}}]}'
```

The first item is rejected with `ERROR_CODE_QTY_STEP_SIZE` and the violation
`{"fieldPath": "order.base_qty_scaled", "ruleId": "step_size"}`; the second
is admitted.

A rejected batch item keeps its result slot, so a retry with the same
`requestId` and the same body replays the same results; the same `requestId`
with a different body, including a different value of a rejected field,
conflicts as before.

## Migration

1. A REST client that sent zero-padded decimals and handled
   `INVALID_ARGUMENT` "too many fractional digits" for them needs no change:
   those requests are now admitted.
2. A REST client of `POST /v1/orders/batch` that treated `400
   INVALID_ARGUMENT` for a too-precise item as the whole batch failing must
   read the per-item results instead: the other items may have been
   admitted.
3. A REST client of `POST /v1/orders/preview` must read `admissible` and
   `rejection` for a too-precise quantity or price instead of a `400`.
4. A REST client of `POST /v1/orders/modify`, `POST /v1/orders/replace-batch`
   or an attached trailing stop's `limitPrice` that branched on
   `INVALID_ARGUMENT` for a too-precise price must branch on
   `PRICE_TICK_SIZE`.

ConnectRPC clients need no change: they send scaled integers, which carry no
digits beyond the scale.
