## What and why

`StartBacktest` has new defaults, so a backtest started with no window and
no balances runs a realistic test of the bot:

- **Starting balance:** without `initial_balances`, a backtest starts with
  1,000 of the bot's quote asset, for example 1000 USDT. It no longer starts
  with the bot's budget setting, which for a dollar-cost-averaging bot is
  the amount of each buy, so such a backtest could afford a single buy. The
  budget stays a setting the bot reads.
- **Window:** without `start_time`, the window is the most recent 365 days
  of data, ending where it ended before. A market with less data is used
  whole. Given bounds are unchanged.
- **Whole seconds:** a `start_time` or `end_time` with a fraction of a second
  is floored to the second. Such a backtest used to be accepted and then
  fail after its retries ran out; it now runs. A backtest the runner refuses
  as invalid fails at once with a message, instead of after its retries.
  That failure is kept with the backtest: starting the same backtest again,
  under any idempotency key, returns it while the backtest is kept, unless
  the request resolves differently (another window, balance or setting).
- **`BacktestReport.fidelity`** now names the starting balance, for example
  `starting balance 1000 USDT`, beside the other assumptions.
- **`initial_balances`** states its existing rule: an empty list means the
  same as leaving it out, and each amount must be more than 0
  (`FUNDING_INVALID` otherwise). Behaviour is unchanged.

A backtest's identity follows its effective request, as before. A call
that repeats an earlier idempotency key returns that key's backtest without
resolving anything again, so to start under the new defaults, use a new
key. Under a new key, a request that left the window or balances out
resolves to the new defaults: it starts a new backtest when those differ
from the earlier backtest's effective inputs, and returns the earlier
backtest when they come out the same (for example, a start or balance it
had given explicitly).

## How clients use it

Start a backtest with the defaults, or spell out the old ones:

```http
POST /strategies.v1.StrategiesService/StartBacktest
{"versionId": "sha256:...", "idempotencyKey": "bt-1"}

POST /strategies.v1.StrategiesService/StartBacktest
{"versionId": "sha256:...", "idempotencyKey": "bt-2",
 "startTime": "2024-01-01T00:00:00Z",
 "initialBalances": [{"asset": "USDT", "amount": "50"}]}
```

- Give `initialBalances` to test with another amount; give `startTime` for a
  longer window than 365 days.

## Migration

None: no field, message or RPC changes. A client that relied on the budget
as the starting balance, or on the longest window, gives them explicitly.
