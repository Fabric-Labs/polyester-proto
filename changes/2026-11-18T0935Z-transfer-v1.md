## What and why

`BATCH_REFUSED` from `BatchCreateInternalTransfers` is now final for its
idempotency key in every case, as the contract states. That includes a batch
refused because a leg failed its checks, for example an unsupported asset or
a destination that is not whitelisted. A retry under the same key with the
same legs returns the same `BATCH_REFUSED` answer, even once the leg would
pass. A retry with different legs under that key is refused with
`IDEMPOTENCY_CONFLICT`. Before, a retry after such a refusal was checked
again and could be accepted.

A check that cannot be decided right now is no longer reported as a refusal.
When a service the checks depend on is briefly unavailable, the whole request
fails with a retryable error: Connect code `unavailable` (REST `503`), error
code `SERVICE_UNAVAILABLE` or `ACCOUNT_SHARD_UNAVAILABLE`. Nothing is recorded
under the key, so a retry with the same key and legs is checked again. Before,
this answered `BATCH_REFUSED` with that error code on the leg.

No message, field or enum value changes.

## How clients use it

The request is unchanged:

```http
POST https://<api-host>/transfer.v1.InternalTransferService/BatchCreateInternalTransfers
Content-Type: application/json

{"idempotencyKey": "payroll-2026-11-18", "legs": [{"destinationSmartAccountAddress": "0x…", "assetId": 7, "amountE18": {"lo": "1000000000000000000"}}]}
```

REST: `POST https://<api-host>/v1/trading/internal-transfers/batch`.

Read the answer as follows:

- `BATCH_REFUSED`: nothing moved and nothing will under this key. The legs
  that caused it carry `error_code`. To try again, fix the cause and submit
  under a new idempotency key.
- A `503` / `unavailable` error: the batch was not decided. Retry with the
  same idempotency key and legs, after `Retry-After` when present.
- `BATCH_PROCESSING`: retry with the same key, or read the batch with
  `GetInternalTransferBatch`, to learn the outcome.

## Migration

1. Treat a `503` / `unavailable` answer from `BatchCreateInternalTransfers` as
   retryable under the same idempotency key, as for `CreateInternalTransfer`.
   Clients that read `SERVICE_UNAVAILABLE` or `ACCOUNT_SHARD_UNAVAILABLE` on a
   leg of a `BATCH_REFUSED` answer as a cue to retry will now get those codes
   as the request's error instead.
2. Do not resubmit a `BATCH_REFUSED` batch under the same key expecting a new
   decision: it returns the same refusal. Use a new key.
