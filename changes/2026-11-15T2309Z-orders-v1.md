## What and why

REST routes now answer a temporary failure with `503 Service Unavailable` instead of `502 Bad Gateway` or `504 Gateway Timeout`. A temporary failure is a dependency that is unavailable or too slow, a deadline, or a request body that could not be read. The `application/problem+json` body keeps the same `code`, and `Retry-After` where one applies.

A `502` or `504` never delivered that body: the public edge replaces either with its own plain-text page (`error code: 502`). Clients therefore got neither the problem document nor its `code` nor `Retry-After`.

The change covers orders, triggers and their reads, market data and the market overview, deposits, withdrawals and auto-withdraw rules, flows and chain analytics, internal transfers and dust conversions, QuickSwap and QuickSwap brokers, daily claims, statement exports, reward campaigns, and the account routes (API keys, MFA, policies, sub-accounts, profile).

`504` stays only where a write's outcome is unknown, because its deadline passed or its commit failed, and a retry could apply it twice:
- the orders and triggers `*_OUTCOME_UNKNOWN` codes, as before;
- creating an API key, an API-key policy or a sub-account policy;
- regenerating MFA recovery codes;
- creating or rotating a QuickSwap broker key;
- creating a whiteboard (`POST /v1/collab/whiteboards`).

ConnectRPC keeps `unavailable` and `deadline_exceeded` as before, with one correction: on the API key, policy, recovery-code, broker key and whiteboard writes above, a deadline or a failed commit now answers `deadline_exceeded`, where it answered `unavailable` or `internal`.

## How clients use it

Retry a `503` with backoff, honouring `Retry-After` when present. Reads are always safe to retry. Writes with an idempotency key are safe to retry with the same key.

```http
POST https://<api-host>/v1/trading/internal-transfers

HTTP/1.1 503 Service Unavailable
Content-Type: application/problem+json

{"type": "https://polyester.dev/problems/service-unavailable", "title": "Service Unavailable", "status": 503, "detail": "deadline", "code": "SERVICE_UNAVAILABLE"}
```

A `504` means the write may have been applied. Read it back (an order by its client order ID, the list of API keys, policies, broker keys or whiteboards) before sending it again.

## Migration

None required. Retry a `503` as you retry other temporary failures: most HTTP retry policies already do. A client that treated a `504` with code `deadline_exceeded` as an unknown outcome reads the same `code` at `503`. For those routes a retry with the same idempotency key is safe.
