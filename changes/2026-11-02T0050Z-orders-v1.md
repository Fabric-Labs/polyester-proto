## What and why

An attached trailing stop on a SELL order now declares the most its buy-back
may pay. `orders.v1.TrailingStopPolicy` has a new field
`limit_price_ticks = 4`: the maximum price of a trailing stop that buys back,
in quote units scaled by 1e9. The exchange reserves the quote that exit may
spend, with its fee, at that price, so the protection is fully funded. A rise
that fires above the maximum still fires, and the exit fills only at or below
it.

- **Required** when the parent order sells, because its trailing stop buys.
- **Must be unset** when the parent order buys, because its trailing stop
  sells.

Released in 9.2. Since 9.2, a SELL order with an attached trailing stop that
omits the field is rejected.

## How clients use it

The field sits in `attached_risk.trailing_stop` of the order intent:
`CreateOrder`, `PreviewOrder` and each `BatchCreateOrders` item. It also sits
in `new_attached_risk.trailing_stop` of `ModifyOrder` and of each
`BatchReplaceOrders` item. Changing it with `ModifyOrder` replaces the leg.

ConnectRPC: a SELL limit order with a trailing stop that buys back at
65000 at most. `limitPriceTicks` is a 1e9-scaled integer, sent as a JSON
string like every int64.

```bash
curl -sS https://<api-host>/orders.v1.OrdersService/CreateOrder \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer <token>' \
  -d '{"order": {"symbolId": 1, "side": "SELL", "baseQtyScaled": "100000000",
       "limitGtc": {"priceTicks": "70000000000000"},
       "attachedRisk": {"trailingStop": {
         "trailingDistanceBps": 150,
         "activationPriceTicks": "60000000000000",
         "limitPriceTicks": "65000000000000"}}}}'
```

REST: the same order. `limitPrice` is a decimal string in quote units per base
unit.

```bash
curl -sS -X POST https://<api-host>/v1/orders \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer <token>' \
  -d '{"order": {"symbol": "BTC-USDT", "side": "SELL", "baseQty": "1",
       "limitGtc": {"price": "70000"},
       "attachedRisk": {"trailingStop": {"trailingDistanceBps": 150,
         "activationPrice": "60000", "limitPrice": "65000"}}}}'
```

`baseQtyScaled` uses the pair's `base_quantity_scale` from `GetSpotConfig`;
the value above assumes a scale of 8.

The same REST field is `attachedRisk.trailingStop.limitPrice` on
`POST /v1/orders/preview` and on each `POST /v1/orders/batch` item. It is
`newAttachedRisk.trailingStop.limitPrice` on `POST /v1/orders/modify` and on
each `POST /v1/orders/replace-batch` item.

A negative value is refused first, with `ERROR_CODE_VALIDATION_ERROR` and a
field violation on `…trailing_stop.limit_price_ticks`, rule `positive`.

**Error codes in 9.2 and 9.2.1 only.** These releases refuse every other
mistake with no field violation:

| Mistake | Code in 9.2 and 9.2.1 |
| --- | --- |
| Set on a BUY parent | `ERROR_CODE_TRIGGER_PRICE_INVALID` |
| Missing on a SELL parent | `ERROR_CODE_TRIGGER_PRICE_INVALID` |
| Off the pair's price tick | `ERROR_CODE_PRICE_TICK_SIZE` |
| Below `activation_price_ticks` | `ERROR_CODE_TRIGGER_PRICE_INVALID` |

REST problem bodies carry the same codes without the `ERROR_CODE_` prefix.
The next release replaces these answers with specific codes and named field
violations. The note `2026-11-02T1812Z-orders-v1.md` holds the current
contract: `BAD_PRICE`, `TRIGGER_BUY_REQUIRES_LIMIT` and `PRICE_TICK_SIZE` on
create, preview and batch create, and `BAD_PRICE` from the side rule on
modify and batch replace. Use that note, not this table, for the current
answers.

Order reads (`GetOrder`, `GetOpenOrders`, `GetOrderHistory`) do not return
the field yet. Don't expect it in an order's attached risk.

## Migration

Clients that place SELL orders with an attached trailing stop must send the
maximum price, and must not send it on BUY parents; otherwise the order is
refused. No change for orders without a trailing stop. To detect these
refusals, match the codes in `2026-11-02T1812Z-orders-v1.md`;
`TRIGGER_PRICE_INVALID` covers them only on 9.2 and 9.2.1.
