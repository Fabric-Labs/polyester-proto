## What and why

`GetDeployProposal` is a new read of one deploy proposal, as its deploy page
shows it before the user approves it: the version, the bot's name, its money
card, every setting with its value, the funding subaccount and amounts, and
where the proposal is. The deploy link `ProposeDeploy` returns opens that
page, which until now had no call to load the proposal it names.

- The response carries the proposal's `summary`, as `ProposeDeploy` recorded
  it, and its `status`, the same `DeployStatus` `GetDeployStatus` returns.
- Only the account that recorded the proposal reads it. Another account's
  proposal is `NOT_FOUND` with `PROPOSAL_NOT_FOUND`, as an unknown one is.
- An API key needs `READ_STRATEGIES` and must be scoped to the main account,
  else `PERMISSION_DENIED` with `AUTH_API_KEY_ACCESS_DENIED`.

## How clients use it

```json
POST /strategies.v1.StrategiesService/GetDeployProposal
{"proposalId": "…"}

{"proposalId": "…",
 "summary": {"versionId": "sha256:…", "botName": "Weekly DCA",
             "moneyCard": {…}, "settings": [{"name": "budget", "value": "100"}],
             "fundingSubaccountId": "…",
             "funding": [{"asset": "USDT", "amount": "200"}], "scenariosPassed": 2},
 "status": {"proposalId": "…", "state": "PROPOSED", "expiresAt": "…"}}
```

- The call is declared `NO_SIDE_EFFECTS`; repeating it changes nothing. It
  has no REST route.
- `status.state` is `PROPOSED` until the proposal is deployed, or `EXPIRED`
  after 24 hours; poll `GetDeployStatus` to follow a deploy.

## Migration

None: the RPC is new.
