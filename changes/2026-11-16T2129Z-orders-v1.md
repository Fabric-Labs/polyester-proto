## What and why

Documentation only: no field, message or behavior changes. The order's
`fee_total` (REST `feeTotal`) now says when it is set and how a client gets
an ended order's fee.

- A fill's fee is recorded once the fill is settled, which can be seconds
  after the order ended.
- Order history reads and single-order reads with execution history (the
  default) carry the fee total of the fills recorded so far. Its quantity
  (`fee_total.qty_scaled`, REST `feeTotal.qty`) shows which fills it covers.
  It is the order's whole fee once that quantity equals the order's filled
  quantity (`cum_qty_scaled`, REST `cumQty`).
- Open-order reads, single-order reads without execution history and private
  WebSocket order updates never carry it, an ended order's update included.
  The private WebSocket's `Unit.orders` and `OrderEvent` documentation now
  says so.

## How clients use it

To show the fee of an order seen on the private WebSocket, or how much of
its quote amount a Market Buy sized by `submitted_max_quote_debit_scaled`
(REST `submittedMaxQuoteDebit`) used: when an update shows the order ended
with a filled quantity above zero, read the order by its ID. Read it again, a
few hundred milliseconds apart, until the fee total's quantity equals the
order's filled quantity.

```text
POST /orders.v1.OrdersReadService/GetOrder
{"orderId": "<the update's order_id>"}

GET /v1/spot/orders/{id}
```

Then, with the fee in QUOTE, the quote used is `cumQuote + feeTotal.amount`
(or minus it when `feeTotal.isRebate` is true). With the fee in BASE, it is
`cumQuote` alone. The unspent amount is `submittedMaxQuoteDebit` less the
quote used.

## Migration

None: no field or behavior changes. Clients that read `fee_total` from
private WebSocket order updates never received it; they should read the order
as described above.
