## What and why

`UserProfilePatch.twitter` is removed. An X/Twitter handle now appears on a
profile only through a successful X verification: the handle X reports for the
verified account, refreshed on each verification. `UserProfile.twitter` and
`twitter_verified` stay, read-only. `UpdateProfile` can no longer add, replace or
clear the X handle, and a request that names `twitter` is rejected as invalid.

A restarted X/Twitter or Discord verification no longer releases the linked
account. `SocialVerification.provider_user_id` and `verified_at` keep describing
the linked account while a new verification runs, and the newly verified account
replaces it only when that verification succeeds.

## How clients use it

Connect X with the social verification calls only, then read the profile:

```http
POST /auth.v1.SocialVerificationService/StartSocialVerification
{"provider": "TWITTER", "handle": "alice"}

POST /auth.v1.SocialVerificationService/SocialVerificationReady
{"provider": "TWITTER"}

POST /auth.v1.SocialVerificationService/GetSocialVerification
{"provider": "TWITTER"}
```

REST: `POST /v1/auth/social/verification:start`,
`POST /v1/auth/social/verification:ready`, `GET /v1/auth/social/verification`.
Once the status is `STATUS_VERIFIED`, `GetProfile` returns the verified handle in
`twitter` with `twitter_verified: true`.

## Migration

1. Stop sending `twitter` in `UpdateProfile` (`PATCH /v1/auth/profile`). A body
   with `twitter` now fails with `invalid_argument` (HTTP 400).
2. Show the X handle from `GetProfile` as read-only, and offer "Connect X"
   through `StartSocialVerification` and `SocialVerificationReady`.
3. While a new verification runs, keep showing the linked account from
   `GetProfile`; it changes only when the new verification succeeds.
