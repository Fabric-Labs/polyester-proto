## What and why

Oversized requests to balance, history, equity and transfer reads now return
the same HTTP 413 problem as every other REST service. The problem code changes
from `PAYLOAD_TOO_LARGE` to `REQUEST_TOO_LARGE`, its type from
`https://polyester.dev/problems/payload-too-large` to
`https://polyester.dev/problems/request-too-large`, and its title and detail
match the other services. The 1 MiB request limit and when it is enforced do
not change. No protobuf message or RPC changes.

## How clients use it

For example, a request to
`POST https://<api-host>/ledger.read.v1.LedgerReadService/GetBalances` with more
than 1 MiB of body data returns:

```http
HTTP/1.1 413 Request Entity Too Large
Content-Type: application/problem+json

{"type":"https://polyester.dev/problems/request-too-large","title":"Request Entity Too Large","status":413,"detail":"request too large","code":"REQUEST_TOO_LARGE"}
```

The size refusal still precedes authentication, for bearer-token and API-key
requests, and for known-length and chunked bodies. A smaller body must still
satisfy the endpoint's normal validation and authentication requirements.

## Migration

Clients that branch on `code: PAYLOAD_TOO_LARGE` or on the
`payload-too-large` problem type for these reads must branch on
`code: REQUEST_TOO_LARGE` instead. Keep status-based HTTP 413 handling and
reduce the body to fit the existing limit before sending another request.
Protobuf encoding and generated request and response types need no changes.
