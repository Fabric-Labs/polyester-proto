## What and why

REST `GET /v1/transfers` gains the optional query parameter `transferCode`,
which lists only transfers with that reason. ConnectRPC `ListTransfers`
already filters by `transfer_code`. Until now REST had no such filter and
ignored the parameter.

`transferCode` takes the same value a REST transfer row shows in its
`transferCode` field: the lower-case reason name, such as `deposit`,
`withdraw`, `maker_fee`, `internal_transfer` or `funding_to_trading`. The
reference lists every value. No other spelling is accepted: an unknown
value, including the upper-case enum name and an empty value, is refused
with HTTP 400 `BAD_REQUEST`, and the detail names the parameter and its
values.

## How clients use it

```http
GET /v1/transfers?transferCode=deposit&limit=100&reversed=true
-> 200 {"transfers": [{"transferCode": "deposit", ...}], "nextPageToken": "..."}

GET /v1/transfers?transferCode=DEPOSIT
-> 400 {"code": "BAD_REQUEST", "detail": "request_validation_failed: transferCode must be one of: deposit, withdraw, ..."}
```

The filter combines with `subaccountId`, `ledger`, `timestampMin`,
`timestampMax`, `limit` and `reversed`. A `nextPageToken` is bound to the
filter, so continue a filtered listing with the same `transferCode`.
Omitting `transferCode` lists every reason, as before. An explicitly empty
`transferCode=` names no reason and is refused with HTTP 400, like an
unknown value.

On ConnectRPC, keep sending the `transfer_code` enum:

```http
POST /ledger.read.v1.LedgerReadService/ListTransfers
{"transferCode": "DEPOSIT", "limit": 100}
```

## Migration

None: the parameter is new and optional. A client that already sent
`transferCode` on REST, which was ignored, now gets filtered rows, or 400 for
a value outside the list.
