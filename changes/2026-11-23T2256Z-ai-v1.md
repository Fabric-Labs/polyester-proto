## What and why

`OrderPreview` gains the `oco` kind (field 19, `OcoPreview`): the typed
preview of a standalone OCO, a take-profit and a stop-loss that both trade the
order's side for its whole quantity. A sell OCO sells base asset the account
already holds; a buy OCO buys the quantity with quote asset the account
already holds. Creating it reserves funds once for both legs: a sell reserves
the quantity of base asset, a buy the quote asset needed to buy the quantity.
The assistant can place such an OCO behind an approval card, and that card
now carries it as typed values like every other order type, so a client draws
both legs against the watched price instead of showing only the summary and
parameters.

`OcoPreview` has:

- `take_profit` and `stop_loss`, each an `OcoLegPreview`: `trigger_price`,
  `trigger_price_source` (`LAST_PRICE` or `INDEX_PRICE`), `direction`
  (`AT_OR_ABOVE` or `AT_OR_BELOW`, which way the watched price must move to
  fire the leg) and `limit_price`, the good-till-canceled exit price, omitted
  for a market exit.
- `reserved_asset`: the asset creating the OCO reserves once for both legs,
  the base asset for a sell and the quote asset for a buy.

On the enclosing `OrderPreview`, an OCO sets `symbol_id`, `symbol`,
`base_asset`, `quote_asset`, `side`, `quantity` and `reference_price` (the
price both legs watch). `reserved_amount` is set for a sell OCO and omitted
for a buy OCO, whose reserve the exchange sets when it creates it.
`estimated_value` is omitted for an OCO.

## How clients use it

Nothing new to call: the preview arrives on the run's `ApprovalRequested`
event, from the server-streaming `WatchRun` RPC, as `orderPreview` with its
`oco` kind set. Read the stream with a ConnectRPC client, which frames the
streamed messages; a plain JSON POST to a streaming method is refused. In
TypeScript, with code generated from `ai/v1/assistant.proto`:

```ts
import { createClient } from "@connectrpc/connect";
import { createConnectTransport } from "@connectrpc/connect-web";
import { AssistantService } from "./gen/ai/v1/assistant_pb";

const assistant = createClient(
  AssistantService,
  createConnectTransport({
    baseUrl: "https://<api-host>",
    interceptors: [
      (next) => (req) => {
        req.header.set("Authorization", "Bearer <session-token>");
        return next(req);
      },
    ],
  }),
);

for await (const { event } of assistant.watchRun({ runId: 1535956427583482916n })) {
  if (event?.event.case !== "approvalRequested") continue;
  const { preview } = event.event.value;
  if (preview.case === "orderPreview" && preview.value.kind.case === "oco") {
    const { takeProfit, stopLoss, reservedAsset } = preview.value.kind.value;
    console.log(takeProfit?.triggerPrice, stopLoss?.triggerPrice, reservedAsset);
  }
}
```

A sell OCO of 0.15 SOL with a take-profit at 90 and a stop-loss at 48, both
market exits, arrives as this event, shown in ProtoJSON (other fields of
`approvalRequested`, such as `summary` and `parameters`, left out):

```json
{

    "seq": "7",
    "approvalRequested": {
      "approvalId": "1535956427583482917",

        "symbolId": 3,

        "baseAsset": "SOL",
```

Prices and quantities are exact decimal strings, in the quote and base asset.
Approving the card places exactly this OCO; `DecideApproval` is unchanged.

## Migration

Update to an SDK generated from this contract before relying on the new kind.
How an older client handles an OCO approval depends on how it decodes events:

- A client decoding binary protobuf, or ProtoJSON with unknown fields
  ignored, keeps the event: the `oco` kind is left unset, and it shows the
  approval's summary and parameters, which state both legs.
- A client decoding ProtoJSON strictly with an older descriptor rejects the
  whole event (`key "oco" is unknown`), so it shows neither the card nor its
  summary. Update the SDK, or decode with unknown fields ignored.
