## What and why

The trading WebSocket now checks an order's attached take-profit, stop-loss
and trailing-stop values the way the Orders API does, before the order is
placed. This applies to protobuf frames (`tradews.v1.ClientFrame`) carrying
`CreateOrder`, `ModifyOrder`, `BatchCreateOrders` or `BatchReplaceOrders`.
The REST and ConnectRPC Orders API is unchanged: it already refused these
values with the same codes.

- **Before:** the socket passed every attached-leg value on. It treated a
  field's type minimum (`-9223372036854775808` for a 64-bit field,
  `-2147483648` for a 32-bit one) as if the field were unset, and still
  placed the order. A take-profit or stop-loss leg with that trigger price
  was dropped, and a trailing stop with that slippage cap exited without a
  cap. The exchange refused other invalid values after the frame was
  accepted, and some with another code: a slippage cap that was not
  positive answered `TRIGGER_PRICE_INVALID`.
- **Now:** the frame is refused with a `CommandReject` and nothing of it is
  placed or changed. In a `BatchCreateOrders` frame only the item with the
  invalid value is refused; the other items proceed.

| Field (under `attached_risk` or `new_attached_risk`) | Valid values | `CommandReject.code` |
| --- | --- | --- |
| `take_profit.trigger_price_ticks`, `stop_loss.trigger_price_ticks` | positive | `TRIGGER_PRICE_INVALID` |
| `take_profit.child.limit_gtc.price_ticks`, `stop_loss.child.limit_gtc.price_ticks` | positive | `BAD_PRICE` |
| `trailing_stop.trailing_distance_ticks` | positive | `TRAILING_DISTANCE_INVALID` |
| `trailing_stop.trailing_distance_bps` | 1 to 10000 | `TRAILING_DISTANCE_INVALID` |
| `trailing_stop.max_slippage_ticks` | positive | `SLIPPAGE_TICKS_INVALID` |
| `trailing_stop.max_slippage_bps` | 1 to 10000 | `SLIPPAGE_BPS_INVALID` when not positive, `MAX_SLIPPAGE_INVALID` above 10000 |
| `trailing_stop.activation_price_ticks` | 0 (none) or positive | `TRIGGER_ACTIVATION_PRICE_INVALID` |
| `trailing_stop.limit_price_ticks` | 0 (none) or positive | `VALIDATION_ERROR` |

These are the codes the Orders API answers for the same fields. No message,
field, enum value or code is added.

## How clients use it

Send attached legs with the values you intend. A trailing stop's
`activation_price_ticks` and `limit_price_ticks` take 0 for none. Its
slippage cap is a choice of `max_slippage_ticks` or `max_slippage_bps`:
omit both for no cap. Its distance is a choice of `trailing_distance_ticks`
or `trailing_distance_bps`, and one is required. A refused frame answers:

```text
ClientFrame { seq: 12, correlation_id: "c-12",
  create_order { order { symbol_id: 7, side: SELL, base_qty_scaled: 1000,
    limit_gtc { price_ticks: 42 },
    attached_risk { take_profit { trigger_price_ticks: -9223372036854775808,
      child { market_ioc {} } } } } } }

ServerFrame { seq: 12, correlation_id: "c-12",
  reject { code: "TRIGGER_PRICE_INVALID",
    detail: "take_profit.trigger_price_ticks: take-profit trigger price must be positive" } }
```

The `detail` names the refused field under the risk policy.

## Migration

A client that sends only valid attached-leg values needs no change. A client
that relied on a type-minimum value to mean "unset" must instead set
`activation_price_ticks` or `limit_price_ticks` to 0, leave the slippage cap
out, or leave the leg out; its frames are refused otherwise. Clients that
matched the account's later refusal of a non-positive slippage cap
(`TRIGGER_PRICE_INVALID`) or of a negative activation price (`TICK_SIZE`)
on the socket now receive the codes in the table, the same as on the
Orders API.
