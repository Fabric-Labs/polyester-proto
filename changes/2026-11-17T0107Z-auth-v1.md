## What and why

One MFA confirmation now covers a short series of related account changes. After a session
completes a fresh step-up, the same signed-in session has a recent-MFA window for 5 minutes. In
that window, three actions need no new step-up proof:

- confirming a Telegram link (`SocialVerificationService.ConfirmSocialVerification` for
  `TELEGRAM`);
- changing Polyester AI's account access (`ApiKeyService.SetAssistantKeys`, with policies or
  presets);
- raising or removing a Telegram approval limit (`ai.v1.AssistantService.SetTelegramApprovalLimits`).

Every other action that needs MFA, including withdrawals, transfers, API keys and policies outside
the assistant, and MFA settings, still needs a fresh, single-use proof each time.

Contract additions in `auth.v1`:

- enum `RecentMFAAction`: `RECENT_MFA_ACTION_TELEGRAM_LINK`, `RECENT_MFA_ACTION_ASSISTANT_ACCESS`
  and `RECENT_MFA_ACTION_TELEGRAM_APPROVAL_LIMITS`;
- `MFAService.GetRecentMFA(action)`, which returns `open` and `expires_at`;
- `MFAService.EndRecentMFA()`, which ends the window at sign-out, cancels the session's pending MFA
  challenges and revokes its unused step-up proofs, including one issued by a challenge completing
  at the same time (it answers once that completion has finished);
- `AuthErrorCode.AUTH_RECENT_MFA_EXPIRED = 66`, returned with PermissionDenied when the window has
  closed.

`ConfirmSocialVerification` and `SetAssistantKeys` are now documented as `MFA_RECENT`.

Behaviour change in `ai.v1`: `SetTelegramApprovalLimits` used to need no MFA. It now needs the
window (or a fresh step-up just before) when a limit is raised or turned off. Setting a new limit,
lowering one or keeping it still needs no MFA.

## How clients use it

Before an allowlisted action, check whether the session's window is open:

```http
POST /auth.v1.MFAService/GetRecentMFA
{"action": "RECENT_MFA_ACTION_ASSISTANT_ACCESS"}

200 {"open": true, "expiresAt": "2026-11-17T01:12:00Z"}
```

- `open: true`: send the action without the `X-Auth-Step-Up` header.
- `open: false`: complete an MFA challenge for fresh step-up (`BeginMFAChallenge` with
  `MFA_CHALLENGE_PURPOSE_FRESH_STEP_UP`). That step-up opens a new window. For
  `ConfirmSocialVerification` and `SetAssistantKeys`, send the step-up token in `X-Auth-Step-Up`,
  which spends it. `SetTelegramApprovalLimits` takes no step-up token: call it after the step-up,
  while the window it opened is open.

An allowlisted action without a proof while the window is closed returns PermissionDenied with
`AUTH_STEP_UP_REQUIRED` (no window in this session) or `AUTH_RECENT_MFA_EXPIRED` (the window has
closed). Complete a step-up and retry. `SetTelegramApprovalLimits` returns the same auth detail,
and ABORTED when the limits keep changing concurrently (read them and retry).

At sign-out:

```http
POST /auth.v1.MFAService/EndRecentMFA
{}
```

Both RPCs take a session token only. They have no REST route.

## Migration

- Clients that raise or remove Telegram approval limits must handle PermissionDenied with
  `AUTH_STEP_UP_REQUIRED` or `AUTH_RECENT_MFA_EXPIRED`: run a fresh step-up, then retry.
- Clients that already send a fresh step-up proof with `ConfirmSocialVerification` or
  `SetAssistantKeys` need no change. The proof is consumed as before.
- Treat unknown `AuthErrorCode` values as a generic auth failure, so code 66 does not break older
  clients.
