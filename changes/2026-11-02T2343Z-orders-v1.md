## What and why

A cancel of an order that has already ended is now always refused with
`ERROR_CODE_ORDER_ALREADY_TERMINAL`, including a repeat of a cancel that
ended the order. Before, a repeat sent within about 10 minutes of the first
cancel was answered `ACCEPTED` again, even when it named another market, and
no cancel confirmation or refusal ever followed it. The answer now says what
happened: the order is already done.

A cancel whose `symbol_id` (REST `symbol`) names another market than the
order's is refused `ERROR_CODE_ORDER_UNKNOWN` and cancels nothing, as before
for a live order. An order that ended a while ago may instead be reported
ended (`ERROR_CODE_ORDER_ALREADY_TERMINAL`).

A repeat sent while the first cancel is still in progress is still answered
`ACCEPTED` and changes nothing.

A client order ID keeps naming its order for at least a minute after the
order ends. A cancel by client order ID sent after that may be refused
`ERROR_CODE_ORDER_UNKNOWN` instead, once the ID no longer names the order;
before, such a repeat was answered `ACCEPTED` for about 10 minutes.

Every cancel request counts against the account's cancel rate limit, a
repeat of one that ended the order included. Before, such a repeat was
answered `ACCEPTED` without counting. With the cancel budget spent, a repeat
is refused `ERROR_CODE_RATE_LIMIT_EXCEEDED` like any other cancel.

## How clients use it

No request changes. ConnectRPC:

```bash
curl -sS https://<api-host>/orders.v1.OrdersService/CancelOrder \
  -H 'Content-Type: application/json' -d '{"orderId": "1234567890123456789"}'
# First cancel of a resting order:  {"status": "ACCEPTED", ...}
# The same cancel once the order has ended: an error whose ErrorDetail
#   code is ERROR_CODE_ORDER_ALREADY_TERMINAL
```

REST:

```bash
curl -sS -X POST 'https://<api-host>/v1/orders/cancel' \
  -H 'Content-Type: application/json' -d '{"orderId": "3sDK21t5nHJ"}'
# Once the order has ended: HTTP 400, "code": "ORDER_ALREADY_TERMINAL"
# Naming another market than the order's: HTTP 404, "code": "ORDER_UNKNOWN"
```

## Migration

A client that retries a cancel after a timeout, or sends it twice, may now
read `ORDER_ALREADY_TERMINAL` where it used to read `ACCEPTED`. Treat
`ORDER_ALREADY_TERMINAL` from a cancel as "already done": the order has
ended, by this cancel or otherwise (filled, expired, canceled). Read the
order (`GetOrder` or the private order stream) for how it ended. Clients
that already handle this code for filled or expired orders need no change.

A client that retries by client order ID more than a minute after the order
ended may read `ORDER_UNKNOWN`. A retry counts against the cancel rate limit;
on `RATE_LIMIT_EXCEEDED`, wait as the rate-limit answer says, or read the order,
before cancelling again. Cancel by order ID when you have it, or
read the order by client order ID before treating `ORDER_UNKNOWN` as an
error.
