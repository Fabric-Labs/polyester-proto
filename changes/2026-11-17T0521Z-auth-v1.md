## What and why

Clearer validation errors and a corrected REST reference. No field, message,
RPC or accepted value changes.

- **Missing required enums say "value is required".** 62 enum fields that
  must be set now carry the `required` validation rule instead of refusing
  the zero value as a forbidden list entry. Most are request fields, such as
  `timeframe` of `GetCandles`, or `interval`, `depth` and `quantity_mode` of
  `GetOrderbookHeatmap`; the others are fields of response messages, which
  always carry a defined value, so only their documentation changes. A request without one is refused as before, with
  `"validation error: timeframe: value is required"` instead of
  `"validation error: timeframe: must not be in list"`. The violation's rule
  ID is `required` instead of `enum.not_in`. Every other value is accepted or
  refused exactly as before. The ConnectRPC reference now lists these fields
  under `required` instead of a `not: {enum: [0]}` schema.
- **REST query errors name the parameter.** The REST market data endpoints
  answer a query parameter they cannot read with a `detail` that names it and
  says what it takes. For an enum, the detail lists the REST values: for
  example `"timeframe must be one of: 1s, 1m, 3m, ..."`,
  `"limit must be a non-negative integer"`,
  `"startTime must be an RFC 3339 date-time, such as 2026-01-02T15:04:05Z"` or
  `"side must be one of: BUY, SELL"`. Previously the detail was a generic
  "The request was malformed or missing required parameters." or
  "Bad request.". The status and `code` (`BAD_REQUEST`) are unchanged.
- **The REST reference is titled "Polyester API" 1.0.0**, the same title and
  version as the ConnectRPC reference, instead of an internal name.
- **The REST reference now documents the API key and sub-account policy
  operations.** These operations were already served but missing from the
  published REST reference:
  - `GET /v1/auth/policies/subaccounts`, `POST /v1/auth/policies/subaccounts`
  - `GET /v1/auth/policies/subaccounts/{policy_id}`,
    `DELETE /v1/auth/policies/subaccounts/{policy_id}`
  - `PATCH /v1/auth/subaccounts/{subaccount_id}/policy`
  - `GET /v1/auth/policies/api-keys`, `POST /v1/auth/policies/api-keys`
  - `GET /v1/auth/policies/api-keys/{policy_id}`,
    `DELETE /v1/auth/policies/api-keys/{policy_id}`
  - `PATCH /v1/auth/api-keys/{key_id}/policy`

## How clients use it

Nothing changes in the calls. A request without a required enum is refused
with the same code as before and a clearer message:

```bash
curl -sS https://<api-host>/marketdata.v1.MarketDataService/GetCandles \
  -H 'Content-Type: application/json' -d '{"symbolId": 1}'
# 400 invalid_argument "validation error: timeframe: value is required"

curl -sS 'https://<api-host>/v1/spot/markets/BTC-USDT/candles?timeframe=7m'
# 400 {"code":"BAD_REQUEST","detail":"timeframe must be one of: 1s, 1m, 3m, 5m, 15m, 30m, 1h, 2h, 4h, 6h, 8h, 12h, 1d, 3d, 1w, 1mo", ...}
```

The policy operations are called as before, for example
`GET https://<api-host>/v1/auth/policies/api-keys`.

## Migration

None for well-formed requests: the same requests are accepted and refused
with the same codes. Only a client that matched the old error text or the
`enum.not_in` rule ID of a missing required enum must match `value is
required` or the `required` rule ID instead.
