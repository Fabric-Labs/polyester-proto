## What and why

When the exchange halts a market because it can no longer match it safely,
it cancels every open order of that market. The trading WebSocket
(`tradews.xml`) now pushes each affected order's end to its account's
connections, so a client sees the cancel without polling.

- **Before:** a connection got only a `MarketResync` (reason `INTERRUPTED`)
  for the market. It learned of the cancels by reconciling through the Orders
  API, which could briefly still show the orders as working.
- **Now:** after that `MarketResync`, each open order of the market gets one
  `OrderEvent`:
  - `status` `CANCELED`;
  - `cancelReason` `MARKET_HALTED`;
  - `remainingQtyScaled` 0 and `cumulativeQtyScaled` unchanged, so fills
    before the halt stand;
  - `version` one above the order's last;
  - `eventTsNs` at the halt.

  It is the same order state the Orders API returns for the order.
- **An order that had already ended:** an order that was already filled or
  canceled but still had a take-profit or stop-loss leg open gets one more
  `OrderEvent`, at its next version, with its own status, quantities and
  `eventTsNs` unchanged.

Nothing on the wire changes: no message, field, enum value or schema
version. `CancelReason` `MARKET_HALTED` (17) is the value the Orders API
already uses for these cancels.

## How clients use it

Subscribe to `orders` with `marketResync`, as before. Handle the new events
like any other `OrderEvent`: keep the highest `version` per order and ignore
older or duplicate ones.

```text
Subscribe (template 6): channels = orders | marketResync
MarketResync (template 29): symbolId = 7, reason = INTERRUPTED
OrderEvent (template 25): symbolId = 7, orderId = <order>, version = <last + 1>,
  status = CANCELED, cancelReason = MARKET_HALTED, remainingQtyScaled = 0
```

On the `MarketResync`, reconcile the market's orders through the Orders API
as before. The `OrderEvent`s that follow apply on top: each arrives once per
connection, after the `MarketResync` and after every earlier event of its
order, and no later event of that order follows. The reconciliation may
already show some of them, at the same version. They can arrive from
milliseconds to seconds after the `MarketResync`, once the exchange has
recorded every cancel of the halt. If the connection cannot be given every
order's end, for example because the market halts again first, it gets
another `MarketResync` for the market instead, after the ends it did get;
reconcile as on any `MarketResync`.

A connection that opts out of `marketResync` is closed with status 1012 at
the halt, as before. It recovers through the Orders API after reconnecting
and gets no `OrderEvent` for the halt.

## Migration

None. Clients that reconcile on `MarketResync` keep working, and the
`OrderEvent`s carry the same states the reconciliation returns.
