## What and why

Every REST decimal string must now match the grammar the reference documents
for it, `^[0-9]+(\.[0-9]+)?$`: ASCII digits with an optional fractional part,
a digit on both sides of the dot, no sign and no surrounding whitespace. An
empty string is not a decimal: only an omitted field is absent. Before, the
REST endpoints accepted different supersets of it: order and trigger writes
read `+0.12`, `.12`, `45.` and `-0.12`, transfer and withdrawal amounts and
policy limits read padded values such as `" 0.01"`, and an empty decimal
read as an omitted one.
One grammar on every surface means a value is never accepted by one endpoint
and refused by another.

A refused decimal answers HTTP 400 with the field's code and names the field:

- Orders and triggers: `BAD_PRICE` for prices and `BAD_QTY` for quantities
  and amounts, or the field's own code where it has one:
  `TRIGGER_PRICE_INVALID` (attached and trigger `triggerPrice`, and a
  ladder's `priceMin` and `priceMax`), `TRIGGER_QTY_INVALID` (a trigger's
  `qty`), `TRIGGER_ACTIVATION_PRICE_INVALID` (a trigger's and a trigger
  modify's `activationPrice`), `TRAILING_DISTANCE_INVALID` (attached and
  trigger `trailingDistance`) and `ICEBERG_DISPLAY_INVALID` (`displayQty`).
- Internal transfers, trading withdrawals and auto-withdraw rules:
  `INVALID_AMOUNT`. A malformed amount was answered `invalid_request` on
  internal transfers and trading withdrawals, and `INVALID_REQUEST` on
  auto-withdraw rules.
- Subaccount policy limits (`maxOrderNotional`): `AUTH_INVALID_REQUEST`. On
  create, omit `maxOrderNotional` for no explicit cap; an empty string, which
  meant no cap before, is now refused.

ConnectRPC requests carry scaled integers and are unchanged.

## How clients use it

Send decimals as plain digit strings, for example:

```http
POST /v1/orders
{"order":{"symbol":"BTC-USDT","side":"BUY","baseQty":"0.12","limitGtc":{"price":"61000.25"}}}
```

A value outside the grammar is refused before it is read:

```http
POST /v1/orders
{"order":{"symbol":"BTC-USDT","side":"BUY","baseQty":"0.12","limitGtc":{"price":"+61000.25"}}}

HTTP/1.1 400 Bad Request
Content-Type: application/problem+json

{"code":"BAD_PRICE","detail":"invalid price: want a decimal string matching ^[0-9]+(\\.[0-9]+)?$","violations":[{"fieldPath":"order.limitGtc.price","ruleId":"format"}]}
```

```http
POST /v1/trading/internal-transfers
{"destinationSmartAccountAddress":"0x…","assetId":7,"amount":" 0.01","idempotencyKey":"k"}

HTTP/1.1 400 Bad Request
{"code":"INVALID_AMOUNT","detail":"invalid amount: want a decimal string matching ^[0-9]+(\\.[0-9]+)?$"}
```

Trailing zeros remain valid: `"45.0"` and `"0.120"` parse as before.

## Migration

1. Format every REST decimal as digits with an optional fractional part:
   `"0.12"`, not `".12"`; `"45"` or `"45.0"`, not `"45."`; no `+` or `-`
   sign; no leading or trailing whitespace.
2. Omit an optional decimal instead of sending `""`. On a subaccount policy
   create, omit `maxOrderNotional` for no explicit cap.
3. A REST client that matched `invalid_request` or `INVALID_REQUEST` for a
   malformed transfer, withdrawal or auto-withdraw amount now receives
   `INVALID_AMOUNT`.
4. A REST client that relied on a negative order or trigger decimal reaching
   validation, for example a negative trailing `limitPrice` answered
   `VALIDATION_ERROR`, now receives the field's format refusal (`BAD_PRICE`).
