## What and why

A message sent without a trading account now runs on the user's **main
account** instead of answering without account data. The chat's account
picker offers "Main account" as its first choice: the user can ask about
their funding balance or their trading accounts without picking one first.

**Availability:** devnet only.

- `SendMessageRequest.subaccount_id`, omitted: the run reads the main account.
  It answers with the main account's balances (its funding balance included),
  every trading account with its equity, API keys, price alerts, fee rates and
  permission checks. It places, changes or cancels no order, trigger or swap:
  asked to trade, it asks the user to select a trading account.
- `SendMessageRequest.subaccount_id`, set: unchanged. The run reads and acts on
  that trading account.
- `BalancesTable.account_id`: the account the balances were read from. It is
  the trading account the request named, or the caller's main account (its
  public account ID) when the request named none.

No field, message or enum value is added or removed.

## How clients use it

Send the message without `subaccountId` when the user picks "Main account":

```json
POST /ai.v1.AssistantService/SendMessage
{
  "text": "What's my funding balance?",
  "idempotencyKey": "send-3c9e51"
}
```

The run's `balancesTable` view then carries the main account's ID in
`accountId`. Send `subaccountId` with the trading account the user picked to
let the run trade:

```json
POST /ai.v1.AssistantService/SendMessage
{
  "text": "Buy 0.1 BTC",
  "idempotencyKey": "send-3c9e52",
  "subaccountId": "4105301236839741"
}
```

## Migration

None for the wire: the request and every message keep their shape. A client
that labels the no-account choice "No account" should label it "Main account":
the run now answers about the main account there.
