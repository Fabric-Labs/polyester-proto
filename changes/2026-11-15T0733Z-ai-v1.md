## What and why

`ListAssistantKeys` can now return each key's account name, so a client can
show the user which accounts the assistant can read by the names they chose
rather than by IDs. `SendMessage` can now say that a message reads no account
at all, for a client whose user has not given the assistant access to any
account.

**Availability:** devnet only.

- `SendMessageRequest.account_selection` (new, `AccountSelection`):
  `ACCOUNT_SELECTION_UNSPECIFIED`, the default, keeps today's meaning: the run
  reads the trading account `subaccount_id` names, or the main account when
  it is omitted. `ACCOUNT_SELECTION_NONE` reads no account: the run answers
  about the markets and Polyester only. `subaccount_id` must then be omitted
  (`INVALID_ARGUMENT` otherwise). The field is part of the request the
  idempotency key covers.
- `AccountSelection` (new enum): `ACCOUNT_SELECTION_UNSPECIFIED` and
  `ACCOUNT_SELECTION_NONE`.

- `ListAssistantKeysRequest.view` (new, `AssistantKeyView`): how much of each
  key to return. `ASSISTANT_KEY_VIEW_UNSPECIFIED`, the default, returns what
  the call returned before: each key's account, ID, public key and state.
  `ASSISTANT_KEY_VIEW_FULL` also returns each key's account name.
- `AssistantKey.label` (new): the name of the key's subaccount, as its owner
  set it. Returned only in the full view. It is empty for the main account's
  key, for a subaccount without a name, and when the name could not be read.
  A name that cannot be read never fails the call: the keys are listed
  without it.
- `AssistantKeyView` (new enum): `ASSISTANT_KEY_VIEW_UNSPECIFIED` and
  `ASSISTANT_KEY_VIEW_FULL`.

`CompleteAssistantKeysResponse` keys never carry a name.

## How clients use it

Send a message that reads no account:

```json
POST /ai.v1.AssistantService/SendMessage
{
  "text": "How is BTC doing?",
  "idempotencyKey": "send-7d1a20",
  "accountSelection": "ACCOUNT_SELECTION_NONE"
}
```

Ask for the full view where names are shown:

```json
POST /ai.v1.AssistantService/ListAssistantKeys
{
  "view": "ASSISTANT_KEY_VIEW_FULL"
}
```

```json
{
  "keys": [
    { "keyId": "ak_01", "publicKeyEd25519": "…", "state": "ACTIVE" },
    {
      "subaccountId": "4105301236839741",
      "keyId": "ak_02",
      "publicKeyEd25519": "…",
      "state": "ACTIVE",
      "label": "Benchmark Maker"
    }
  ]
}
```

The first key has no `subaccountId`: it is the main account's key, and the
client names it "Main account" itself. Omit `view` when names are not needed:
the call then reads no names and stays as fast as before.

## Migration

None: `view` and `account_selection` are optional, and their defaults answer
as before.
