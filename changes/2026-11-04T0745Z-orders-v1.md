## What and why

An order with attached risk (take-profit, stop-loss or trailing stop) whose
leg's exit could never meet the pair's minimum quantity, step size or minimum
notional is refused with the same code as before (`ERROR_CODE_MIN_QTY`,
`ERROR_CODE_QTY_STEP_SIZE` or `ERROR_CODE_MIN_NOTIONAL`), but the answer now
says which leg: the `ErrorDetail` carries a `FieldViolation` on the leg's
attached-risk field, its `rule_id` that code, and the message names the leg.
Before, the refusal read like a too-small order, and the user could not tell
the leg was the problem. The RiskPolicy reference documents how a leg's exit is
valued for the minimums. Message shapes are unchanged.

## How clients use it

CreateOrder, BatchCreateOrders items, PreviewOrder's rejection, ModifyOrder
and BatchReplaceOrders items:

```json
{
  "code": "ERROR_CODE_MIN_NOTIONAL",
  "violations": [{
    "fieldPath": "order.attached_risk.stop_loss",
    "ruleId": "MIN_NOTIONAL",
    "message": "Its stop-loss can't be placed when it triggers (MIN_NOTIONAL), so the order was not placed. Nothing changed."
  }]
}
```

The field path is `order.attached_risk.<leg>` for a create, a batch create
item and a preview, `new_attached_risk.<leg>` for a modify and
`items[i].new_attached_risk.<leg>` for a batch replace item, where `<leg>` is
`take_profit`, `stop_loss` or `trailing_stop`. REST names the same fields in
camelCase (`order.attachedRisk.stopLoss`, `items[i].attachedRisk.stopLoss`,
`newAttachedRisk.stopLoss`). A refusal of the order itself carries no such
violation.

## Migration

None: the code is unchanged, and the violation is additional detail.
