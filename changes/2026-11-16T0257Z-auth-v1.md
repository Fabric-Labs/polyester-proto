## What and why

The account read procedures now answer authentication refusals and oversized
requests in the caller's protocol, as every other API does. Until now a
ConnectRPC, gRPC or gRPC-web call they refused before reading it got a REST
problem body, which those clients cannot parse: they fell back to the HTTP
status, with an empty message and no `auth.v1.AuthErrorDetail`.

The procedures are `auth.v1.AuthService/Me`; `ApiKeyService` `GetApiKey` and
`ListApiKeys`; `PolicyService` `GetApiPolicy`, `GetSubaccountPolicy`,
`ListApiPolicies` and `ListSubaccountPolicies`; `SubaccountService`
`ListSubaccounts`, `ListSubaccountMembers` and `ListSubaccountInvites`;
`SubaccountViewService` `GetSubaccount` and `ListSubaccountActivity`;
`SubaccountRoleService/GetEffectiveSubaccountPermissions`; the
`AddressBookService` reads (`ListAddressBooks`, `GetAddressBookView`,
`ListAddressBookEntries`, `GetWithdrawWhitelistView`,
`ListInternalTransferWhitelistEntries`, `ListTransferCounterparties`,
`ListTransferDestinations`); `vip.v1.VIPService/GetVIPStatus`;
`ratelimit.v1.RateLimitService/GetTradingRateLimits`;
`fees.v1.FeeService/GetSpotFeeRates`; and
`checkpoints.v1.CheckpointService/ListMyCheckpoints`.

| Code | API | ConnectRPC code (was → now) | HTTP status (REST) |
| --- | --- | --- | --- |
| `AUTH_*` refusals (missing or invalid credentials, API-key signature, timestamp, receive window, headers, source IP) | Account reads above | `unauthenticated` with no detail → `unauthenticated` with the `AuthErrorDetail` | 401 |
| `AUTH_TEMPORARILY_UNAVAILABLE` | Account reads above | `unavailable` with no detail → `unavailable` with the `AuthErrorDetail` and `Retry-After: 5` | 503 |
| `REQUEST_TOO_LARGE` | Account reads above, API-key requests | `unknown` → `resource_exhausted` | 413 |

A refused gRPC-web call from a browser can now read its status and the
`AuthErrorDetail` from `Grpc-Status`, `Grpc-Message` and
`Grpc-Status-Details-Bin`. REST answers are unchanged. No message, field or
enum value changed.

## How clients use it

```http
POST /auth.v1.ApiKeyService/ListApiKeys
Content-Type: application/json

HTTP/1.1 401 Unauthorized

{"code":"unauthenticated","message":"API key signature is invalid","details":[{"type":"auth.v1.AuthErrorDetail","value":"CDASHEFQSSBrZXkgc2lnbmF0dXJlIGlzIGludmFsaWQ","debug":{"code":"AUTH_SIGNATURE_INVALID","message":"API key signature is invalid"}}]}
```

```http
POST /vip.v1.VIPService/GetVIPStatus
Content-Type: application/json

HTTP/1.1 503 Service Unavailable
Retry-After: 5

{"code":"unavailable","message":"authentication temporarily unavailable; retry with a fresh login","details":[{"type":"auth.v1.AuthErrorDetail","value":"CC4SQGF1dGhlbnRpY2F0aW9uIHRlbXBvcmFyaWx5IHVuYXZhaWxhYmxlOyByZXRyeSB3aXRoIGEgZnJlc2ggbG9naW4","debug":{"code":"AUTH_TEMPORARILY_UNAVAILABLE","message":"authentication temporarily unavailable; retry with a fresh login"}}]}
```

```http
POST /auth.v1.ApiKeyService/ListApiKeys
Content-Type: application/json
X-API-KEY-ID: <key>

HTTP/1.1 429 Too Many Requests

{"code":"resource_exhausted","message":"request too large"}
```

ConnectRPC answers `resource_exhausted` with HTTP 429 by its own protocol
mapping; branch on the code and the `AuthErrorDetail`, not the status.

## Migration

1. Where a ConnectRPC, gRPC or gRPC-web client of these procedures reads an
   authentication refusal from the HTTP status alone, read the
   `AuthErrorDetail` `code` instead, as on the other APIs.
2. Where such a client detects an oversized request by matching `unknown`,
   match `resource_exhausted` instead. Do not retry it unchanged: send a
   smaller request.

REST clients that branch on the HTTP status or the problem `code` need no
change.
