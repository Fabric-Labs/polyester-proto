## What and why

No field, message or behaviour changes. The documentation changes, and the
published validation range of `orders.v1.Order.version` now matches its
type: the `0..2147483647` rule is removed, so the range is the full unsigned
32-bit range. The field is only ever returned, never sent, so no request
changes. The documentation of an order's `version` now states how a client
uses it to tell a current read from a stale one:

- `orders.v1.Order.version` (REST `version`), returned by GetOrder,
  GetOpenOrders and GetOrderHistory, is the same per-order counter as
  `version` on the order's events on the private WebSocket (`OrderEvent`) and
  the trade WebSocket (`OrderEvent`).
- It is 0 while the order is accepted but not yet on the book (status
  `PENDING`), 1 from its first book state, and it rises with every later
  published change of the order's state: an amend in place, a fill, a change
  of its attached risk, a cancel or a replace. It is an unsigned 32-bit
  counter that increases on every change of the order: it would wrap to 0
  only after 4,294,967,295 changes to one order ID. A replace that gives the
  order a new ID starts that order's own version.
- A read can lag behind the order's events. An amend in place keeps the order
  ID, so only the version shows that a read is older than an event already
  applied.
- `fee_total` is not covered by the version: a fill's fee is recorded after the
  fill, so two responses with the same version can show different fee totals.
  A read includes `attached_risk` only on request, so its absence is no change
  of the order.

## How clients use it

Keep, per order ID, the highest version applied from reads and events alike.
Drop any read, and ignore any event, whose version is below it. A stream need
not show every version, so a gap is not an error; read the order to recover
its current state.

```text
POST /orders.v1.OrdersReadService/GetOrder
{"orderId": "1234567890123456789"}
GET /v1/spot/orders/1234567890123456789

applied = {}                               # order ID -> highest version
on event or read of order o:
  if o.version < applied.get(o.orderId, 0): drop it   # older state
  else: apply it; applied[o.orderId] = o.version
```

For example, a client places an order (event version 1), amends it in place
(event version 2) and then reads it. A read that returns version 1 shows the
size and price from before the amend: drop it and keep the amended state.

## Migration

None: behaviour is unchanged. A client that adopts a read's quantities and
price without checking its version should now compare the version as above,
so a lagging read cannot undo an amend it has already applied.
