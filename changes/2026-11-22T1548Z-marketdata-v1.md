## What and why

The public API now refuses input it used to ignore. Before, a misspelled or
misplaced parameter was dropped without an error, so the request ran without
it. A misspelled account selector read or traded on the main account, and a
misspelled candle filter returned the latest candles. This is a deliberate
breaking change before v1: unknown input is refused, never ignored. The rule
covers every public REST operation and every public RPC, not only the services
listed above.

- REST: a query parameter the operation does not declare gets
  `400 BAD_REQUEST`. The detail names the parameter. When it is another
  spelling of a declared one, the detail says which to use, for example
  `subaccount_id is not supported; use subaccountId`. Otherwise it lists the
  declared parameters. An empty value counts: `?start=` is refused too.
- ConnectRPC: a POST carrying query parameters gets `invalid_argument` naming
  them, with the request body field to use when one matches. A GET takes only
  the Connect protocol's own parameters (`connect`, `encoding`, `message`,
  `base64`, `compression`).
- ConnectRPC JSON: a request body field the request message does not declare
  gets `invalid_argument` naming it. Both spellings of a declared field still
  work, for example `subaccountId` and `subaccount_id`.

Separately, `include_reference` on `GetCandles` and `GetCandlesColumns`
(`includeReference` on REST candles) now documents its listing cutover.
Reference candles cover only the time before the pair's listing: each one's
bucket starts before the bucket that contains `listing_at`, as `GetSpotConfig`
reports it. From that bucket on, the pair's own candles cover the market. A
pair without `listing_at` has no listing cutoff; availability, the requested
range and pagination still apply. The behaviour is unchanged; only its
description is new.

## How clients use it

Send only the parameters an operation declares, with their documented names:

```http
GET /v1/balances?subaccountId=<subaccount id>
GET /v1/spot/markets/BTC-USDT/candles?timeframe=1m&startTime=2026-11-12T00:00:00Z&endTime=2026-11-13T00:00:00Z
```

Over ConnectRPC, put every field in the request body, never in the URL:

```http
POST /orders.v1.OrdersService/CreateOrder
Content-Type: application/json

{"subaccountId": "<subaccount id>", "order": {...}}
```

A request with no account selector still acts on the main account, and a
valid `subaccountId` still goes through the same account checks.

## Migration

1. Check every REST call for query parameters the API reference does not list
   for that operation, such as `subaccount_id`, `start`, `end` or
   `startTimeMs`. Rename them to the documented names (`subaccountId`,
   `startTime`, `endTime`) or remove them. Each of these calls now gets `400`.
2. Check every ConnectRPC call for query parameters on POST requests, and move
   any account selector into the request body as `subaccountId`.
3. Check every ConnectRPC JSON body for fields the request message does not
   declare, and remove or rename them.
