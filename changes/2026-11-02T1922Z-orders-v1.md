## What and why

When the exchange halts a market, its orders and triggers now always reach a
visible end. Before, they could stay open with nothing reserved behind them, or
disappear, and no reason told clients that a halt had ended them. Halts are
exceptional: the exchange halts a market only to protect its integrity. The
market refuses new orders and triggers until it trades again. Released in
9.2.1.

Two cancel reasons are added:

- `orders.v1.CancelReason` gains `CANCEL_REASON_MARKET_HALTED = 17`. When a
  market is halted, the exchange cancels every open order of that market.
  Each such order ends `CANCELED` with this reason, once, at the halt time.
  Fills before the cancel stand.
- `triggers.v1.TriggerCancelReason` gains
  `TRIGGER_CANCEL_REASON_MARKET_HALTED = 13`. The same halt ends every open
  trigger of the market, and releases its reserved funds: standalone stops,
  take profits, trailing stops, TWAPs and ladders, and the attached
  take-profit, stop-loss and trailing-stop legs of the market's orders. Each
  such trigger ends `STATUS_CANCELED` with this reason, once, at the halt
  time.

The halt also changes what clients see in three other ways:

- **Parent orders show their legs ended.** An order the halt cancels ends its
  live legs with it. An order that had already ended, for example `FILLED`, is
  republished at its next version with the same status, fills and time, and
  its legs shown ended. So an order's version can increase once at a halt even
  when its status doesn't change.
- **Orders refused after admission end `REJECTED`.** The halted market refuses
  every order that reaches it after the halt, including the order whose
  arrival halted it. Admission comes first, so `CreateOrder` may already have
  answered success with an order ID. The order then ends `REJECTED` with
  `reject_reason` `ERROR_CODE_MARKET_HALTED` (56, an existing value) instead
  of vanishing. A synchronous `ERROR_CODE_MARKET_HALTED` from a write is
  unchanged: it still means the request was refused before admission.
- **Triggers refused after admission end `STATUS_FAILED`.** A trigger created
  after the halt ends failed instead of vanishing; its create call may already
  have answered success. The intended reason is the existing
  `TRIGGER_FAILURE_REASON_MARKET_HALTED` (8). Known gap: reads currently
  report `failure_reason` as the unnamed value 212 instead, until a fix
  reports 8.

## How clients use it

The new values appear wherever the two enums already appear: an order's
`cancel_reason` (for example in `OrdersReadService.GetOrder`,
`GetOrderHistory` and the private WebSocket's `OrderEvent`), and a trigger's
or trigger event's `cancel_reason` (`TriggersService.GetTrigger`,
`ListTriggers`, `ListTriggerEvents`). No request changes.

```bash
# Authenticate as for any private read (omitted here).
curl -sS https://<api-host>/orders.v1.OrdersReadService/GetOrderHistory \
  -H 'Content-Type: application/json' -d '{"status": "CANCELED", "limit": 50}'
# An order the halt canceled:
#   "status": "CANCELED", "cancelReason": "CANCEL_REASON_MARKET_HALTED"
# An order refused after the halt:
#   "status": "REJECTED", "rejectReason": "ERROR_CODE_MARKET_HALTED"
curl -sS 'https://<api-host>/v1/triggers/<base58-trigger-id>/events'
# REST drops the enum prefix: "cancelReason": "MARKET_HALTED"
```

ConnectRPC JSON carries order and trigger IDs as decimal strings of their
`fixed64`. REST paths take the base58 public ID instead; for example
`1234567890123456789` is `3sDK21t5nHJ`. A decimal ID in a REST trigger path
is refused with HTTP 400 `INVALID_TRIGGER_ID`.

Right after a halt, a trigger read can briefly answer the retryable
`UNAVAILABLE` (REST 503, `code` `UNAVAILABLE`) until the trigger's end is
readable. A retry then returns the canceled trigger, never the trigger as
live.

Trading WebSocket (SBE schema `tradews`, version 35):

- `CancelReason` gains `MARKET_HALTED = 17`.
- At the halt, a session receives `MarketResync` (reason `INTERRUPTED`) for
  the market. This requires the subscription to enable `marketResync`
  together with orders or executions. Without it, the connection closes with
  WebSocket status 1012. The halt's per-order cancels and trigger ends are
  not pushed: reconcile the market's orders and triggers through the Orders
  API and `ListTriggers`, as for any `MarketResync`.
- An order the halted market refuses after admission arrives as `OrderEvent`
  `status` `REJECTED`, `rejectReason` `MARKET_HALTED` (56).

## Migration

None: the enums gain values and existing values are unchanged. A client that
switches exhaustively over either enum should handle the new value, for
example by showing "Market halted"; an unknown value should already fall back
to a generic cancel. Clients that treat a successful `CreateOrder` or
`CreateTrigger` as proof that it rests should already reconcile through reads
or the private feed; a halt is one more reason an admitted order or trigger
ends `REJECTED` or `STATUS_FAILED`.
