## What and why

A request refused for its credentials is now answered in the protocol the
client called with, on every service:

- A ConnectRPC, gRPC or gRPC-web call of a procedure the API serves gets the
  refusal's error code and an `auth.v1.AuthErrorDetail` naming the refusal,
  with one message per refusal: `unauthenticated` with
  `AUTH_AUTHENTICATION_REQUIRED` ("authentication required") for missing or
  invalid session credentials, `unauthenticated` with
  `AUTH_SIGNATURE_INVALID`, `AUTH_TIMESTAMP_SKEW`, `AUTH_RECV_WINDOW_INVALID`,
  `AUTH_MISSING_HEADERS`, `AUTH_KEY_EXPIRED`, `AUTH_KEY_DISABLED` or
  `AUTH_IP_NOT_ALLOWED` for an API-key refusal, `resource_exhausted` with
  `AUTH_REPLAY_CAPACITY_EXHAUSTED`, and `unavailable` with
  `AUTH_TEMPORARILY_UNAVAILABLE`.
- Any other request, including a path shaped like a procedure the API does not
  serve, gets the REST `application/problem+json` body with the documented
  code and status.

What changes, per service:

| Service | Request | Before | Now |
| --- | --- | --- | --- |
| Account and security (`auth.v1`) | RPC refused for an API key | `unauthenticated`, `AUTH_AUTHENTICATION_REQUIRED`, message is the REST code (for example `SIGNATURE_INVALID`) | `unauthenticated` with the refusal's own detail, for example `AUTH_SIGNATURE_INVALID` |
| Account and security (`auth.v1`) | RPC without valid session credentials | message "missing Authorization header" or "invalid token" | message "authentication required"; code and detail unchanged |
| Account and security (`auth.v1`) | JSON POST to a procedure path the API does not serve, for example `/auth.v1.AuthService/Unknown` | ConnectRPC error JSON | `401` problem with the refusal's code, or `403 AUTH_SESSION_KIND_NOT_ALLOWED` for an API key |
| Rewards (`rewards.v1`) | RPC without valid session credentials | plain-text `401 unauthenticated`, so clients saw `unauthenticated` without a detail | `unauthenticated` with `AUTH_AUTHENTICATION_REQUIRED` |
| Rewards (`rewards.v1`) | Request to a path under `/rewards.v1.RewardCampaignService/` the API does not serve | plain-text `401` | `401` problem with the refusal's code |
| Price alerts (`alerts.v1`) | RPC refused for an API key | `unauthenticated`, `AUTH_AUTHENTICATION_REQUIRED`, message "unauthenticated" | the refusal's own code, detail and message |
| Price alerts (`alerts.v1`) | RPC refused because the key's signed requests fill its receive windows | `unauthenticated` | `resource_exhausted`, `AUTH_REPLAY_CAPACITY_EXHAUSTED` |
| Price alerts (`alerts.v1`) | RPC without valid session credentials | message "unauthenticated" | message "authentication required"; code and detail unchanged |
| Price alerts (`alerts.v1`) | Any request that is no RPC of the service | plain-text `401` or `503`, or a ConnectRPC error body for a request shaped like one | problem with the documented code and status (`429` for replay capacity) |
| Notifications (`notifications.v1`) | RPC without valid session credentials | message "unauthenticated" | message "authentication required"; code and detail unchanged |
| Notifications (`notifications.v1`) | Any request that is no RPC of the service | plain-text `401`, or `403` with API-key headers, or a ConnectRPC error body for a request shaped like one | `401 UNAUTHENTICATED` problem, or `403 AUTH_SESSION_KIND_NOT_ALLOWED` problem |

## How clients use it

Read the reason of a refused RPC from its `auth.v1.AuthErrorDetail`, never
from the message text:

```text
POST https://<api-host>/alerts.v1.PriceAlertService/ListAlerts
Content-Type: application/json
X-API-KEY-ID: <key id>
X-API-TIMESTAMP: <stale timestamp>
X-API-SIGNATURE: <signature>

{}

HTTP/1.1 401 Unauthorized
{"code":"unauthenticated","message":"API key timestamp is outside the request's receive window",
 "details":[{"type":"auth.v1.AuthErrorDetail","value":"..."}]}
```

The detail's `code` is `AUTH_TIMESTAMP_SKEW`. A REST client reads the problem
body's `code`, for example `TIMESTAMP_SKEW`, and its HTTP status.

## Migration

1. RPC clients of the price alerts API: tell API-key refusals apart by the
   `AuthErrorDetail` code instead of treating every `unauthenticated` as
   `AUTH_AUTHENTICATION_REQUIRED`, and retry `resource_exhausted`
   (`AUTH_REPLAY_CAPACITY_EXHAUSTED`) after a short wait instead of treating
   it as a credential failure.
2. RPC clients of the account and security API: read the API-key refusal from
   the `AuthErrorDetail` code instead of the error message.
3. Clients that compared refusal messages ("missing Authorization header",
   "invalid token", "unauthenticated") should compare detail codes instead.
4. Clients that parsed a plain-text refusal body from the rewards, price
   alerts or notifications APIs should parse the problem body, or the RPC
   error.
