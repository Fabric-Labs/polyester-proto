## What and why

The documentation now states what happens to an order's attached
take-profit, stop-loss or trailing stop when the parent order ends after a
small partial fill. It used to say that such legs always keep protecting the
filled position.

When the parent order ends after a partial fill and no exit has run, each leg
is checked against the pair's minimums at the filled quantity, valued where
its exit would execute. This applies however the parent ends: canceled alone,
by `CancelAllOrders` or the dead-man switch (`CancelAllAfter`), or with the
unfilled remainder of an immediate-or-cancel or market order. A leg whose exit
would be below the minimum order value could never be placed, so it ends at
once with status `STATUS_FAILED` and failure reason
`TRIGGER_FAILURE_REASON_MIN_NOTIONAL` (`TRIGGER_FAILURE_REASON_MIN_QUANTITY`
below the minimum quantity), without firing. The parent's other legs whose
exits meet the minimums stay active and protect the filled quantity. A
trailing sell exit has no price to value it at, so only the minimum quantity
is checked when the parent ends; if its exit is below the minimum order value
when it fires, it ends `STATUS_FAILED` with
`TRIGGER_FAILURE_REASON_MIN_NOTIONAL` then.

This is not an `EVENT_FIRE_REFUSED`. An attached leg's exit refused below the
minimums while its parent order is still open is reported as
`EVENT_FIRE_REFUSED`: the position can still grow, so the leg stays active.
`EVENT_FIRE_REFUSED` for other reasons, such as a rate limit or an account
repair, is unchanged.

A leg that fails this way with `TRIGGER_FAILURE_REASON_MIN_NOTIONAL` or
`TRIGGER_FAILURE_REASON_MIN_QUANTITY` now reports the filled quantity it was
checked at, rounded down to the pair's quantity step. Before, a leg whose
parent's only fill arrived as the parent ended (an immediate-or-cancel or
market order) kept the parent's full quantity.

Documentation changed on `RiskPolicy`, `OrdersService.CancelAllOrders`,
`OrdersService.CancelAllAfter`, `TriggerEventType.EVENT_FIRE_REFUSED`,
`TriggerFailureReason.TRIGGER_FAILURE_REASON_MIN_NOTIONAL` and
`Trigger.qty_scaled`. No message, field or enum value changed.

## How clients use it

Read an order's legs after the parent ends to see which still protect the
position. Over REST a failed leg has `status` `FAILED` and `failureReason`
`MIN_NOTIONAL` (`STATUS_FAILED` and `TRIGGER_FAILURE_REASON_MIN_NOTIONAL` over
ConnectRPC). Its quantity is the filled quantity it was checked at: `qty`, a
decimal string in base asset units, over REST (`GET /v1/triggers/{trigger_id}`
and `GET /v1/triggers`), and `qty_scaled` (JSON `qtyScaled`) over ConnectRPC.
`ListTriggerEvents` carries the `EVENT_FAILED` event with its failure reason;
trigger events carry no quantity:

```bash
curl -sS https://<api-host>/v1/triggers/<trigger id>
curl -sS https://<api-host>/triggers.v1.TriggersService/ListTriggerEvents \
  -H 'Content-Type: application/json' -d '{"triggerId": "<trigger id>"}'
```

The private trigger stream publishes the same `STATUS_FAILED` state and an
`EVENT_FAILED` event with that reason. Show a failed protective leg to the
user, for example next to the leg that is still active.

## Migration

None: no message, field or enum value changed. A client that treats every
leg as live until the parent is canceled before any fill should also handle
a leg that ends `STATUS_FAILED` with `TRIGGER_FAILURE_REASON_MIN_NOTIONAL`
or `TRIGGER_FAILURE_REASON_MIN_QUANTITY` when the parent ends.
