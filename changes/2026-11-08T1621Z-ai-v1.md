## What and why

**Availability:** devnet only. Not available on testnet yet; the service isn't deployed or routed there.

`SendMessageRequest` gains `subaccount_id`, the trading account the
assistant reads and acts on for that message. An account can hold several
trading accounts and a session names none, so the client passes the one the
user has selected. It must be one the caller's account owns: another
account's trading account, also one shared with the caller as a member, or
an ID that does not exist is refused with `INVALID_ARGUMENT`, without saying
which. Without it, the
assistant answers without account data: it cannot read balances or orders,
or place and cancel orders, in that run.

## How clients use it

Pass the selected trading account's public ID with each message:

```bash
curl -sS https://<api-host>/ai.v1.AssistantService/SendMessage \
  -H 'Authorization: Bearer <session-token>' -H 'Content-Type: application/json' \
  -d '{"text": "Show my balances", "idempotencyKey": "msg-81c2", "subaccountId": "4128830192"}'
```

- `subaccount_id` is a `fixed64` public ID, a decimal string in JSON, like
  other requests that name a trading account.
- It is part of the request the idempotency key covers. Repeating a key with
  another trading account is `IDEMPOTENCY_CONFLICT`.
- Each message names its own trading account. A conversation may continue on
  another trading account; earlier order approvals stay bound to the account
  they were requested on.

## Migration

None. The field is optional, and the service has not been published yet.
