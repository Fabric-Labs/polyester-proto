## What and why

The API reference now states which API keys may manage keys and policies.
`AuthenticationMethod` gains `ADMIN_API_KEY`: a signed API key request that
only an admin API key may make. These six RPCs declare it in place of
`API_KEY`, next to `SESSION_TOKEN`:

- `ApiKeyService`: `CreateApiKey`, `UpdateApiKey`, `DeleteApiKey`;
- `PolicyService`: `SetApiKeyPolicy`, `SetSubaccountPolicy`,
  `UpdateSubaccountPolicy`.

The API already behaves this way: any other API key is refused HTTP 403,
PermissionDenied, with `AUTH_ADMIN_KEY_REQUIRED`. Only the reference changes.
An admin key signs its requests exactly as any API key does, so the
documented security schemes stay the same. The reference lists the method as
`admin_api_key`.

The documentation examples also change, with no contract change:
`CreateOrder` and `BatchCreateOrders` now show a GTC limit buy with a
stop-loss below and a take-profit above its price. `PreviewOrder` keeps its
market buy and gets the same stop-loss and take-profit prices.

## How clients use it

Call these RPCs with a session token, or sign the request with an admin API
key of the main account. A standard API key gets 403 with
`AUTH_ADMIN_KEY_REQUIRED`.

```json
// DELETE /v1/auth/api-keys/{key_id}
// (POST /auth.v1.ApiKeyService/DeleteApiKey)
{"keyId": "ak_1a3c6de8153d5a5b04cd2a6529779542"}
```

## Migration

None: no request, response or behaviour changes. A client that read these
RPCs' authentication methods from the reference now sees `admin_api_key`
instead of `api_key`. A client that called them with a standard API key was
already refused.
