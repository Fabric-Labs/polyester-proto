## What and why

BatchReplaceOrders now documents how quote refreshes chain. Its response
answers admission, before each admitted item's amend or replace completes.
Until that change completes, a later change of the same order, including an
item of the next batch, is rejected with a retryable code. Which code depends
on how the item names the order:

- by client order ID: `ORDER_MODIFY_IN_PROGRESS`;
- by the `replacementOrderId` the earlier batch returned:
  `ORDER_PLACEMENT_PENDING` until that replacement's placement has been
  confirmed to admission (it may already rest on the book), then
  `ORDER_MODIFY_IN_PROGRESS` until the replace completes.

This was already the behavior; the contract now states it so that market
makers sending back-to-back refreshes handle these as retryable answers rather
than as failures. The descriptions of the two error codes say the same:
`ORDER_PLACEMENT_PENDING` means the placement has not been confirmed yet, not
that the order is off the book.

## How clients use it

Read each item's `status` and `code`. When an item is `REJECTED` with
`ORDER_MODIFY_IN_PROGRESS` or `ORDER_PLACEMENT_PENDING`, resend only that item,
in a new batch under a fresh `requestId`, after a short backoff, for example
50 ms doubling to 1 s with jitter. Name the order by its client order ID, or by
the latest `replacementOrderId` you were given.

- A fresh key is for rejected items only. Resending under the rejected batch's
  key replays the same rejection, even after the earlier change completes.
- Never resend admitted items: each is already applied or in progress, and a
  new batch would change the order again.
- A request whose outcome you did not receive is never resent under a new
  key. Within 60 seconds of sending it, reconcile it by resending the identical
  request under the same key or by reading the batch with
  `GetBatchReplaceStatus`. After that window the batch is no longer retained:
  reconcile the individual orders and never resubmit the batch.

```http
POST /orders.v1.OrdersService/BatchReplaceOrders
Content-Type: application/json

{
  "requestId": "refresh-0002-retry-1",
  "symbolId": 1,
  "items": [{ "clientOrderId": "quote-bid-1", "newPriceTicks": "100010" }]
}
```

The REST form, `POST /v1/orders/replace-batch`, has its own body: the pair's
`symbol` instead of `symbolId`, and each item's price as a decimal string in
`newPrice` instead of `newPriceTicks`. Its request schema refuses unknown
fields, so the ConnectRPC body above is rejected there.

```http
POST /v1/orders/replace-batch
Content-Type: application/json

{
  "requestId": "refresh-0002-retry-1",
  "symbol": "BTC-USDT",
  "items": [{ "clientOrderId": "quote-bid-1", "newPrice": "100.10" }]
}
```

## Migration

None: requests, responses and error codes are unchanged. Clients that treated
`ORDER_MODIFY_IN_PROGRESS` or `ORDER_PLACEMENT_PENDING` on a batch item as
final should retry it as above.
