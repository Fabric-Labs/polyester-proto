## What and why

An attached take-profit or stop-loss whose trigger price is at or past its
parent order's price now names the leg. Before, CreateOrder, PreviewOrder,
BatchCreateOrders, ModifyOrder and BatchReplaceOrders answered such an order
with the error code alone (ERROR_CODE_TRIGGER_PRICE_INVALID for a limit
order, ERROR_CODE_TRIGGER_WOULD_TRIGGER_IMMEDIATELY for a market order's
last-price leg past the best price it takes), so a client could not tell which
exit price to change.

The ErrorDetail now carries one FieldViolation:

- `field_path`: the leg's trigger price, for example
  `order.attached_risk.take_profit.trigger_price_ticks` (CreateOrder,
  PreviewOrder, a BatchCreateOrders item), or
  `new_attached_risk.stop_loss.trigger_price_ticks` (ModifyOrder). REST names
  the same field in its request names, for example
  `order.attachedRisk.takeProfit.triggerPrice`, or
  `items[0].attachedRisk.takeProfit.triggerPrice` for a batch item.
- `rule_id`: the error code without its prefix, `TRIGGER_PRICE_INVALID` or
  `TRIGGER_WOULD_TRIGGER_IMMEDIATELY`.
- `message`: the order the exit prices must take for the order's side. For a
  buy, the take-profit above the limit price and the stop-loss below it, so the
  take-profit is above the stop-loss; for a sell, the other way round. A
  modify, whose request carries no side, states both sides.

When both legs are past the parent's price, the take-profit is named.

`FieldViolation.field_path` now documents which message a path is relative to;
no path changes. A request refused whole names fields in that request
(`items[i].*` in a batch). A BatchCreateOrders item's rejection answers that
item alone and names its fields under `order`, as a CreateOrderRequest
carrying the item would; its index is the result's position. A
BatchReplaceOrders item's error names fields in the whole request
(`items[i].new_attached_risk...`). REST names every batch item field under
`items[i]`. The
error codes, transport codes and when an order is rejected are unchanged; only
the violation is new. Over ConnectRPC the error message is the violation's
message; over REST the problem's `detail` is.

## How clients use it

Preview a buy at 64,000 with its take-profit at 60,000 and its stop-loss at
70,000:

```http
POST /orders.v1.OrdersService/PreviewOrder
{"order":{"symbolId":1,"side":"BUY","baseQtyScaled":"10000","limitIoc":{"priceTicks":"64000000000000"},
  "attachedRisk":{"takeProfit":{"triggerPriceTicks":"60000000000000","child":{"marketIoc":{}}},
                  "stopLoss":{"triggerPriceTicks":"70000000000000","child":{"marketIoc":{}}}}}}
```

```json
{"admissible":false,"rejection":{"code":"ERROR_CODE_TRIGGER_PRICE_INVALID","violations":[{
  "fieldPath":"order.attached_risk.take_profit.trigger_price_ticks","ruleId":"TRIGGER_PRICE_INVALID",
  "message":"A buy order's take-profit trigger price must be above its limit price and its stop-loss trigger price below it, so its take-profit is above its stop-loss. This take-profit is at or below the limit price (TRIGGER_PRICE_INVALID), so the order would not be placed. Nothing changed."}]}}
```

Highlight the field the violation names and show its message.

## Migration

None: the error codes are unchanged, and the violation is added to an
ErrorDetail field clients already receive.
