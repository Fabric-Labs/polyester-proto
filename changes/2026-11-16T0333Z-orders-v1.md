## What and why

- `orders.v1.ErrorCode.ERROR_CODE_ATTACHED_LEGS_EXCEEDED` now answers the
  ConnectRPC code `failed_precondition` instead of `invalid_argument`. The
  refusal names a temporary state of the order: legs being cancelled count
  until they end, and the same request succeeds once they have. It now answers
  like `ERROR_CODE_ATTACHED_EXIT_WORKING`, the other attached-leg refusal that
  clears on its own. The REST status stays `400`, with problem code
  `ATTACHED_LEGS_EXCEEDED`.
- `TakeProfitPolicy`, `StopLossPolicy` and `TrailingStopPolicy`
  `trigger_price_source`: an order whose `INDEX_PRICE` leg is on a market
  without an index price is rejected before any fill with `reject_reason`
  `ERROR_CODE_TRIGGER_PRICE_SOURCE_UNSUPPORTED`. The documentation named a
  reason that is not an `ErrorCode` value. The behavior is unchanged.

## How clients use it

A modify that adds a leg while the order's earlier legs are still being
cancelled is refused, and the same request can be sent again once those legs
have ended:

```json
POST /orders.v1.OrdersService/ModifyOrder
{"orderId": "1234567890",
 "newAttachedRisk": {"takeProfit": {"triggerPriceTicks": "96010000000",
                                    "child": {"marketIoc": {}}}}}
```

ConnectRPC answers `failed_precondition` with the detail code
`ERROR_CODE_ATTACHED_LEGS_EXCEEDED`. REST (`POST /v1/orders/modify`) answers
`400` with problem code `ATTACHED_LEGS_EXCEEDED`. Read the order's legs and
retry once the cancelled ones have ended.

## Migration

Clients that branch on the error code `ERROR_CODE_ATTACHED_LEGS_EXCEEDED`
(REST problem code `ATTACHED_LEGS_EXCEEDED`) need no change.

ConnectRPC clients that handle this refusal by its status code, or by an SDK
exception class derived from it, must update that handler:

1. Handle `ERROR_CODE_ATTACHED_LEGS_EXCEEDED` under `failed_precondition`.
   A handler that catches only `invalid_argument`, or the SDK's validation
   error class, no longer receives it. In the TypeScript SDK it arrives as
   `PreconditionFailedError` instead of `ValidationError`.
2. Do not retry it at once. Read the order's attached legs, and send the
   same modify again only after the legs being cancelled have ended.

REST clients see the same `400` and problem code as before.
