## What and why

`AuthService.Me` now leaves `session` unset when the caller presented no
access token, as `MeResponse.session` documents ("Session assurance details
for the presented access token, if any"). A request signed with an API key
presents no access token, so its `Me` response has no `session`. Before this
fix those responses carried an empty `session` (no `session_id`, level
`SESSION_LEVEL_UNSPECIFIED`), which strict clients rightly rejected as a
session without an ID.

Callers with an access token are unchanged: their `session` carries the
session ID, level, authentication methods and authentication time as before.

## How clients use it

ConnectRPC:

```bash
curl -sS https://<api-host>/auth.v1.AuthService/Me \
  -H 'Content-Type: application/json' -d '{}'
```

REST:

```bash
curl -sS https://<api-host>/v1/auth/me
```

Signed API-key request: the response has `accountId`, `apiKeyId`,
`username` and `rootSmartAccountAddress` and no `session` field, in both
ConnectRPC JSON and REST. Access-token request: `session` is present with a
non-empty `sessionId`.

## Migration

None: the response now matches the documented contract. Clients that treated
an empty `session` as "no session" keep working; clients that rejected a
`session` without a `session_id` now succeed with API keys.
