## What and why

`GetSubaccount` can again include the sub-account's current balances in its
aggregated view. `GetSubaccountRequest.include_balances` (field 6) and
`GetSubaccountResponse.balances` (field 6) are back with the same field
numbers and types as before they were withdrawn, so clients built on either
contract keep encoding and decoding every message. The balances expansion now
works for API-key callers as well as session callers.

`balances` has the same shape as the `GetBalances` response: one row per
asset with funding, trading, reserved and available amounts.

Access follows `GetBalances`. The caller needs the `READ_BALANCES` action on
the sub-account: its role, the sub-account's attached policy and, for an API
key, the key's policy must allow it. An API key bound to a sub-account reads
only that sub-account, and a root-scoped API key cannot read a sub-account's
balances.

## How clients use it

Set `include_balances` (REST `includeBalances=true`). Absent or `false` means
no balances, and the view is answered as before.

```http
POST /auth.v1.SubaccountViewService/GetSubaccount
{"subaccountId": "<subaccount id>", "includeBalances": true}

GET /v1/auth/subaccounts/{subaccount_id}?includeBalances=true
```

- A caller who may see the sub-account but lacks `READ_BALANCES` gets
  `PermissionDenied` with `AUTH_SUBACCOUNT_ACCESS_DENIED` (REST 403).
- A sub-account the caller cannot see is `NotFound` (REST 404), as without
  balances.
- When balances cannot be read right now, the call fails with `Unavailable`
  and `AUTH_TEMPORARILY_UNAVAILABLE` (REST 503 `application/problem+json`).
  It changed nothing; retry the same request, or omit `includeBalances` to get
  the rest of the view.

## Migration

None: the fields are restored additively. Clients that dropped them can add
them back; clients that kept them see balances again when they ask.
