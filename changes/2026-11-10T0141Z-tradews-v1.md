## What and why

The trading WebSocket's SBE encoding now refuses the `postOnly` flag on an
order that cannot rest. A `CreateOrder`, or a `BatchCreateOrders` item, with
`postOnly` set on a LIMIT order with time in force IOC or FOK, or on a MARKET
order, is rejected with `INVALID_ORDER_FLAGS` (214) and no order is created.
Before, such an order was acknowledged and stored with `postOnly: true`,
although post-only has no meaning for an order that never rests. The REST and
ConnectRPC Orders API could not express this combination and are unchanged.

Post-only stays valid on GTC and GTD LIMIT orders. The description of the
`postOnly` choice in `tradews.xml` now says so: "valid only for GTC and GTD
limit orders" (it said GTC only). Undefined flag bits are still rejected. The
schema version stays 36: no field, message or enum value changed.

## How clients use it

Set `postOnly` (bit 0 of `flags`) only on a LIMIT order with time in force
GTC or GTD. The same rule applies to each `BatchCreateOrders` (template 7)
item. SBE `CreateOrder` (template 2):

```text
orderType=LIMIT timeInForce=GTC flags=1                 -> CommandAck
orderType=LIMIT timeInForce=GTD expireAtTsNs=<t> flags=1 -> CommandAck
orderType=LIMIT timeInForce=IOC flags=1                 -> CommandReject code=214
orderType=LIMIT timeInForce=FOK flags=1                 -> CommandReject code=214
orderType=MARKET timeInForce=IOC flags=1                -> CommandReject code=214
```

The refusal of a single create is a `CommandReject` with `code` 214
(`INVALID_ORDER_FLAGS`). A batch item is answered in its `BatchCreateAck`
result with `status` rejected and `code` 214, and the batch's other items are
admitted or rejected on their own.

## Migration

Clients that send `postOnly` on IOC, FOK or MARKET orders must stop setting
the flag on them; the server now rejects those orders instead of accepting
them. Treat `INVALID_ORDER_FLAGS` as a client input error and do not retry the
order unchanged.
