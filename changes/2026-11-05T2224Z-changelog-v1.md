## What and why

Published changelog posts can now be edited. Staff may republish a post, for
example to correct its copy or withdraw a change, so a post's content is no
longer fixed once published. `PostSummary` gains two fields so clients can tell
which version they hold:

- `revision`: starts at 1 and increases with each republication.
- `updated_at`: when the current revision was published; equals `published_at`
  for revision 1.

A post's `slug`, `published_at` and its changes' `id` values stay the same across
revisions. A withdrawn change simply disappears from the next revision.

## How clients use it

`ListPosts` and `GetPost` return the new fields in every post summary. To follow
edits, poll `ListPosts` and read a post again when its `revision` differs from
the one you hold; drop a post that is no longer listed.

```bash
curl -sS https://<api-host>/changelog.v1.ChangelogService/ListPosts \
  -H 'Content-Type: application/json' -d '{"limit": 100}'
curl -sS 'https://<api-host>/v1/changelog/posts?limit=100'
curl -sS 'https://<api-host>/v1/changelog/posts/2026-11-04'
```

```json
{"slug": "2026-11-04", "publishedAt": "2026-11-04T10:00:00Z", "updatedAt": "2026-11-06T09:30:00Z", "revision": 2}
```

`GetPost` responses are now cacheable for 60 seconds with
`stale-while-revalidate=300`, like the list responses, and their ETag changes
with the revision.

`ListChanges` paging: when the post a `page_token` points into was republished
since the token was issued, the next page restarts at the first change of that
post's current revision. Nothing in the current revision is skipped, but changes
of that post that you already received can appear again, so match them by `id`.
Posts you paged past before the republication are not revisited; use `revision`
to find them.

## Migration

None required: both fields are new and existing calls keep working. A client that
stores a post and treats it as final should start comparing `revision`, or it
keeps showing edited or withdrawn content.
