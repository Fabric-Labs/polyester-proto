## What and why

`TriggersService.BatchCancelTriggers` cancels up to 50 of the account's
triggers in one request. Until now a client that wanted to clear its
stop-loss, take-profit, trailing-stop, TWAP or ladder triggers had to call
`CancelTrigger` once per trigger, which is slow for a large set and runs into
the per-request rate limit. The new RPC adds `BatchCancelTriggersRequest`,
`BatchCancelTriggersResultItem` (with its `Status` enum) and
`BatchCancelTriggersResponse`. Existing messages and RPCs are unchanged.

Each trigger is canceled as `CancelTrigger` cancels it, and answered on its
own, in request order: `ACCEPTED`, or `REJECTED` with a `code` and an
`orders.v1.ErrorDetail`. One item's rejection does not stop the others.
`TRIGGER_NOT_FOUND` names an ID that is none of the account's triggers;
`TRIGGER_STATUS_INVALID` a trigger that has already ended, which the client
can treat as done. `RATE_LIMIT_EXCEEDED`, `PAIR_BACKLOGGED` and
`TRIGGER_CONTROL_IN_PROGRESS` items can be retried in a new request.

## How clients use it

ConnectRPC: `POST /triggers.v1.TriggersService/BatchCancelTriggers`

```json
{
  "requestId": "tpsl-cancel-all-7f3a",
  "triggerIds": ["4819204118729944315", "4819204118729944316"]
}
```

REST: `POST /v1/triggers/cancel-batch`, with the same body, trigger IDs as
base58 public IDs:

```json
{
  "requestId": "tpsl-cancel-all-7f3a",
  "triggerIds": ["2RDF8nT5vTq", "2RDF8nT5vTr"],
  "subaccountId": "6TyD9cJ2fXa"
}
```

The response carries `results` (one per trigger ID, same order, each with
`status`, `triggerId`, `code` and `error`), `acceptedCount`, `rejectedCount`
and the server time (`ts`/`tsNs` on ConnectRPC, `tsNs` on REST).

- `trigger_ids`: 1 to 50 distinct, non-zero IDs; more is rejected whole with
  `BATCH_TOO_LARGE`, a duplicate or an empty list with `VALIDATION_ERROR`. To
  cancel more, send further requests of up to 50.
- `request_id` (required, 1–64 of `A-Za-z0-9._:/-`): retrying with the same
  `request_id` and the same `trigger_ids` within 2 minutes returns the
  original results and cancels nothing again, so retry a timed-out request
  unchanged. The same `request_id` with other `trigger_ids` rejects every item
  with `CONFLICT_IDEMPOTENCY_KEY_REUSE`.
- `subaccount_id` is the optional subaccount selector of every trigger write:
  omitted, a subaccount-scoped API key acts for its bound subaccount and other
  callers for their root account. An explicit zero is rejected with
  `INVALID_ARGUMENT` (REST: `INVALID_SUBACCOUNT_ID`).
- Each trigger counts one against the account's cancel rate limit, as a
  `CancelTrigger` does.
- `ACCEPTED` means the cancellation was requested; the trigger's events report
  when it is canceled.

## Migration

None: the RPC and its messages are new.
