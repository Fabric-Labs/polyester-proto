## What and why

When the Orders API refuses a request because of exactly one field, the
top-level error message now names that field and says what to correct.
Before, many of these refusals returned only the error code's generic text,
for example `Request validation failed.` for a good-till-date order whose
expiry is outside its window, or `Price must align with the tick size.` for
an off-tick price. The specific reason appeared only in the error detail's
violations.

The message now reads `validation error: <field>: <reason>`, the same
wording request validation already uses. The error code, the HTTP and
ConnectRPC status, and the error detail with its violations are unchanged. A
refusal with several violations keeps listing each one, one line per
violation, as before. A refused attached take-profit, stop-loss or trailing
stop keeps its own message.

## How clients use it

ConnectRPC: the `message` names the proto field.

```bash
curl -sS https://<api-host>/orders.v1.OrdersService/CreateOrder \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer <token>' \
  -d '{"order":{"symbolId":1,"side":"BUY","baseQtyScaled":"10000","limitGtd":{"priceTicks":"70000000000000","expireAt":"2026-01-01T00:00:00Z"}}}'
# 400 {"code":"invalid_argument",
#      "message":"validation error: order.limit_gtd.expire_at: expiry must be between 1 second and 30 days after admission time",
#      "details":[{"type":"orders.v1.ErrorDetail", ...}]}
```

REST: the problem `detail` names the REST field.

```bash
curl -sS -X POST https://<api-host>/v1/orders \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer <token>' \
  -d '{"order":{"symbol":"BTC-USDT","side":"BUY","baseQty":"0.0001","limitGtd":{"price":"70000","expireAt":"2026-01-01T00:00:00Z"}}}'
# 400 {"code":"VALIDATION_ERROR",
#      "detail":"validation error: order.limitGtd.expireAt: expiry must be between 1 second and 30 days after admission time",
#      "violations":[{"fieldPath":"order.limitGtd.expireAt","ruleId":"range", ...}], ...}
```

## Migration

None required. Keep branching on the typed error code (`ErrorDetail.code`
over ConnectRPC, the problem `code` over REST) and on the violations' field
paths and rules. Use the message only for display. Code that compared the
message with the old generic text no longer matches it.
