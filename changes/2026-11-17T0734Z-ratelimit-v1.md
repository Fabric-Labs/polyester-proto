## What and why

Trading reads are now rate limited per account, as order previews already
are. They share one read limit, policy class `TRADING_READ`, with
`orders.v1.OrdersService/PreviewOrder`. The limit belongs to the root
account: the root account, all of its subaccounts and every API key and
session share it. A subaccount or API key cannot add to it. Clients that read
often should subscribe to the private order stream instead of polling.

The read limit is 100 units a second with a burst of 200, for every VIP tier.
Each read's cost is fixed before it runs, from what it asks for, not from the
rows it returns:

| Read | Cost in units |
| --- | --- |
| `orders.v1.OrdersReadService/GetOpenOrders`, REST `GET /v1/orders/open` | 1 per 100 rows the `limit` asks for, rounded up (default page 1) |
| `orders.v1.OrdersReadService/GetOrderHistory`, REST `GET /v1/orders/history` | 2 per 100 rows the `limit` asks for, rounded up |
| `orders.v1.OrdersReadService/GetUserTrades`, REST `GET /v1/spot/trades` | 2 per 100 rows the `limit` asks for, rounded up |
| `orders.v1.OrdersReadService/GetOrder`, REST `GET /v1/spot/orders/{order_id}` | 1 |
| `orders.v1.OrdersReadService/GetBatchReplaceStatus` | 1 |
| `triggers.v1.TriggersService/GetTrigger`, REST `GET /v1/triggers/{trigger_id}` | 1 |
| `triggers.v1.TriggersService/ListTriggers`, REST `GET /v1/triggers` | 1 per 100 rows the `limit` asks for, rounded up |
| `triggers.v1.TriggersService/ListTriggerEvents`, REST `GET /v1/triggers/{trigger_id}/events` | 2 per 100 rows the `limit` asks for, rounded up |
| `ratelimit.v1.RateLimitService/GetTradingRateLimits`, REST `GET /v1/trading/rate-limits` | 1 |
| `fees.v1.FeeService/GetSpotFeeRates`, REST `GET /v1/spot/fee-rates` | 1 per 100 symbols returned, rounded up |
| `orders.v1.OrdersService/PreviewOrder` (unchanged) | 1 |

A read over the limit is refused and not served:

- ConnectRPC: `resource_exhausted` with the `polyester.ratelimit.v1.RateLimitDetail`
  error detail (`reason` `QUOTA_EXCEEDED`, `operation_id`, `policy_class`
  `TRADING_READ`, `scope`, `limit`, `remaining`, `retry_after_ms`,
  `policy_version`).
- REST: HTTP 429 with the problem code `RATE_LIMIT_EXCEEDED` and the same
  decision in the problem's `rateLimit` member (`operationId`, `policyClass`,
  `reason`, `scope`, `limit`, `remaining`, `retryAfterMs`, `policyVersion`;
  the integers as decimal strings).

Both carry the `Retry-After`, `RateLimit-Limit`, `RateLimit-Remaining`,
`RateLimit-Reset` and `X-Polyester-RateLimit-Policy-Version` headers. When
the limit cannot be checked, reads are served; an order preview is refused
`unavailable` (REST 503 `RATE_LIMIT_AUTHORITY_UNAVAILABLE`) as before.

Clients can discover the read limit:

- `TradingRateLimitClass` gains `TRADING_RATE_LIMIT_CLASS_READ` (REST `READ`).
- `GetTradingRateLimits` returns three `rules`, placement, cancellation and
  read, and up to three `api_key_rules`, in the same order. The read rule is
  the root account's, also when a subaccount is selected.
- `GetRateLimitConfig` returns 33 rules, one per class (cancellation,
  placement, read) for each of VIP0 through VIP10.

## How clients use it

Read the limits in force:

```bash
curl -sS https://<api-host>/ratelimit.v1.RateLimitService/GetTradingRateLimits \
  -H 'Authorization: Bearer <session-token>' \
  -H 'Content-Type: application/json' -d '{}'
curl -sS https://<api-host>/v1/trading/rate-limits \
  -H 'Authorization: Bearer <session-token>'
```

The response's read rule:

```json
{"policyClass": "TRADING_RATE_LIMIT_CLASS_READ", "vipTier": 0,
 "quotaWeight": "100", "periodMs": "1000", "burstWeight": "200"}
```

REST spells the class `READ` and shows the same numbers as decimal strings.

Reads are called as before. A page of 1000 open orders costs 10 units, a
page of 1000 fills 20:

```bash
curl -sS https://<api-host>/orders.v1.OrdersReadService/GetOpenOrders \
  -H 'Authorization: Bearer <session-token>' \
  -H 'Content-Type: application/json' -d '{"limit": 1000}'
curl -sS 'https://<api-host>/v1/spot/trades?limit=1000' \
  -H 'Authorization: Bearer <session-token>'
```

On a refusal, wait `Retry-After` seconds (or `retry_after_ms`) before the
next read.

## Migration

1. Handle `resource_exhausted` / HTTP 429 `RATE_LIMIT_EXCEEDED` on every read
   listed above, as on order creation: back off for `Retry-After` and retry.
2. A client that polls should use the private order stream, or poll less
   often and with smaller pages; every subaccount and API key of a root
   account draws on the same read limit.
3. Accept a third rule class: `GetTradingRateLimits` now returns three
   `rules` and `GetRateLimitConfig` 33. Select rules by `policy_class`
   instead of by position or count. A client that decodes responses with a
   JSON parser that rejects unknown enum names must update to an SDK that
   knows `TRADING_RATE_LIMIT_CLASS_READ` (REST `READ`); binary protobuf
   clients decode it unchanged.
