## What and why

A `ModifyTrigger` that names no field to change, with or without its
symbol, now answers `ERROR_CODE_TRIGGER_PATCH_EMPTY`, the code the trading
engine answers for the same request, instead of the generic
`ERROR_CODE_VALIDATION_ERROR`. Its field violation no longer names a field:
its `field_path` is empty and its `rule_id` is `patch_empty`. Before, the
violation named `trigger`, which is not a field of the request.

The transport status is unchanged: ConnectRPC answers `INVALID_ARGUMENT` and
REST answers HTTP 400. The trigger is not modified.

## How clients use it

A modify with no field to change:

```http
POST /triggers.v1.TriggersService/ModifyTrigger
Content-Type: application/json

{"triggerId":"1234567890123456789"}
```

answers `invalid_argument` with an `orders.v1.ErrorDetail` whose `code` is
`ERROR_CODE_TRIGGER_PATCH_EMPTY` and whose one violation has an empty
`fieldPath` and `ruleId` `patch_empty`. Adding only `symbolId` answers the
same.

REST answers `PUT /v1/triggers/{trigger_id}` with the body `{}`, or with only
`{"symbol":"BTC-USDT"}` (or the `symbol` query parameter), with HTTP 400:

```json
{"status":400,"code":"TRIGGER_PATCH_EMPTY","detail":"no patch fields provided","violations":[{"fieldPath":"","ruleId":"patch_empty","message":"no patch fields provided"}]}
```

A modify names a field to change when it sets `trigger_price_ticks`
(REST `triggerPrice`), a trailing distance, `activation_price_ticks`
(REST `activationPrice`) or a slippage cap.

## Migration

1. A client that matched `ERROR_CODE_VALIDATION_ERROR` (REST
   `VALIDATION_ERROR`) for a `ModifyTrigger` with no field to change must
   match `ERROR_CODE_TRIGGER_PATCH_EMPTY` (REST `TRIGGER_PATCH_EMPTY`).
2. A client that read the violation's field path `trigger` for this refusal
   must accept an empty field path.

Clients that matched only the transport status, or that never send an empty
modify, need no change.
