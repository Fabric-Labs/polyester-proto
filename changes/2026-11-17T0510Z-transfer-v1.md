## What and why

Creating an internal transfer over REST, one at a time or as a batch, now
answers a missing fresh step-up or missing recent MFA with the specific auth
code, the same code ConnectRPC already carries in `auth.v1.AuthErrorDetail`
and the same answer `GET /v1/trading/internal-transfers` gives. Before, REST
answered both with the generic `PERMISSION_DENIED`, so a client could not tell
which prompt to show.

| Refusal on `POST /v1/trading/internal-transfers` and `POST /v1/trading/internal-transfers/batch` | Before | Now |
| --- | --- | --- |
| The transfer needs a fresh step-up the request does not carry, or carries one that is not valid | `403` `PERMISSION_DENIED` | `403` `AUTH_STEP_UP_REQUIRED` |
| The transfer needs a recently MFA-elevated session | `403` `PERMISSION_DENIED` | `403` `AUTH_MFA_ELEVATION_REQUIRED` |

The status stays `403`. The `type` and `title` follow the code:

- step-up: `https://polyester.dev/problems/permission-denied` →
  `https://polyester.dev/problems/auth-step-up-required`;
- MFA elevation: `https://polyester.dev/problems/permission-denied` →
  `https://polyester.dev/problems/auth-mfa-elevation-required`;
- `title`: `Permission Denied` → `Forbidden`.

Every other `PERMISSION_DENIED` refusal, such as a caller without access to
the selected subaccount, is unchanged. ConnectRPC is unchanged: these
refusals are still `permission_denied` with the `auth.v1.AuthErrorDetail`
code and the `transfer.v1.ErrorDetail` code `ERROR_CODE_PERMISSION_DENIED`.

## How clients use it

Branch on `code`, and prompt for a fresh step-up or for MFA accordingly, then
retry with the same `idempotencyKey`:

```text
POST /v1/trading/internal-transfers
{"destinationSmartAccountAddress":"0x2222222222222222222222222222222222222222",
 "assetId":7,"amount":"1","idempotencyKey":"transfer-1"}

403 application/problem+json
{"type":"https://polyester.dev/problems/auth-step-up-required","title":"Forbidden",
 "status":403,"detail":"fresh step-up required","code":"AUTH_STEP_UP_REQUIRED"}
```

A missing recent MFA answers the same way with `"code":"AUTH_MFA_ELEVATION_REQUIRED"`,
`"type":"https://polyester.dev/problems/auth-mfa-elevation-required"` and
`"detail":"MFA session elevation required"`. A fresh step-up is sent in the
`X-Auth-Step-Up` header.

## Migration

A REST client that read `PERMISSION_DENIED` (or the `permission-denied` type)
from these two routes as "show a step-up or MFA prompt" must match
`AUTH_STEP_UP_REQUIRED` and `AUTH_MFA_ELEVATION_REQUIRED` (or their types)
instead. Keep treating `PERMISSION_DENIED` as a refusal that a step-up does not
fix. ConnectRPC clients need no change.
