## What and why

The REST trigger list, `GET /v1/triggers`, now names each trigger's
self-trade prevention mode `selfTradePreventionMode`, as the single-trigger
read `GET /v1/triggers/{trigger_id}`, the trigger create request and the
ConnectRPC JSON do. Before, the list named it `stpMode`, so a client that read
both endpoints with one trigger model lost the field on one of them. Only the
REST list's response field name changes: no message, field or enum changes,
and the value set is unchanged.

## How clients use it

Read the mode from `selfTradePreventionMode` on every REST trigger read. The
REST list:

```http
GET /v1/triggers?limit=50
```

```json
{"triggers": [{"triggerId": "<trigger ID>", "selfTradePreventionMode": "EXPIRE_MAKER"}], "nextPageToken": "<cursor>"}
```

The same list over ConnectRPC, whose answer is unchanged:

```http
POST /triggers.v1.TriggersService/ListTriggers
{"limit": 50}
```

```json
{"triggers": [{"triggerId": "<trigger ID>", "selfTradePreventionMode": "EXPIRE_MAKER"}], "nextPageToken": "<cursor>"}
```

`GET /v1/triggers/{trigger_id}` and `/triggers.v1.TriggersService/GetTrigger`
answer the same field under `trigger`. Paging is unchanged: `limit` defaults
to 100 and is at most 1000; triggers come newest first (creation time, then
trigger ID, descending); pass the answer's `nextPageToken` as `pageToken` for
the next page, and an empty `nextPageToken` ends the list. The cursor is bound
to the account, sub-account scope, filters and sort order.

## Migration

A REST client that reads `stpMode` from `GET /v1/triggers` must read
`selfTradePreventionMode` instead. REST order reads keep `stpMode`.
