## What and why

A refusal for a missing permission now names the action to grant. Before,
internal transfers and dust conversions refused such a request with the
message `forbidden`. Now the message names the action and who lacks it, in
the same words the other account APIs use:

- the API key's policy: `API key policy does not grant CONVERT_DUST`;
- the sub-account's policy: `Subaccount policy does not grant INTERNAL_TRANSFER`;
- a session's sub-account role: `Your subaccount role does not grant CONVERT_DUST`.

The actions named are `INTERNAL_TRANSFER` (creating transfers and
batches), `CONVERT_DUST` (quoting, converting and reading conversions) and
`READ_BALANCES` (listing dust balances). These error codes don't change:
ConnectRPC answers `permission_denied` with `ErrorDetail` code
`PERMISSION_DENIED`, or `POLICY_DENIED` for a sub-account role, and REST
answers HTTP 403 with the same `code`.

One code does change. `GetInternalTransferBatch`
(`GET /v1/trading/internal-transfers/batch`) answered `NOT_FOUND` to an API
key whose policy does not grant `READ_INTERNAL_TRANSFERS`. It now refuses
such a key `PERMISSION_DENIED` with `API key policy does not grant
READ_INTERNAL_TRANSFERS`, for every request ID: the key can read no batch,
and the answer is the same whether the batch exists or not. A caller allowed
to read transfers still gets `NOT_FOUND` for a batch it may not read and for
an unknown one.

## How clients use it

A client whose API key's policy lacks `CONVERT_DUST`:

```http
POST /transfer.v1.DustConversionService/ListDustConversions
{}
-> 403 {"code": "permission_denied", "message": "API key policy does not grant CONVERT_DUST", "details": [...]}
   (the transfer.v1.ErrorDetail in details still carries ERROR_CODE_PERMISSION_DENIED)

GET /v1/trading/dust/conversions
-> 403 {"type": "https://polyester.dev/problems/permission-denied", "title": "Permission Denied",
        "status": 403, "detail": "API key policy does not grant CONVERT_DUST", "code": "PERMISSION_DENIED"}
```

To fix the refusal, grant the named action on the API key's policy or the
sub-account's policy, or give the session a sub-account role that includes
it.

## Migration

Clients that matched the literal message `forbidden` should match the error
code instead; those codes and HTTP statuses are unchanged.

A client reading batches with an API key should treat `PERMISSION_DENIED`
from `GetInternalTransferBatch` as "grant `READ_INTERNAL_TRANSFERS` on the
key's policy", not as an unknown batch. It answered `NOT_FOUND` before.
