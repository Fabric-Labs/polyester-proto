## What and why

Each account now has its own trading read limit: the root account and each
subaccount separately. Until now a root account, all of its subaccounts and
every API key and session shared one read limit, so a market maker running
many subaccounts under one root was refused reads as soon as a few
subaccounts read full pages of fills. This deliberately reverses that rule
from the previous release; placement and cancellation limits already work
this way.

- Order, fill, trigger, trading-limit and fee reads, and order previews,
  cost units of the read limit of the account they read. That is the root
  account for a read of the root, and the subaccount for a read of a
  subaccount. Reading one subaccount no longer uses another's budget.
- A subaccount's read limit is its own read-limit override when it has one,
  else its root account's VIP tier read limit, whoever reads it, including a
  member invited to the subaccount. A root account's override covers the
  root account's own reads only. Subaccounts no longer read on it.
- An API key's read limit applies on top of the account's: a read or preview
  is refused when either is exhausted. It is the key's own override when it
  has one, else the read limit of the account the key reads.
- `GetTradingRateLimits` reports the selected account's own read rule,
  resolved as its placement and cancellation rules are, and the calling
  key's read rule in `api_key_rules`. Before, it reported the root account's
  read rule even for a selected subaccount.

The default read limit, unit costs and refusals are unchanged: 100 units a
second with a burst of 200 for every VIP tier, one unit per 100 rows a list's
`limit` asks for (two for order history, fills and trigger events), and
`resource_exhausted` (REST 429 `RATE_LIMIT_EXCEEDED`) with `RateLimitDetail`
over the limit. A refusal's `scope` is `ACCOUNT` for a read of the root
account, `SUBACCOUNT` for a read of a subaccount, or `API_KEY`.

This is a behaviour change, not a wire change: no message, field or error
code changed. A subaccount now reads at its own read-limit override or at
its VIP tier's limit, never on its root account's override. A subaccount can
therefore get a lower read limit than before when its root account has a
raised read limit and the subaccount has none of its own, or when the
subaccount has its own read-limit override below the root's.

## How clients use it

Nothing changes in the calls. Read the limit that applies to an account
with `GetTradingRateLimits`, selecting the subaccount when it is not the
caller's bound one:

```text
POST /ratelimit.v1.RateLimitService/GetTradingRateLimits
{"subaccountId": "<subaccount public ID, decimal string>"}

GET /v1/trading/rate-limits?subaccountId=<subaccount public ID, base58>
```

The third entry of `rules` (`TRADING_RATE_LIMIT_CLASS_READ`, REST `READ`) is
that account's read limit, shared by every API key and session reading for
it. The third entry of `api_key_rules`, present for an API key, is the
key's own read limit, enforced on top of the account's.

## Migration

Clients whose root account or subaccounts have a read limit other than the
default should check each subaccount they read:

1. Call `GetTradingRateLimits` for each subaccount and read its `READ` rule.
2. Where that rule is lower than the subaccount needs, either request a
   read-limit override for that subaccount, or pace that subaccount's reads
   to its own `READ` rule.
3. Pace reads per account (the root account and each subaccount separately)
   rather than across all subaccounts of a root, and per API key when the key
   has its own read rule.

Clients whose accounts all read at the default limit need no change: each
account now has the whole default limit to itself.
