## What and why

A sub-account's owner can no longer lose the owner role through member calls.
These four calls now refuse with the new error
`auth.v1.AuthErrorCode.AUTH_SUBACCOUNT_OWNER_ROLE_LOCKED = 47` when they
target the sub-account's owner:

- `InviteSubaccountMember` naming the owner as invitee;
- `RespondSubaccountInvite` accepting an invite whose grantee is the owner,
  including an invite created before this change (declining or canceling
  such an invite still works);
- `UpdateSubaccountMemberRole` changing the owner's role, for example a
  downgrade to ADMIN or VIEWER, whether the owner or a delegated admin calls
  it;
- `RemoveSubaccountMember` removing the owner. This call refused already,
  but with `AUTH_INVALID_REQUEST`.

Before, inviting the owner and accepting could replace their owner role with
the invited role, so an owner could lose control of their own sub-account.

Released in 9.2.

## How clients use it

The refusal is ConnectRPC `failed_precondition` with an
`auth.v1.AuthErrorDetail` whose `code` is `AUTH_SUBACCOUNT_OWNER_ROLE_LOCKED`.
On REST it is HTTP 412 `application/problem+json` with
`"code": "AUTH_SUBACCOUNT_OWNER_ROLE_LOCKED"` and the title "Subaccount Owner
Role Locked". The request changes nothing.

ConnectRPC JSON carries the account IDs as decimal strings of their `fixed64`.
REST paths take their base58 public IDs. The examples write them as
`<sub-decimal>` and `<owner-decimal>`, or `<sub-base58>` and
`<owner-base58>`.

```bash
# ConnectRPC
curl -sS https://<api-host>/auth.v1.SubaccountService/UpdateSubaccountMemberRole \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer <token>' \
  -d '{"subaccountId": "<sub-decimal>", "granteeAccountId": "<owner-decimal>", "role": "VIEWER"}'
# {"code": "failed_precondition", "details": [AuthErrorDetail {code: AUTH_SUBACCOUNT_OWNER_ROLE_LOCKED}]}

# REST
curl -sS -X PATCH https://<api-host>/v1/auth/subaccounts/<sub-base58>/members/<owner-base58> \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer <token>' \
  -d '{"role": "VIEWER"}'
# HTTP 412 {"status": 412, "code": "AUTH_SUBACCOUNT_OWNER_ROLE_LOCKED",
#           "title": "Subaccount Owner Role Locked", ...}
```

The other REST routes:

- `POST /v1/auth/subaccounts/{subaccount_id}/invites`
- `POST /v1/auth/subaccounts/invites/{invite_id}:respond`
- `DELETE /v1/auth/subaccounts/{subaccount_id}/members/{grantee_account_id}`

The step-up MFA rules of these calls are unchanged. `ListSubaccountMembers`
still lists the owner with role `OWNER`.

## Migration

Clients that matched `AUTH_INVALID_REQUEST` (Connect `invalid_argument`) when
removing the owner must match `AUTH_SUBACCOUNT_OWNER_ROLE_LOCKED` (Connect
`failed_precondition`, REST 412) instead. Nothing else changes: no valid call
is newly refused, because changing the owner's role was never a supported
outcome.
