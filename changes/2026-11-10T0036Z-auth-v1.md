## What and why

API keys now need an account permission on their API-key policy for the deposit-address, sub-account and Guard Signer calls, and for the main account's address book. Before, any active key could make these calls, with or without a policy. `PolicyAction` gains seven account permissions, valid on API-key policies only:

| Permission | Calls it opens to an API key |
| --- | --- |
| `CREATE_DEPOSIT_ADDRESS` | `CreateDepositAddress` |
| `READ_DEPOSIT_ADDRESSES` | `ListDepositAddresses` |
| `READ_SUBACCOUNTS` | `ListSubaccounts`, `GetSubaccount` |
| `READ_SUBACCOUNT_ACTIVITY` | `ListSubaccountActivity` |
| `READ_SUBACCOUNT_MEMBERS` | `ListSubaccountMembers`, and the members expansion of `GetSubaccount` |
| `READ_SUBACCOUNT_INVITES` | `ListSubaccountInvites`, and the invites expansion of `GetSubaccount` |
| `READ_GUARD_SIGNER_STATUS` | `GetGuardSignerStatus` |

Each applies within the key's scope: a key scoped to the main account reaches the main account and the sub-accounts it owns, and a key scoped to a sub-account reaches only that sub-account. `ListSubaccountMembers` now accepts API keys. `CREATE_DEPOSIT_ADDRESS` returns at its earlier enum value, 10.

The main account's address book now needs `READ_ADDRESS_BOOK` (or `MANAGE_ADDRESS_BOOK`) on the policy of a key scoped to the main account, as a sub-account's book already did: `GetAddressBookView`, `ListAddressBookEntries`, `ListTransferCounterparties`, `ListTransferDestinations`, `ListInternalTransferWhitelistEntries` and `GetWithdrawWhitelistView` without a sub-account.

`GetGuardSignerStatus` no longer answers an API key for a sub-account another main account owns, even when that main account shares it with the key's main account. The refusal is `PERMISSION_DENIED` with `AUTH_API_KEY_ACCESS_DENIED`. The main account's own session still reads it.

## How clients use it

Grant the permissions on the key's API-key policy with an interactive session, for example over ConnectRPC `/auth.v1.PolicyService/UpdateApiPolicy`:

```json
{
  "policyId": "<decimal-fixed64-policy-id>",
  "policy": {"actions": ["READ_SPOT", "READ_ADDRESS_BOOK", "READ_SUBACCOUNTS", "READ_DEPOSIT_ADDRESSES", "CREATE_DEPOSIT_ADDRESS"]},
  "updateMask": "actions",
  "expectedRevision": "3"
}
```

The key then signs the calls as any API-key request, for example `GET /v1/auth/subaccounts`, `GET /v1/auth/subaccounts/{subaccount_id}/members` or `GET /v1/chain/deposit-addresses`.

A key without the permission is refused with `PERMISSION_DENIED` and `AUTH_API_KEY_ACCESS_DENIED`, and the message names the missing permission. A main-account address-book read without `READ_ADDRESS_BOOK` is refused with `PERMISSION_DENIED` and `AUTH_SUBACCOUNT_ACCESS_DENIED`, as a sub-account's already was. `GetSubaccount` omits the members and invites expansions for a key without their permission rather than failing. A target outside the key's scope answers `NOT_FOUND`.

## Migration

1. **API keys without a policy lose these calls:** `CreateDepositAddress`, `ListDepositAddresses`, `ListSubaccounts`, `GetSubaccount`, `ListSubaccountActivity`, `ListSubaccountInvites`, `GetGuardSignerStatus`, and, for keys scoped to the main account, the main account's address-book reads listed above. To keep them, attach an API-key policy that grants the permissions in the table above (and `READ_ADDRESS_BOOK` for the address book).
2. Existing API-key policies were granted the seven permissions when this change was deployed, and policies attached to a key scoped to the main account were also granted `READ_ADDRESS_BOOK` unless they already read the address book, so keys with a policy keep their access.
3. A client that creates or updates API-key policies must include these permissions for keys that make these calls; a new policy grants none of them unless named.
4. A key that read Guard Signer status for a sub-account another main account shares with its main account must use a session token, or a key of the main account that owns the sub-account.
5. A client that rewrites a policy's whole `actions` list must keep the account permissions it read back, or the update removes them.
