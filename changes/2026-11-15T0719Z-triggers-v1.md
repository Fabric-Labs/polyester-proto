## What and why

An OCO's client list ID now follows the same rule as a client order ID: 1 to
36 ASCII characters using letters, digits, period, underscore, colon, slash,
or hyphen (`^[A-Za-z0-9._:/-]{1,36}$`). The rule covers
`OcoIntent.client_list_id` in `CreateOco` and the `client_list_id` filter of
`ListTriggers`, on ConnectRPC, REST and the trading WebSocket alike.

The contract used to say "at most 36 bytes in UTF-8", which no create path
honored. Non-ASCII IDs were already refused, but with a client trigger ID
error. The trading WebSocket already enforced the set above, while ConnectRPC
and REST admitted spaces and other ASCII punctuation. Every path now applies
the same rule. A refused ID is answered differently on each path:

| Path | Answer |
| --- | --- |
| ConnectRPC `CreateOco` | `INVALID_ARGUMENT` with an `ErrorDetail` of code `ERROR_CODE_VALIDATION_ERROR` and a violation with `field_path` `oco.client_list_id` and `rule_id` `string.pattern` (`string.min_len` when empty, `string.max_len` when longer than 36) |
| REST `POST /v1/triggers/oco` | HTTP 400, problem `code` `VALIDATION_ERROR`, with a `violations` entry with `fieldPath` `oco.clientListId` and the same `ruleId` |
| ConnectRPC `ListTriggers` | `INVALID_ARGUMENT`. The message names `client_list_id` and the details carry the field violation, but there is no `ErrorDetail` code |
| REST `GET /v1/triggers` | HTTP 400, problem `code` `VALIDATION_ERROR`. The field is named only in `detail` (`validation error: client_list_id: does not match regex pattern ...`); there are no `violations` |
| Trading WebSocket `CreateOco`, SBE and protobuf frames | `CommandReject` with code `BAD_REQUEST` and detail `client_list_id must be 1 to 36 supported ASCII characters`, before the command takes its seq |

`TRIGGER_CANCEL_REASON_OCO` is now documented for an OCO created with
`CreateOco` too: when one leg's order trades the OCO's last quantity, the
other leg ends `CANCELED` with this reason. The behavior is unchanged; only
the description was incomplete.

## How clients use it

Send a client list ID from the allowed set, exactly as given:

```http
POST /triggers.v1.TriggersService/CreateOco
Content-Type: application/json

{
  "oco": {
    "symbolId": 1,
    "side": "SELL",
    "qtyScaled": "100000",
    "clientListId": "tp-sl:btc/2026-11-15_1",
    "takeProfit": {"triggerPriceTicks": "78000000000000", "child": {"marketIoc": {}}},
    "stopLoss": {"triggerPriceTicks": "72000000000000", "child": {"marketIoc": {}}}
  }
}
```

REST: `POST /v1/triggers/oco` with `clientListId` in the body. Find the OCO
later with `GET /v1/triggers?symbol=BTC-USDT&clientListId=tp-sl:btc/2026-11-15_1`
or `ListTriggers` with `client_list_id`, which takes the same IDs.

## Migration

1. Clients that build client list IDs from letters, digits and `. _ : / -`
   need no change.
2. Clients that put spaces, other punctuation, or non-ASCII characters in a
   client list ID must map them into the allowed set before calling
   `CreateOco`. Such an ID is now refused on every path.
