## What and why

REST policy updates can now remove the per-order notional cap by sending an explicit null. Omitting the field keeps the existing cap. This matches the existing ConnectRPC field-mask clear operation.

## How clients use it

Send `PATCH /v1/auth/policies/subaccounts/{policy_id}` with the policy's latest revision in `If-Match`, for example `If-Match: "7"`, and this JSON body:

```json
{"maxOrderNotional": null}
```

To set a cap instead, supply a positive decimal string in quote units with six decimal places of precision; additional trailing zeros are accepted. Zero and negative inputs remain refused with `AUTH_INVALID_REQUEST`. After clearing, GET reports `maxOrderNotional: "0"`, the existing representation of no explicit cap. Other policy fields remain unchanged.

ConnectRPC already supports the same clear operation through `/auth.v1.PolicyService/UpdateSubaccountPolicy`. Select the field and omit its candidate value:

```json
{
  "policyId": "<decimal-fixed64-policy-id>",
  "policy": {},
  "updateMask": "maxOrderNotional",
  "expectedRevision": "7"
}
```

Selecting the field with `"policy": {"maxOrderNotional": null}` also clears it in Connect JSON. Omitting it from the mask leaves it unchanged. ConnectRPC notional amounts use integer quote microunits (one unit is 0.000001 quote units). REST path identifiers use the policy's base58 public ID; ConnectRPC JSON uses the decimal fixed64 ID.

## Migration

None: existing set and omitted-field updates retain their behavior. Clients that remove a cap should send explicit null over REST or use the selected field-mask operation over ConnectRPC, without numeric sentinel values.
