## What and why

`AbandonInternalTransferBatch` makes the absence of a batch under an
idempotency key final. A client that recorded a key may not know whether its
`BatchCreateInternalTransfers` call was ever sent, and a delayed call can
still land after a read by key answered `NOT_FOUND`. Abandoning the key
settles it:

- If a batch was submitted under the key, the call answers that batch's
  outcome exactly as `GetInternalTransferBatch` reads it by key, and changes
  nothing.
- Otherwise it records the key as abandoned and answers `BATCH_ABANDONED`.

`BATCH_ABANDONED`, a new `InternalTransferBatchStatus` value, is final: it
guarantees that no funds moved under the key and that none ever will. Branch
on it as "never moved", not as an error. From then on:

- every `BatchCreateInternalTransfers` under the key, a retry included, is
  refused `FAILED_PRECONDITION` with the new
  `ERROR_CODE_IDEMPOTENCY_KEY_ABANDONED`, and nothing moves;
- `GetInternalTransferBatch` by that key, and every later abandon of it,
  answers `BATCH_ABANDONED`, with no request ID and no legs.

A create and an abandon that race on one key end in exactly one of the two
outcomes: the batch is processed under the key, and the abandon answers it,
or the key is abandoned and nothing moved.

The key is scoped as `BatchCreateInternalTransfers` scopes it: to the
session's account, or to the API key. The caller needs the `INTERNAL_TRANSFER`
permission, since abandoning consumes a key a create could use. To answer an
existing batch, it also needs the read permission on every source account of
that batch, refused as the key read refuses it (`PERMISSION_DENIED`, or
`UNAVAILABLE` while the permission cannot be decided yet). No MFA is required:
the call never moves funds. Each call counts as one
`BatchCreateInternalTransfers` admission against the rate limit.

## How clients use it

```http
POST /transfer.v1.InternalTransferService/AbandonInternalTransferBatch
Content-Type: application/json

{"idempotencyKey": "rebalance-2026-11-24-001"}
```

REST: `POST /v1/trading/internal-transfers/batch/abandon` with the same body;
`status` reads `ABANDONED`. A later batch under the key is refused HTTP 400
with code `IDEMPOTENCY_KEY_ABANDONED`.

The response has the shape of `GetInternalTransferBatchResponse`:
`request_id`, `status` and `legs`. For `BATCH_ABANDONED`, `request_id` is
empty and `legs` is empty. Repeating the call is safe: after a lost answer,
call it again with the same key.

## Migration

None for existing calls. Clients that switch on `InternalTransferBatchStatus`
must accept `BATCH_ABANDONED`. It appears only for keys the caller abandoned.
