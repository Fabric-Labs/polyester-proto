## What and why

The API reference now describes how each operation authenticates and which
values depend on the environment. No request, response or behavior changes.

- The OpenAPI reference declares the API-key signature as three header
  security schemes, `ApiKeyIdAuth` (`X-API-KEY-ID`), `ApiKeyTimestampAuth`
  (`X-API-TIMESTAMP`) and `ApiKeySignatureAuth` (`X-API-SIGNATURE`). Each
  operation lists one security alternative per credential it accepts:
  `BearerAuth` for a session token, the three API-key headers together for
  an API key, `BrokerApiKeyAuth` for a broker API key. An operation that
  lists only `BearerAuth` accepts session tokens only.
- Examples that depend on the environment show placeholders: `<app-host>`
  for the app host in the wallet sign-in challenge and message, the passkey
  `rpId` and the sub-account authorization message, `<environment>` for its
  audience, and `<polyester-chain-id>` for the Polyester chain ID inside
  those messages. Replace them with your environment's app host,
  environment name and Polyester chain ID before you use an example.
- Reference candle prices in the `GetCandles` REST example are decimals, as
  the API returns them.
- `CreateSubaccountChallengeResponse.polyester_chain_id` differs per
  environment: read it from the response instead of assuming a fixed value.

## How clients use it

Read an operation's `security` to choose its credential. For a session
token:

```http
Authorization: Bearer <session token>
```

For an API key, send all three signature headers:

```http
X-API-KEY-ID: <key id>
X-API-TIMESTAMP: <unix milliseconds>
X-API-SIGNATURE: <signature>
```

## Migration

None: the wire contract is unchanged. Clients that hard-coded devnet's
Polyester chain ID should use the `polyester_chain_id` the challenge
response returns.
