## What and why

Cancel-all and the dead-man switch can now stop the account's waiting
triggers as well as its orders, so one request halts all automated trading.

- `CancelAllOrdersRequest.include_triggers` and
  `CancelAllAfterRequest.include_triggers` (default `false`): when `true`,
  every stop-loss, take-profit, trailing stop, TWAP, ladder and attached
  take-profit, stop-loss or trailing leg on the matched symbols whose orders
  trade on the side filter, created before the request was accepted (for the
  switch, before its expiry time, even when the expiry is processed later),
  ends canceled with reason
  `TRIGGER_CANCEL_REASON_CANCEL_ALL` and releases its reserved funds. Its open
  orders are canceled with the others, and none places an order after the
  response (for the switch, after its expiry is processed). A trigger created
  at or after a switch's expiry time is not stopped by it.
- `CancelAllOrdersResponse.matched_triggers`: with `include_triggers`, the
  number of triggers that matched, each stopped unless `dry_run` is set; zero
  without it.
- `TriggerCancelReason.TRIGGER_CANCEL_REASON_CANCEL_ALL` (16): the reason
  such a trigger ends with.
- `TriggerFailureReason.TRIGGER_FAILURE_REASON_TRIGGER_STOPPING` (263): the
  `fire_refusal_reason` of an `EVENT_FIRE_REFUSED` when a trigger's condition
  was met while it was being stopped; it then ends canceled with
  `TRIGGER_CANCEL_REASON_CANCEL_ALL`.
- On the trading WebSocket, `CancelAllOrders` and `CancelAllAfter` take
  `includeTriggers` and `CommandAck` carries `matchedTriggers`.

Without `include_triggers` nothing changes: only orders are canceled and
triggers keep running.

## How clients use it

```http
POST /orders.v1.OrdersService/CancelAllOrders
{"requestId": "halt-1", "includeTriggers": true}
```

```http
POST /v1/orders/cancel-all
{"requestId": "halt-1", "includeTriggers": true}
```

The response's `matchedTriggers` counts the triggers stopped. A retry with
the same `requestId` must keep `includeTriggers` unchanged: it is part of the
request's criteria, and a retry with other criteria is refused with
`CONFLICT_IDEMPOTENCY_KEY_REUSE`. Set it on every arm or refresh of
`CancelAllAfter`; a disable ignores it.

## Migration

**ConnectRPC, REST and the trading WebSocket's protobuf frames:** none. The
new fields are additive and default to `false` or zero, which keeps today's
behavior; clients built on the previous contract keep working unchanged.

**Trading WebSocket SBE clients: must update.** The SBE schema moves from
version 49 to version 50: `CancelAllOrders` and `CancelAllAfter` gain
`includeTriggers` and `CommandAck` gains `matchedTriggers`, which changes
their fixed blocks. The socket decodes only the current schema version, so
from this release it refuses every frame of version 49 with `BAD_SBE`, whether
or not the client uses the new option.

1. Regenerate your SBE codecs from the version 50 `tradews` schema.
2. Encode `includeTriggers` as 0 in `CancelAllOrders` and `CancelAllAfter`
   to keep today's behavior, or 1 to stop triggers too.
3. Decode `CommandAck.matchedTriggers` (zero unless a cancel-all set
   `includeTriggers`).
4. Deploy the updated client when this release reaches your environment;
   version 49 frames are refused from then on.
