## What and why

Market data errors over ConnectRPC now carry their stable error code where
the published error catalog says: the error `message` is the code itself,
such as `PAGE_TOKEN_INVALID`, `BAD_REQUEST` or `UNKNOWN_SYMBOL`, with the
code's ConnectRPC status. Before, the message was free text and the code
reached clients only in the `X-Polyester-Error-Code` response header, so a
ConnectRPC client saw a generic `invalid_argument` or `not_found`. The header
is still sent, and now on every such error.

A new `marketdata.v1.ErrorDetail` keeps the human-readable reason. It is
attached only to errors the caller can correct (`BAD_REQUEST`,
`INVALID_ARGUMENT`, `UNKNOWN_SYMBOL`, `NOT_FOUND`, `PAGE_TOKEN_INVALID`); its
`reason` says what to fix, for example `timeframe SEC_1 has no index price
candles`. For `PAGE_TOKEN_INVALID` it tells a malformed `page_token` (`bad
page_token`) from one issued for another request (`page_token does not match
request`). Service-side failures (`UNAVAILABLE`, `UPSTREAM_ERROR`,
`PRICE_BAND_STALE`, `PRICE_BAND_UNKNOWN`) carry the code and no reason.
Request validation errors keep their field violations as well.

This applies to every error the service returns for a request it could read.
A request body ConnectRPC cannot decode, an unsupported content type or an
oversized body is refused with ConnectRPC's standard error, as on every
service. REST answers are unchanged: the problem body's `code` was already
the stable code.

## How clients use it

```bash
curl -sS https://<api-host>/marketdata.v1.MarketDataService/GetIndexPriceCandles \
  -H 'Content-Type: application/json' -H 'Connect-Protocol-Version: 1' \
  -d '{"symbolId":1,"timeframe":"MIN_1","limit":2,"pageToken":"bogus"}'
# 400 X-Polyester-Error-Code: PAGE_TOKEN_INVALID
# {"code":"invalid_argument","message":"PAGE_TOKEN_INVALID",
#  "details":[{"type":"marketdata.v1.ErrorDetail","value":"...","debug":{"reason":"bad page_token"}}]}
```

Branch on the code in `message`. Read `marketdata.v1.ErrorDetail.reason`
from the error details when present, and show it; never branch on its
wording.

## Migration

None required, but cursor handling can now be written as documented: when a
candle read (`GetCandles`, `GetCandlesColumns`, `GetIndexPriceCandles`)
fails with `PAGE_TOKEN_INVALID`, drop the stored `page_token` and request the
first page again. A client that classified that failure as a generic
`invalid_argument` now sees `PAGE_TOKEN_INVALID`. A client that displayed the
error message now shows the code; display `ErrorDetail.reason` instead when it
is present.
