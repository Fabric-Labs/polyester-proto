## What and why

A new API, `strategies.v1.StrategiesService`, lets a user, or a tool acting
for them, write, test and propose trading bots. A bot is a manifest
(settings, events, money limits and behaviour examples) plus code. The API:

- describes the bot format of a runtime version: the bot API reference, the
  manifest's JSON Schema, the allowed indicators and the limits
  (`GetStrategyReference`), and lists starting templates
  (`ListStrategyTemplates`); both are public and need no credentials;
- validates a bot and stores it as an immutable, content-addressed version
  (`ValidateStrategy`), runs its behaviour examples (`RunScenarios`),
  backtests it on past market data (`StartBacktest`, `GetBacktest`) and
  returns the review summary a user approves (`ExplainStrategy`);
- records a deploy proposal and returns the link to the website's deploy
  page (`ProposeDeploy`), and reports the deploy's progress
  (`GetDeployStatus`);
- reads the caller's bots, their recent decisions and their logs
  (`ListBots`, `GetBot`, `ListBotLogs`).

No call moves money, creates a subaccount, deploys a bot or stops one:
deploying takes the user's MFA and wallet signature on the deploy page.
Every call acts for the caller's main account.

`auth.v1.PolicyAction` gains three API-key permissions for this API. Each is
a main-account permission: it is honored only for an API key scoped to the
main account, and a sub-account policy refuses it.

- `READ_STRATEGIES = 46`: read strategy versions, backtests, review
  summaries, deploy proposals, bots and bot logs.
- `DRAFT_STRATEGIES = 47`: validate and store strategy versions, run their
  behaviour examples and start backtests. It never deploys, changes, stops or
  deletes a bot.
- `PROPOSE_STRATEGY_DEPLOY = 48`: record a deploy proposal. The user then
  deploys it on the website with MFA and a wallet signature; the permission
  never deploys a bot, creates a subaccount or moves funds.

They are dedicated permissions rather than aliases of trading ones, so a key
can draft and propose bots without trading rights, and none of them can move
money.

The contract is published ahead of the service: until the service is live,
its calls are not served.

## How clients use it

ConnectRPC only; there is no REST mapping yet. Amounts are exact decimal
strings with an asset symbol (`{"asset": "USDT", "amount": "50"}`), never
binary floats. Bot, backtest and proposal IDs are fixed64 public IDs
(decimal strings in JSON); `version_id` is an opaque string.

```json
POST /strategies.v1.StrategiesService/ValidateStrategy
{
  "name": "Weekly DCA",
  "manifest": {
    "markets": ["BTC/USDT"],
    "schedule": "mon 09:00 UTC",
    "settings": {"budget": {"kind": "quote", "asset": "USDT", "default": "50", "min": "10"}},
    "limits": {"max_order": {"asset": "USDT", "amount": "60"}, "max_open_gtc_orders": 2}
  },
  "code": "def on_timer(bot, state, timer):\n    ..."
}

{"versionId": "…", "runtimeVersion": "…", "valid": true, "moneyCard": {"budget": {"asset": "USDT", "amount": "50"}}}
```

```json
POST /strategies.v1.StrategiesService/ProposeDeploy
{
  "versionId": "…",
  "botName": "Weekly DCA",
  "settings": [{"name": "budget", "value": "50"}],
  "funding": [{"asset": "USDT", "amount": "500"}],
  "idempotencyKey": "propose-1"
}

{"proposalId": "123", "deployUrl": "https://<app-host>/…", "expiresAt": "…"}
```

- A bot with mistakes is not an error: `ValidateStrategy` returns
  `valid: false` with up to 50 `errors`, each with a location, a rule, a
  message and a hint.
- `StartBacktest` takes a required `idempotencyKey`: a retry with the same
  key and request returns the backtest the first call started, even when an
  unset window bound would now resolve to a longer window. Across keys, it
  returns the same `backtestId` for the same version, effective window,
  effective settings and effective initial balances:
  defaults count as their resolved values (an unset window bound as the
  longest window with data, a left-out setting as its default, empty
  `initialBalances` as the budget setting in the quote asset), balances are
  compared sorted by asset, and decimals in canonical form (`"50"` equals
  `"50.0"`). Changing the initial balances starts another backtest. Poll
  `GetBacktest` until `status` is `DONE` or `FAILED`.
- `ProposeDeploy` funds the bot from the main account, or from
  `fundingSubaccountId`, a subaccount of the caller's main account. The same
  `idempotencyKey` and request return the same proposal.
- `ListBots` pages newest first (default 50, max 200); `ListBotLogs` pages
  oldest first (default 100, max 200). Both use `pageToken` /
  `nextPageToken`.
- Errors carry a `strategies.v1.ErrorDetail` with a stable `code`, and
  `retryAfter`, `botCap`, `markets` or `shortfall` where they apply.

Grant the permissions in an API-key policy's `actions`, like any other
action:

```json
POST /auth.v1.PolicyService/CreateApiPolicy
{
  "policy": {
    "name": "Strategy drafting",
    "actions": ["READ_STRATEGIES", "DRAFT_STRATEGIES"]
  }
}
```

Policy reads list them in public enum order. A key whose policy lacks the
call's permission is refused with `PERMISSION_DENIED`
(`AUTH_API_KEY_ACCESS_DENIED`, "API key policy does not grant …"); a key
scoped to a subaccount is refused even when its policy grants it.

## Migration

None: the service and the three policy actions are new. A client that
renders policy actions should show an unknown value without failing, as for
any action it does not recognize.
