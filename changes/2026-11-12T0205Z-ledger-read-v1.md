## What and why

Order history, own trades and transfer history now distinguish an omitted upper time bound from an explicit epoch bound. An omitted upper bound is unbounded; an explicit bound at or before the Unix epoch returns an empty final page. `ListTransfersRequest.ts_max_us` gains optional presence at its existing field number, with the same name and units. The order and trade request fields already have optional presence.

## How clients use it

ConnectRPC JSON, with inclusive bounds in microseconds for transfers and nanoseconds for orders and trades:

```http
POST /ledger.read.v1.LedgerReadService/ListTransfers
{"tsMaxUs":"0"}

POST /orders.v1.OrdersReadService/GetOrderHistory
{"endTsNs":"0"}

POST /orders.v1.OrdersReadService/GetUserTrades
{"endTsNs":"0"}
```

REST equivalents:

```http
GET /v1/transfers?timestampMax=0
GET /v1/orders/history?endTime=1970-01-01T00:00:00Z
GET /v1/spot/trades?endTime=1970-01-01T00:00:00Z
```

Each returns no records and an empty continuation token. REST also accepts negative transfer upper bounds and pre-epoch order/trade upper dates as empty ranges. Omit the parameter or field for an unbounded query. REST order/trade lower dates at or before the epoch mean from the beginning. REST order/trade dates after `2262-04-11T23:47:16.854775807Z` are refused with `INVALID_START_TIME` or `INVALID_END_TIME`, rather than wrapping. Connect order/trade numeric bounds above `9223372036854775807` are refused with status `invalid_argument` and typed `orders.v1.ErrorDetail`: `violations[].field_path` identifies `start_ts_ns` or `end_ts_ns`, and `violations[].rule_id` carries the matching `INVALID_START_TIME` or `INVALID_END_TIME` code. Positive supported bounds remain inclusive. Default page size remains 100 and maximum 1000; ordering is unchanged. Reuse continuation tokens only with their original bounds and filters.

## Migration

Regenerate clients. Callers that used an explicit zero as an unbounded sentinel must omit the upper bound instead. In Go, `TsMaxUs` changes from `uint64` to `*uint64`: use `nil` for unbounded and a pointer to zero for epoch. Previously generated scalar clients may omit a binary zero when serializing; regenerate to request an explicit epoch reliably. Availability follows the release containing this change.
