## What and why

Balance charts and the root portfolio snapshot now return exact balances at
the 18-decimal ledger scale, the same `polyester.type.v1.U128` representation
`GetBalances` uses. The previous 7-decimal `uint64` fields could not carry a
balance above 1,844,674,407,370.9551615 whole units, so an account or root
portfolio holding more of one asset received an unavailable error for the
whole response instead of its balances.

- `BalanceSeries.balance_q` (field 3, `repeated uint64` at 1e7) is removed.
  `BalanceSeries.balance` (field 4, `repeated polyester.type.v1.U128`) replaces
  it: the exact balance at each point, aligned 1:1 with the implicit
  timestamps.
- `PortfolioAssetEquity.balance_q` (field 2, `uint64` at 1e7) is removed.
  `PortfolioAssetEquity.balance` (field 4, `polyester.type.v1.U128`) replaces
  it: the exact combined Funding and Trading balance across the master
  account and all owned subaccounts.

REST keeps the same property names. `series[].balance[]` of
`GET /v1/balances/history` and `assets[].balance` of
`GET /v1/equity/portfolio/snapshot` stay decimal strings in whole units of the
asset. They are now exact, with up to 18 decimal places instead of at most 7,
and trailing zeros trimmed.

## How clients use it

```json
POST /ledger.read.v1.LedgerReadService/GetBalanceHistory
{ "range": "DAY_7" }
```

Each `series[].balance[i]` is a `U128` `{ "hi": "...", "lo": "..." }`; the
balance in whole units is `((hi << 64) | lo) / 10^18`.

```json
POST /ledger.read.v1.LedgerReadService/GetPortfolioEquitySnapshot
{}
```

Each `assets[].balance` is a `U128` at the same 18-decimal scale.

`GET /v1/balances/history?range=7d` and `GET /v1/equity/portfolio/snapshot`
return the same balances as exact decimal strings, for example
`"4989049756000"` or `"1844674407370.955161549999999999"`.

## Migration

1. ConnectRPC and Protobuf clients: read `BalanceSeries.balance` instead of
   `balance_q`, and `PortfolioAssetEquity.balance` instead of `balance_q`.
   Decode each `U128` as `(hi << 64) | lo` and divide by 10^18, not 10^7. A
   client built on the previous contract decodes these responses with empty
   chart balances and zero snapshot balances, without an error, so update
   before relying on balances from either RPC.
2. REST clients: no field changes. Accept decimal strings with up to 18
   decimal places and values above 1,844,674,407,370.9551615; parse them with
   an arbitrary-precision decimal type rather than a 64-bit integer or float.
