## What and why

An order refused because spot trading is not allowed now says which policy
lacks the permission and what to enable. Effective permission is the API key's
policy and the sub-account's policy together; until now, both cases answered
`ERROR_CODE_POLICY_SPOT_TRADE_DENY` with one text, so a caller could not tell
which policy to change.

- New `ERROR_CODE_API_KEY_SPOT_TRADE_DENY` (78): the API key's policy does not
  grant `TRADE_SPOT` (Spot Trading Write). When neither policy grants it, this
  code is returned, so enable it on the API key first.
- `ERROR_CODE_POLICY_SPOT_TRADE_DENY` (23) now means only the sub-account's
  policy: it does not grant `TRADE_SPOT`, or the sub-account has no policy
  and is read-only.
- `ERROR_CODE_API_KEY_POLICY_REQUIRED` (27) is now returned for an API key
  with no policy attached, on order placement, cancellation and trigger
  controls; such a key has no permissions.
- An API key on the master account whose own market list excludes the pair is
  refused `ERROR_CODE_API_KEY_MARKET_DENY` (29) instead of
  `ERROR_CODE_POLICY_MARKET_DENY` (20).

The same codes and texts apply to REST, ConnectRPC and the trading WebSocket:
its `RejectCode` gains `API_KEY_SPOT_TRADE_DENY` (78), with the same number
as the API's error code, and its schema's semantic version becomes 2.3.0. The
schema version (49) is unchanged.

## How clients use it

Read the error code, not the text. A refused create over ConnectRPC:

```bash
curl -sS https://<api-host>/orders.v1.OrdersService/CreateOrder \
  -H 'Content-Type: application/json' -d '{"order": {...}}'
# 403 permission_denied
# {"code":"permission_denied",
#  "message":"The API key's policy does not allow spot trading. Enable Spot Trading Write (TRADE_SPOT) on the API key's policy.",
#  "details":[{"type":"orders.v1.ErrorDetail", ...}]}   # ErrorDetail.code = ERROR_CODE_API_KEY_SPOT_TRADE_DENY
```

REST `POST /v1/orders` answers 403 with `"code": "API_KEY_SPOT_TRADE_DENY"`
and the same `detail`. The texts:

| Code | Text |
| --- | --- |
| `API_KEY_SPOT_TRADE_DENY` | The API key's policy does not allow spot trading. Enable Spot Trading Write (TRADE_SPOT) on the API key's policy. |
| `POLICY_SPOT_TRADE_DENY` | The sub-account's policy does not allow spot trading. Enable Spot Trading Write (TRADE_SPOT) on the sub-account's policy. |
| `API_KEY_POLICY_REQUIRED` | This API key has no policy attached, so it has no permissions. Attach a policy to the API key that grants what it needs, such as Spot Trading Write (TRADE_SPOT). |

A preview of such an order answers `admissible: false` with the same code.

## Migration

This is a breaking change for clients that act on these error codes. No
message or field changes, but some refusals caused by the API key now return a
different code. The number is the same on REST, ConnectRPC and the trading
WebSocket `RejectCode`:

| Case | Before | Now |
| --- | --- | --- |
| The API key's policy does not grant Spot Trading Write (`TRADE_SPOT`), including when the sub-account's policy lacks it too | `POLICY_SPOT_TRADE_DENY` (23) | `API_KEY_SPOT_TRADE_DENY` (78) |
| The API key has no policy, for a spot-trading call | `POLICY_SPOT_TRADE_DENY` (23) | `API_KEY_POLICY_REQUIRED` (27) |
| The API key has no policy, for a read-only call (cancel-all dry run, trading WebSocket subscription) | `POLICY_SPOT_READ_DENY` (71) | `API_KEY_POLICY_REQUIRED` (27) |
| A master-account API key whose own market list excludes the pair, on order create, preview and batch create | `POLICY_MARKET_DENY` (20) | `API_KEY_MARKET_DENY` (29) |
| The sub-account's policy does not grant Spot Trading Write, or the sub-account has no policy | `POLICY_SPOT_TRADE_DENY` (23) | unchanged, `POLICY_SPOT_TRADE_DENY` (23) |

What to do:

1. Wherever you handle `POLICY_SPOT_TRADE_DENY` (23) as "the caller cannot
   trade", also handle `API_KEY_SPOT_TRADE_DENY` (78) and
   `API_KEY_POLICY_REQUIRED` (27). Tell the user to enable Spot Trading Write
   on the API key's policy for 78, to attach a policy to the API key for 27,
   and to enable it on the sub-account's policy for 23.
2. Wherever you handle `POLICY_SPOT_READ_DENY` (71) for an API key, also
   handle `API_KEY_POLICY_REQUIRED` (27).
3. Wherever you handle `POLICY_MARKET_DENY` (20) for a master-account API key,
   handle `API_KEY_MARKET_DENY` (29) instead: change the API key's market
   list.
4. Trading WebSocket clients that map `RejectCode` values: add 78.

Every refusal above is still a permission refusal: HTTP 403, ConnectRPC
`permission_denied`. Clients that only check that status need no change.
