## What and why

A sub-account policy's per-order notional cap (`maxOrderSize`) now refuses an
oversized stop-loss, take-profit, trailing stop, TWAP or OCO when it is
created, as it already refuses an oversized order or ladder level. Before, such
a trigger was accepted, then failed with `policy_max_notional` when it fired
and placed nothing. A protective stop-loss that could never execute looked
armed. The request, response and error messages are unchanged; `CreateTrigger`
and `CreateOco` can now answer an error they did not answer before.

The child order is valued at the price bound it would carry when it fires:

- a limit child at its limit price;
- a market stop-loss or take-profit at its trigger price moved by its slippage
  cap, or the pair's default cap when it sets none: up for a BUY, down for a
  SELL;
- a BUY trailing stop at its limit price; a SELL trailing stop at its first
  trigger level: its activation price, or the current best bid when it has
  none, less its trailing distance and slippage cap;
- a TWAP per slice: its largest slice, at its limit price, or for market slices
  at the current best price moved by the slippage cap;
- an OCO at each leg's order, for the OCO's whole quantity.

`ModifyTrigger` meets the same cap: a change that raises a live trigger's
order over `maxOrderSize`, such as a market stop's trigger price or slippage
cap, or an OCO leg's trigger price, is refused and the trigger keeps its
terms. A change that lowers the order's value is accepted even over a cap
lowered since the create, as for orders. A sell trailing stop's changes (its
activation price, trailing distance or slippage cap) are checked when it
fires, not when they are made: its trigger level follows the market up.

An order's attached take-profit, stop-loss and trailing stop meet the cap the
same way, each at its order's price bound for the order's quantity:
`CreateOrder`, `PreviewOrder` and each `BatchCreateOrders` item whose attached
exit is over the cap are refused, naming that leg, instead of resting and
failing when the exit fires. `ModifyOrder` and `BatchReplaceOrders` judge the
legs a change installs, unless it lowers the leg it replaces, and the legs it
keeps when it raises the order's quantity. A sell trailing stop has no upper
price bound, so its cap is checked when it fires.

Under-cap triggers, orders and ladders behave as before. A trigger whose policy
is lowered after it is created is still checked when it fires, and fails with
`policy_max_notional` there, as today. So is a SELL trailing stop that fires
above its first trigger level, a TWAP slice made larger by earlier slices that
did not fill, and a market TWAP created while the pair has no current price.

## How clients use it

Nothing changes in the request. An oversized create, or a modify that raises
a trigger's order over the cap, answers
`INVALID_ARGUMENT` with an `ErrorDetail` of code
`ERROR_CODE_POLICY_MAX_NOTIONAL`, the code an oversized `CreateOrder`
answers, and nothing is created or reserved. The message names the order that
could not be placed, and for a TWAP its slice number, for example "Its slice 3
can't be placed when it triggers (POLICY_MAX_NOTIONAL), so the trigger was not
created. Nothing changed." With a policy cap of 7.00 USDT, this stop-loss
(0.00013 BTC at a limit of 64,800 USDT, 8.42 USDT) is refused:

```http
POST /triggers.v1.TriggersService/CreateTrigger
Content-Type: application/json

{
  "subaccountId": "<subaccount id>",
  "trigger": {
    "symbolId": 1,
    "qtyScaled": "13000",
    "clientTriggerId": "sl-btc-1",
    "stopLoss": {
      "triggerPriceTicks": "64800000000000",
      "side": "BUY",
      "child": { "limitGtc": { "priceTicks": "64800000000000" } }
    }
  }
}
```

REST: `POST /v1/triggers` and `POST /v1/triggers/oco` answer the same code in
their problem body.

An order refused for an attached exit answers the same code, with a field
violation on that leg, for example `field_path`
`order.attached_risk.take_profit`, `rule_id` `POLICY_MAX_NOTIONAL`, message
"Its take-profit can't be placed when it triggers (POLICY_MAX_NOTIONAL), so
the order was not placed. Nothing changed." A batch item carries it on its
own result.

## Migration

None required. A client that sized triggers above its sub-account's
`maxOrderSize` now learns it at create instead of from a failed trigger. Size
each child within the cap, or raise the policy's `maxOrderSize`.
