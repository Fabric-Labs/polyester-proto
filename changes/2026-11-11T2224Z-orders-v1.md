## What and why

A batch replace (`BatchReplaceOrders`) whose items include one refused for its value no longer fails as a whole. Such an item has a price off the pair's tick size, a REST decimal with more fractional digits than the price scale, or an attached-risk price off the tick or otherwise invalid. Only that item is rejected, at its index, with its code and an indexed field violation. The other items are processed as usual, as batch create already does.

No message, field or enum changes.

## How clients use it

ConnectRPC `POST /orders.v1.OrdersService/BatchReplaceOrders`:

```json
{"requestId":"q-1","symbolId":1,"items":[
  {"clientOrderId":"a","newPriceTicks":"70000000000000"},
  {"clientOrderId":"b","newAttachedRisk":{"takeProfit":{"triggerPriceTicks":"80000001000000","child":{"marketIoc":{}}}}}]}
```

The call now answers 200. Item 1 has status `BATCH_REPLACE_ITEM_ADMISSION_STATUS_REJECTED`, code `PRICE_TICK_SIZE`, and error `ERROR_CODE_PRICE_TICK_SIZE` with the violation `items[1].new_attached_risk.take_profit.trigger_price_ticks`. Item 0 is processed as usual.

REST `POST /v1/orders/replace-batch` behaves the same way. A `newPrice` such as `"70000.0000000001"`, finer than the 9-digit price scale, rejects only its item, with `PRICE_TICK_SIZE` and the violation `items[1].newPrice`. Before this change it answered 400 for the whole request.

The rejected item keeps its `itemIndex`, and `GetBatchReplaceStatus` reports it rejected with the same code. An identical retry within the replay window returns the identical result. The decimal as sent is part of the request's identity, so a different value under the same `requestId` is a conflict, not a replay.

These value refusals are per item: `PRICE_TICK_SIZE`, `TRIGGER_PRICE_INVALID`, `TRIGGER_PRICE_SOURCE_UNSUPPORTED`, `TRAILING_DISTANCE_INVALID` and `MAX_SLIPPAGE_INVALID`. A malformed request is still refused as a whole with `INVALID_ARGUMENT` / 400. That covers an item that names no order or both IDs, an empty patch, or an attached-risk policy of the wrong shape (`VALIDATION_ERROR`, `BAD_PRICE`).

## Migration

Clients that treated an error answer of `BatchReplaceOrders` for one item's price as "nothing was applied" must now read the per-item results: the batch answers 200, and its other items may be admitted. Resend only the rejected items, corrected, in a new batch under a fresh `requestId`.
