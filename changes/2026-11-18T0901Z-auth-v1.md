## What and why

One MFA confirmation still covers a new user's Telegram and assistant setup, but
through the standard MFA-elevated session instead of a separate recent-MFA
window. Completing an MFA challenge already returns an MFA-elevated session
token (`SessionInfo.session_level` `MFA_ELEVATED`, with `auth_time`). For 30
minutes after that challenge, the same elevated session can:

- confirm a Telegram link (`SocialVerificationService.ConfirmSocialVerification`
  for `TELEGRAM`);
- change the Polyester AI assistant's account access
  (`ApiKeyService.SetAssistantKeys`, with policies or presets);
- raise or remove a Telegram approval limit
  (`ai.v1.AssistantService.SetTelegramApprovalLimits`).

This is the same rule the address book already follows. Setting or lowering a
Telegram limit still needs no MFA. Other actions retain their existing MFA
requirements; actions that require a fresh proof still require one.

Removed from the public contract:

- `MFAService.GetRecentMFA` and `MFAService.EndRecentMFA`, with
  `GetRecentMFARequest`, `GetRecentMFAResponse`, `EndRecentMFARequest` and
  `EndRecentMFAResponse`;
- the `RecentMFAAction` enum;
- the `AuthErrorCode` value `AUTH_RECENT_MFA_EXPIRED` (66).

Documentation only, no behavior change: `InternalTransferService.CreateInternalTransfer`,
`InternalTransferService.BatchCreateInternalTransfers` and
`WithdrawService.CreateWalletTradingWithdraw` now name the same MFA-elevated session (an MFA
challenge completed in the last 30 minutes, otherwise `AUTH_MFA_ELEVATION_REQUIRED`) where they
said "recent MFA", and the `MFA_RECENT` requirement in `polyester.api` options is described the
same way.

## How clients use it

The client reads its own session's elevation instead of asking the server: the
session token returned by `CompleteMFAChallengeResponse.access_token` carries
`session_level`, `auth_time` and the authentication methods.

1. Before one of the three actions, check the current session: if it is
   `MFA_ELEVATED` and `auth_time` is less than 30 minutes ago, send the call
   with that session and no `X-Auth-Step-Up` header.
2. Otherwise prompt for MFA (`BeginMFAChallenge`, then `VerifyTOTPChallenge`,
   `FinishPasskeyChallenge` or `VerifyRecoveryCodeChallenge`) and switch to the
   elevated `access_token` from the response for this and later calls.
3. `ConfirmSocialVerification` and `SetAssistantKeys` also still accept a fresh
   step-up proof in `X-Auth-Step-Up` from a session that is not elevated, and
   spend it.

Refusals:

- `ConfirmSocialVerification` and `SetAssistantKeys`: `PermissionDenied` with
  `AUTH_STEP_UP_REQUIRED` when the session is not elevated (or its elevation is
  older than 30 minutes) and carries no proof.
- `SetTelegramApprovalLimits` raising or removing a limit: `PermissionDenied`
  with `AUTH_MFA_ELEVATION_REQUIRED`.

```text
POST /auth.v1.MFAService/BeginMFAChallenge
{"purpose": "MFA_CHALLENGE_PURPOSE_SESSION_ELEVATION"}

POST /auth.v1.MFAService/VerifyTOTPChallenge
{"challengeId": "...", "code": "123456"}
-> {"session": {"sessionLevel": "MFA_ELEVATED", "authTime": "..."}, "accessToken": "..."}

POST /ai.v1.AssistantService/SetTelegramApprovalLimits   (Authorization: Bearer <accessToken>)
{"limits": {"perApprovalUsd": "500"}}
```

## Migration

1. Stop calling `GetRecentMFA` and `EndRecentMFA`; they no longer exist.
2. Decide whether to prompt from the current session token's `session_level`
   and `auth_time` (30 minutes), as above.
3. After an MFA prompt, use the elevated `access_token` it returns.
4. Treat `AUTH_STEP_UP_REQUIRED` and `AUTH_MFA_ELEVATION_REQUIRED` on these
   actions as "prompt for MFA, then retry with the elevated session". Remove
   handling of `AUTH_RECENT_MFA_EXPIRED`.
