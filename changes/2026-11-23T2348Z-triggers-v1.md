## What and why

`ListTriggers` takes a new optional filter, `client_trigger_id`: it lists the
triggers created with that client trigger ID, running or ended, newest first.
A client whose trigger create timed out, or failed with
`TRIGGER_CREATE_OUTCOME_UNKNOWN`, can now find its outcome with one read
instead of paging a pair's trigger history.

A client trigger ID is unique per sub-account, pair and trigger type only
while its trigger is active and for 60 seconds after it ends; after that a
new create can use it again. The filter can therefore match several
triggers. `symbol_id` and `trigger_type` keep one ID's scope, and the first
result is the latest create with the ID.

`ListTriggers` now also states its guarantees: a list reflects every trigger
request acknowledged before it, including a trigger that ended right after
its create, and fails with a retryable `UNAVAILABLE` until it can. An ended
trigger stays listable for at least 24 hours after it ends.

`LadderTrigger` now documents how a ladder's total quantity splits across
its levels and how each level is priced, so a ladder sized from a quote
amount can be converted exactly. Each level but the last gets the total
divided by the number of levels, rounded down to the pair's step size; the
last level gets the rest.

## How clients use it

ConnectRPC:

```bash
curl -sS https://<api-host>/triggers.v1.TriggersService/ListTriggers \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer <token>' \
  -d '{"clientTriggerId":"bot-1732400000-17","symbolId":1,"triggerType":"STOP_LOSS"}'
# 200 {"triggers":[{"triggerId":"...","clientTriggerId":"bot-1732400000-17","status":"STATUS_FAILED", ...}]}
```

REST:

```bash
curl -sS 'https://<api-host>/v1/triggers?clientTriggerId=bot-1732400000-17&symbol=BTC-USDT&triggerType=STOP_LOSS' \
  -H 'Authorization: Bearer <token>'
```

- An empty or longer than 36-byte value is rejected with `INVALID_ARGUMENT`
  and `ERROR_CODE_CLIENT_TRIGGER_ID_INVALID` (REST problem code
  `CLIENT_TRIGGER_ID_INVALID`).
- An empty list proves only what was true when the read was made: no
  trigger of the request's scope (its filters, the caller's sub-account)
  had been created with the ID, or the one that had ended more than 24
  hours ago. It does not prove a create of unknown outcome will never take
  effect: one still in flight can land after the read. To settle such a
  create, retry the identical create with the same client trigger ID while
  its window lasts; it returns the trigger it created, if any, instead of
  creating a second.
- `UNAVAILABLE` means the list is catching up; retry the same request. A
  successful list never leaves out a trigger whose create was acknowledged
  before the read.
- A list whose `status` filter names live statuses only (`CREATED`, `ARMED`,
  `RUNNING`, `PAUSED`) never reads ended-trigger history and is the
  cheapest to serve. Any list that can include ended triggers also reads
  their history.
- Follow realtime trigger updates to track triggers, and use `ListTriggers`
  to recover and reconcile (after a reconnect, a restart or a create of
  unknown outcome), not to poll.
- Paging, the limit (default 100, at most 1000) and the cost (one unit of
  the trading read limit per 100 rows asked) are unchanged. A page token is
  bound to the filter.
- An OCO's take-profit and stop-loss have no client trigger ID; find them
  with `client_list_id`.

## Migration

None required: the filter is optional. A `ListTriggers` page token issued
before this release is refused with `INVALID_ARGUMENT` once; start paging
again without it.
