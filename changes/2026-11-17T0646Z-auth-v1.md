## What and why

Policy templates are now applied as copies. A template is a reusable API key
or sub-account policy of the main account that is never attached to a key or
sub-account itself. Applying it attaches a new copy of its current revision,
so editing the template later changes nothing it was applied to. Before, the
template itself was attached, and an edit silently changed every key and
sub-account that used it.

- `SetApiKeyPolicy` and `SetSubaccountPolicy` given a template ID attach a new
  copy. Their responses now return `policy_id`, the policy now attached: the
  new copy when a template was named, the named policy otherwise, and 0 when
  the policy was cleared.
- `ApiPolicyView` and `SubaccountPolicyView` gain `source_template_revision`.
  With `source_template_id`, it records the template and the template revision
  the copy was made from. Both are set when the copy is made and never change,
  even when the template is later edited or deleted.
- `SubaccountPolicySpec` gains `is_template`, so sub-account templates can be
  created like API key templates.
- `is_template` is chosen at creation. An `update_mask` that selects it is
  refused with `InvalidArgument`, and the REST update of an API key policy no
  longer accepts `isTemplate`.
- A template cannot be created and attached in one call: `CreateApiPolicy`
  with `assign_to_key_id`, or `CreateSubaccountPolicy` with `subaccount_id`,
  together with `is_template` is refused with `InvalidArgument`.
- Only the main account owner creates, edits and deletes templates. A
  delegated sub-account admin may apply the main account's templates to the
  keys and sub-accounts it manages there, with the same role and fresh
  step-up as any other policy change.
- An assistant key refuses a template, in an assistant key set's
  `policy_id` and in `SetApiKeyPolicy`, with `FailedPrecondition` and
  `AUTH_POLICY_INVALID`; pass a policy or a preset.
- A template is never in use, so deleting it always succeeds; its copies
  keep their lineage.

Existing keys and sub-accounts that held a template now each hold their own
copy of it, with the same permissions.

## How clients use it

Create a template once, then apply it to each key or sub-account. Each call
needs a session with a fresh step-up.

```http
POST /v1/auth/policies/subaccounts
{"policy": {"name": "Market maker desk", "spotMarketScope": "ALL", "actions": ["TRADE_SPOT"], "isTemplate": true}}

PATCH /v1/auth/subaccounts/{subaccount_id}/policy
{"policyId": "<template id>"}
-> {"policyId": "<new copy id>"}
```

ConnectRPC: `/auth.v1.PolicyService/SetSubaccountPolicy` with
`{"subaccountId": "<id>", "policyId": "<template id>"}` returns
`{"policyId": "<copy id>"}`; `/auth.v1.PolicyService/SetApiKeyPolicy` with
`{"keyId": "ak_...", "policyId": "<template id>"}` works the same for API keys.

To see whether a copy is behind its template, compare the copy's
`sourceTemplateRevision` with the template's `revision`. To bring a target up
to date, apply the template again: it gets a new copy of the current revision.
To change one target only, edit its copy.

## Migration

1. Code that attached a template and later edited the template to change the
   keys or sub-accounts using it must now edit each copy, or apply the edited
   template again to each target.
2. Code that read a key's or sub-account's policy ID back and expected the
   template's ID gets the copy's ID; use `policy_id` from the set response, or
   `source_template_id` of the attached policy.
3. Stop sending `is_template` in update masks and REST policy updates, and
   create templates without `assign_to_key_id` or `subaccount_id`.
4. Assistant keys take a policy or a preset, never a template.
