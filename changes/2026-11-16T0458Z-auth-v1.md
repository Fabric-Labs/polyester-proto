## What and why

`SocialVerification` gains `change_available_at` (`changeAvailableAt` in JSON): the time in UTC from which the caller may change or unlink its linked X/Twitter or Discord account again. Each provider allows one change or unlink per 30 days. Until now a client learned that a user was inside that window only by attempting the change and reading the `AUTH_SOCIAL_CHANGE_LIMIT_REACHED` rejection, after the user had gone through MFA and entered the new account's details.

The field is set whenever the 30-day rule applies, whether or not a verification failed, and is empty when a change or unlink is allowed now (always for Telegram). A first link, a link after an unlink, and a re-verification of the linked X/Twitter handle are not changes, and stay allowed while it is set.

`StartSocialVerification` and `UnlinkSocialAccount` now check the 30-day rule before asking for a step-up: a refused change answers `AUTH_SOCIAL_CHANGE_LIMIT_REACHED` (with `retry_after` equal to `change_available_at`) without first answering `AUTH_MFA_NOT_ENROLLED`, and a step-up proof sent with it stays unspent.

## How clients use it

Read the verification for each provider with the session token, as before, and disable Change and Remove while `changeAvailableAt` is set:

```http
GET https://<api-host>/v1/auth/social/verification?provider=DISCORD
```

ConnectRPC: `POST /auth.v1.SocialVerificationService/GetSocialVerification` with `{"provider": "DISCORD"}`.

```json
{
  "verification": {
    "provider": "DISCORD",
    "status": "STATUS_VERIFIED",
    "verifiedAt": "2026-11-08T09:12:44.512031Z",
    "changeAvailableAt": "2026-12-08T09:12:44.512031Z"
  }
}
```

The responses of `StartSocialVerification`, `SocialVerificationReady` and `UnlinkSocialAccount` carry the field too: after an unlink it shows when the provider's account can next be changed. API keys read the status view of `GetSocialVerification`, which leaves the field empty.

## Migration

None: the field is new and optional. Clients that ran a change flow to find the limit can read `changeAvailableAt` instead, and need not ask for MFA before calling `StartSocialVerification` or `UnlinkSocialAccount` for a change the rule refuses.
