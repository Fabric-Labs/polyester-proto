## What and why

`auth.v1.AuthErrorCode` gains seven values. Each names a reason a request's
credentials were refused:

- `AUTH_SIGNATURE_INVALID`: the API key signature does not verify, or the key is unknown.
- `AUTH_TIMESTAMP_SKEW`: the request timestamp is malformed or too far from the server clock.
- `AUTH_MISSING_HEADERS`: the timestamp or signature header is missing.
- `AUTH_KEY_EXPIRED`: the API key has expired.
- `AUTH_KEY_DISABLED`: the API key is disabled or revoked.
- `AUTH_IP_NOT_ALLOWED`: the key's IP allowlist does not include the request's source address.
- `AUTH_API_KEY_NOT_ACCEPTED`: the API does not accept API keys.

Order reads, order and trigger writes, and balance reads now answer a refused
ConnectRPC, gRPC or gRPC-web call with a ConnectRPC error: code
`unauthenticated`, a message, and an `auth.v1.AuthErrorDetail` that carries
the reason. Before, these calls got a REST problem body. Connect clients then
saw only `unauthenticated` with the message "401 Unauthorized" and no details,
so they could not tell a bad signature from a skewed clock or a blocked
address.

One exception: a request with no credentials at all, or with a missing,
malformed or expired session token, is not an API-key failure. It gets the
existing `AUTH_AUTHENTICATION_REQUIRED`, not one of the new values.

REST calls are unchanged: HTTP 401 with an `application/problem+json` body
whose `code` is the same reason without the `AUTH_` prefix (`SIGNATURE_INVALID`,
`TIMESTAMP_SKEW`, `IP_NOT_ALLOWED`, and so on). The exception's REST code is
`UNAUTHENTICATED`.

## How clients use it

A refused ConnectRPC call returns HTTP 401 with this body:

```bash
curl -sS https://<api-host>/orders.v1.OrdersReadService/GetOpenOrders \
  -H 'Content-Type: application/json' -H 'Connect-Protocol-Version: 1' \
  -H 'X-API-KEY-ID: <key-id>' -H 'X-API-TIMESTAMP: <ms-since-epoch>' \
  -H 'X-API-SIGNATURE: <signature>' -d '{}'
# 401
# {"code":"unauthenticated","message":"API key signature is invalid",
#  "details":[{"type":"auth.v1.AuthErrorDetail","value":"<base64>"}]}
```

The decoded detail is `{"code": "AUTH_SIGNATURE_INVALID", "message": "API key
signature is invalid"}`. Connect, gRPC and gRPC-web clients read it from the
error's details. For example, with connect-go:

```go
var connectErr *connect.Error
if errors.As(err, &connectErr) && connectErr.Code() == connect.CodeUnauthenticated {
	for _, d := range connectErr.Details() {
		if v, _ := d.Value(); v != nil {
			if detail, ok := v.(*authv1.AuthErrorDetail); ok {
				switch detail.GetCode() {
				case authv1.AuthErrorCode_AUTH_TIMESTAMP_SKEW:
					// Sync the clock, then sign the request again.
				case authv1.AuthErrorCode_AUTH_IP_NOT_ALLOWED:
					// Call from an address on the key's allowlist.
				}
			}
		}
	}
}
```

The same REST call answers `{"type": ".../signature-invalid", "status": 401,
"code": "SIGNATURE_INVALID", ...}` as `application/problem+json`, as before.

## Migration

None: the change is additive. Clients that only check for `unauthenticated`
keep working. To act on the reason, read `auth.v1.AuthErrorDetail` from the
error's details. Clients built on the previous contract decode the new values
as unknown enum numbers (48 to 54).
